# 精确索引的设计：TU 是唯一的索引单位

**约束（你刚定的三条，它们一起把方案空间压到了几乎只剩一条路）：**

```text
1. 索引必须精确 —— 连 std:: 的作用域都要对
2. 多数项目没有构建信息（没有 compile_commands.json / .vcxproj），必须支持
3. STL / SDK 每次随项目一起索引，不做"只索引项目文件"的裁剪
```

先说清楚为什么"模糊索引"在你这三条下不成立，这不是口味问题：

```text
std:: 的名字在头文件里是写成 _STD_BEGIN / _GLIBCXX_BEGIN_NAMESPACE_VERSION 的，
它到底展开成什么，取决于**谁包含它、在什么宏状态下包含它**。
没有构建信息 ⇒ 没有 -D 列表 ⇒ 只有"按 include 图走出来"这一条路能得到环境。
所以：想精确，就必须真的为每个文件算出它的宏环境；想便宜，就必须承认不精确。
你选了精确，那么就只剩"把精确做快"这一条路。
```

## 一、现在的设计错在哪（不是实现，是单位）

我们现在把"文件"当作索引单位：为**每个文件**单独算宏环境、单独解析、单独抽 facts，
再因为第一遍拿不到环境而做第二遍修复。对 STL 来说这是 1 761 份工作，其中绝大多数文件
**被几十上百个 TU 共享**，于是同一个文件的环境与解析被重复计算了几十上百次。

**正确的索引单位是 TU（每个源文件一次）**，理由不是跟 clangd，而是你的约束本身：

```text
· 编译器只编译 TU；头文件没有"自己的环境"，它的环境来自包含它的那个 TU
· 一个 TU 解析一次，就能得到该 TU 里所有文件在**那一刻的宏状态**下的精确 facts
  （std:: 的作用域因此是对的：TU 的解析里 _STD_BEGIN 已经展开）
· 头文件里声明的名字，由"包含它的所有 TU"共同提供；同名同位置自然合并
· 单独打开一个没有 TU 包含它的头文件时，把它当作自己的 TU 索引一次即可
```

于是：**索引路径 = 项目里每个源文件读一次 TU，facts 按来源文件归档**。
这恰好是我们已经有、但没被用起来的 `FileIndexer::index_unit_rendering`。

## 二、成本从哪来，能不能降下来（全部是实测数字）

一次 TU 读（`LuaSource.cpp`，闭包 110 文件、渲染后 2 MB、594k token）：

```text
render（宏展开 + 生成文本 + span）   913 ms
parse（含词法 24 ms）                387 ms
sweep（抽 facts + 按文件归属）      3 200 ms
```

198 个 TU 的话是 15 分钟 —— 但这里面**绝大部分是重复的**，因为 198 个 TU 共享同一批头文件。
所以三刀，按收益排序：

```text
① 渲染按文件缓存，键 = (文件内容, 到达该文件的宏环境哈希)
   一个头文件在 198 个 TU 里的环境通常相同 → 渲染一次、复用 198 次
   收益：render 913 ms → 首个 TU 付，之后只付真正变化的头文件

② facts 按文件缓存，键 = 同上
   TU 解析后，只对"这个 (内容, 环境) 组合以前没见过"的文件抽 facts
   收益：sweep 3 200 ms → 首个 TU 付，之后接近 0

③ ②命中之后，每个 TU 的边际成本 ≈ parse（387 ms）
   198 个 TU ≈ 77 s 的首建（后台、可缓存）；简单项目（20 个源文件）≈ 8 s
   第二次打开只解码（91 ms/TU，已实测）
```

**注意 ①② 的键必须包含环境**，否则宁可不用：同样的文本在不同宏状态下是不同的程序，
缓存错了就是"精确"的反面。这一点我们已经在 summary 上踩过一次（`env_hash`）。

## 三、要删掉的东西（删了才叫换了模型）

```text
· provisional summary 这个概念（TU 解析不需要"先猜后修"）
· 第二遍：parsed_since_the_last_pass / prepare_the_re_read / commit_the_re_read
· 按文件的闭包走查（units_for_the_pass 里每文件一跳）
· 诊断对 pending_work 的全局门控（精确性由 TU 保证，不由"全部读完"保证）
· RE_READ_SLICE / COOK_SLICE / 写锁预算这一族只为修补存在的旋钮
保留：summary（它变成 TU 产物的 per-file 片段）、cache.redb、unit/unit_indices 表、
      cook（打开文件的精确视图）、Session::view
```

## 四、没有构建信息时，TU 从哪来

```text
· 源文件清单：项目根下按扩展名扫描（.c/.cc/.cpp/.cxx/.m/.mm），已有能力
· 编译参数：现有配置阶梯（docs/no-build-database.md）：编译器推断、include 目录、-D、标准
· 头文件：不作为 TU 生成，只在被包含时进入索引；单独打开时按需索引一次
· 风险：一个"仅头文件"的库（header-only）没有源文件 → 把它的头文件当成 TU（配置可指定）
```

## 五、验收指标（每一步都可独立量）

```text
M1  单个 TU 的 render/facts 按 (内容, 环境) 命中缓存：第二次读同一 TU ≤ 100 ms（已有 91 ms）
M2  198 个 TU 的首建总时长：目标 ≤ 90 s（现在按文件路径 131 s，但没有精确性保证）
M3  简单项目（≤30 个源文件）：首建 ≤ 10 s，首屏 ≤ 1 s
M4  编辑一个文件：只重算它的 TU（≤ 1 s），不触发全项目
M5  std:: 成员在补全里出现，且范围正确（这是"精确"的验收）
```

## 六、这条路的风险，先说清楚

```text
· 首建仍然要付"每个 TU 一次解析"的钱；198 个 TU 不可能变成 0
  → 除非接受后台化（clangd 的做法），而你的第 3 条要求"每次随项目一起索引"，那就必须后台
· 环境哈希的粒度：同一头文件在不同 TU 里环境不同是常态（-D 不同），缓存命中率取决于项目
  → 先做 ①，量命中率，再决定 ② 值不值
· 手写 parser 的 parse 是 387 ms / 594k token；这是地板，除非重写 parser
```
