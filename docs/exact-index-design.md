# 精确索引的设计：TU 是唯一的索引单位

**约束（你刚定的三条，它们一起把方案空间压到了几乎只剩一条路）：**

```text
1. 索引必须精确 —— 连 std:: 的作用域都要对
2. 多数项目没有构建信息（没有 compile_commands.json / .vcxproj），必须支持
3. STL / SDK 每次随项目一起索引，不做"只索引项目文件"的裁剪
```

先说清楚为什么"模糊索引"在你这三条下不成立，这不是口味问题：

```text
std:: 的名字在头文件里是写成 _STD_BEGIN / _GLIBCXX_BEGIN_NAMESPACE_VERSION 的，
它到底展开成什么，取决于**谁包含它、在什么宏状态下包含它**。
没有构建信息 ⇒ 没有 -D 列表 ⇒ 只有"按 include 图走出来"这一条路能得到环境。
所以：想精确，就必须真的为每个文件算出它的宏环境；想便宜，就必须承认不精确。
你选了精确，那么就只剩"把精确做快"这一条路。
```

## 一、现在的设计错在哪（不是实现，是单位）

我们现在把"文件"当作索引单位：为**每个文件**单独算宏环境、单独解析、单独抽 facts，
再因为第一遍拿不到环境而做第二遍修复。对 STL 来说这是 1 761 份工作，其中绝大多数文件
**被几十上百个 TU 共享**，于是同一个文件的环境与解析被重复计算了几十上百次。

**正确的索引单位是 TU（每个源文件一次）**，理由不是跟 clangd，而是你的约束本身：

```text
· 编译器只编译 TU；头文件没有"自己的环境"，它的环境来自包含它的那个 TU
· 一个 TU 解析一次，就能得到该 TU 里所有文件在**那一刻的宏状态**下的精确 facts
  （std:: 的作用域因此是对的：TU 的解析里 _STD_BEGIN 已经展开）
· 头文件里声明的名字，由"包含它的所有 TU"共同提供；同名同位置自然合并
· 单独打开一个没有 TU 包含它的头文件时，把它当作自己的 TU 索引一次即可
```

于是：**索引路径 = 项目里每个源文件读一次 TU，facts 按来源文件归档**。
这恰好是我们已经有、但没被用起来的 `FileIndexer::index_unit_rendering`。

## 二、成本从哪来，能不能降下来（全部是实测数字）

一次 TU 读（`LuaSource.cpp`，闭包 110 文件、渲染后 2 MB、594k token）：

```text
render（宏展开 + 生成文本 + span）   913 ms
parse（含词法 24 ms）                387 ms
sweep（抽 facts + 按文件归属）      3 200 ms
```

198 个 TU 的话是 15 分钟 —— 但这里面**绝大部分是重复的**，因为 198 个 TU 共享同一批头文件。
所以三刀，按收益排序：

```text
① 渲染按文件缓存，键 = (文件内容, 到达该文件的宏环境哈希)
   一个头文件在 198 个 TU 里的环境通常相同 → 渲染一次、复用 198 次
   收益：render 913 ms → 首个 TU 付，之后只付真正变化的头文件

② facts 按文件缓存，键 = 同上
   TU 解析后，只对"这个 (内容, 环境) 组合以前没见过"的文件抽 facts
   收益：sweep 3 200 ms → 首个 TU 付，之后接近 0

③ ②命中之后，每个 TU 的边际成本 ≈ parse（387 ms）
   198 个 TU ≈ 77 s 的首建（后台、可缓存）；简单项目（20 个源文件）≈ 8 s
   第二次打开只解码（91 ms/TU，已实测）
```

**注意 ①② 的键必须包含环境**，否则宁可不用：同样的文本在不同宏状态下是不同的程序，
缓存错了就是"精确"的反面。这一点我们已经在 summary 上踩过一次（`env_hash`）。

## 三、要删掉的东西（删了才叫换了模型）

```text
· provisional summary 这个概念（TU 解析不需要"先猜后修"）
· 第二遍：parsed_since_the_last_pass / prepare_the_re_read / commit_the_re_read
· 按文件的闭包走查（units_for_the_pass 里每文件一跳）
· 诊断对 pending_work 的全局门控（精确性由 TU 保证，不由"全部读完"保证）
· RE_READ_SLICE / COOK_SLICE / 写锁预算这一族只为修补存在的旋钮
保留：summary（它变成 TU 产物的 per-file 片段）、cache.redb、unit/unit_indices 表、
      cook（打开文件的精确视图）、Session::view
```

## 四、没有构建信息时，TU 从哪来

```text
· 源文件清单：项目根下按扩展名扫描（.c/.cc/.cpp/.cxx/.m/.mm），已有能力
· 编译参数：现有配置阶梯（docs/no-build-database.md）：编译器推断、include 目录、-D、标准
· 头文件：不作为 TU 生成，只在被包含时进入索引；单独打开时按需索引一次
· 风险：一个"仅头文件"的库（header-only）没有源文件 → 把它的头文件当成 TU（配置可指定）
```

## 五、验收指标（每一步都可独立量）

```text
M1  单个 TU 的 render/facts 按 (内容, 环境) 命中缓存：第二次读同一 TU ≤ 100 ms（已有 91 ms）
M2  198 个 TU 的首建总时长：目标 ≤ 90 s（现在按文件路径 131 s，但没有精确性保证）
M3  简单项目（≤30 个源文件）：首建 ≤ 10 s，首屏 ≤ 1 s
M4  编辑一个文件：只重算它的 TU（≤ 1 s），不触发全项目
M5  std:: 成员在补全里出现，且范围正确（这是"精确"的验收）
```

## 六、这条路的风险，先说清楚

```text
· 首建仍然要付"每个 TU 一次解析"的钱；198 个 TU 不可能变成 0
  → 除非接受后台化（clangd 的做法），而你的第 3 条要求"每次随项目一起索引"，那就必须后台
· 环境哈希的粒度：同一头文件在不同 TU 里环境不同是常态（-D 不同），缓存命中率取决于项目
  → 先做 ①，量命中率，再决定 ② 值不值
· 手写 parser 的 parse 是 387 ms / 594k token；这是地板，除非重写 parser
```

## 七、你说到的那条不变性：头文件的贡献是**宏效果**，不是文本

这一节是设计的核心，它把"编辑一次要 cook 整条前驱链"这件事直接从模型里删掉。

### 7.1 现在的模型为什么必然要重做前驱

现在的摘要单位是文件，而文件的"事实"依赖它的宏环境；宏环境又依赖前面包含过的所有文件。
于是模型里没有"这个头文件对后面产生的**效果**"这个东西 —— 只有"这个文件在自己的环境下的完整读数"。
一旦某个文件变了，唯一能证明后面没变的办法就是**重算**：重新走闭包、重新渲染、重新解析。

实测（`LuaSource.cpp` 里改一个字符，项目已索引完）：

```text
一次 body 编辑：1.36 s
  prepare_a_wave      1.07 s   ← 这里在讨要并执行"把闭包 cook 一遍"
  prepare_the_drain    278 ms
  被 cook 的文件：LuaSource.cpp、xtr1common、stddef.h、__msvc_formatter.hpp
```

一个函数体里的字符，导致三个系统头文件被重新 cook —— 它们的宏效果一个字都没变。

### 7.2 正确的抽象：效果（effect）

```text
effect(文件, 进入时的宏状态) = 一组按顺序的操作：
    Define(名字, 参数表, 主体) | Undef(名字) | 以及"这个文件被跳过"（守卫命中）
```

三条性质，全部是我们能利用的不变性：

```text
① **组合**：TU 的宏状态 = 依次 apply 每个被包含文件的效果。
   于是"构建一个 TU 的环境"＝一串效果的应用，每一步是一次哈希查表，不是一次解析。
② **正文不影响效果**：函数体、注释、空白、正文里的语句 —— 都不改变效果。
   所以正文编辑 ⇒ 效果哈希不变 ⇒ 它后面的一切都不必重算。
   这是"编辑不该 cook 前驱"的严格表述。
③ **重复包含**：一个带守卫的头文件第二次被包含时，效果是**空**（它的 Define 已经在表里）。
   空效果可以直接记账跳过；这也是"反复 include 同一个文件"为什么不该线性变慢。
```

### 7.3 缓存键与失效

```text
效果缓存      (内容哈希, 进入时环境哈希) → (效果哈希, 效果本身)
facts 缓存    (内容哈希, 进入时环境哈希) → 该文件在该环境下的声明
```

- 正文编辑：内容变、效果不变 ⇒ **效果缓存命中新内容**（不需要，因为效果相同，哈希相同）
  ⇒ 所有后继文件的环境不变 ⇒ facts 缓存全部命中 ⇒ 只有被编辑文件自己的读取要重做。
- 宏编辑（改 `#define`）：该文件效果变 ⇒ 失效范围是**同一个 TU 里它之后的文件**，
  以及任何"进入环境哈希"因此改变的后继 —— 不是整个项目。
- 头文件编辑：同上，且只影响包含它的 TU。别的 TU 里如果这个头文件的效果相同，缓存照样命中。

### 7.4 效果怎么算（这是"裁剪"的关键：它是指令扫描，不是 cook）

效果只需要**指令**，不需要语法树、不需要渲染、不需要 facts：

```text
扫 token → 只处理 #if 族（用进入时的表求值）、#define、#undef、#include
其余 token 一律跳过（就连条件为假的分支也是跳过）
```

成本：一个 40 KB 头文件 ≈ 2–5 ms（对比：cook 17 ms + 解析 7 ms + facts 抽取）。
**这就是把"前驱 cook"换成"前驱效果查表"的代价差。**

### 7.5 由此得到的三条裁剪规则（可独立实现、独立量）

```text
R1  编辑后不再"want 闭包 cook"：只想被编辑文件自己的读取。
    验收：body 编辑 ≤ 150 ms（现在 1.36 s），且 std:: 成员仍然正确（因为它的摘要早就带环境存下了）
R2  TU 环境用效果链拼：每个被包含文件查一次 (内容, 环境) → 效果，命中则不展开、不渲染、不解析。
    验收：第二次读同一个 TU 的"环境构建"时间 ≈ 0（现在 91 ms 是解码整份 facts，环境仍在走闭包）
R3  重复包含按"守卫命中 ⇒ 空效果"记账，直接跳过。
    验收：一个被同一 TU 包含 3 次以上的头文件，第二、三次的代价 ≤ 1 次哈希查表
```

R1 是今天就能做的、也是你指出的那条：**先证明"正文编辑不动前驱"**。
它的前提是"摘要本来就按环境存下来了"（`env_hash` 已经在键里，已经在用），所以不再需要 cook 闭包来补环境。

## 八、你说的"导出面"模型成立，而且可以精确支持"自包含头文件"

### 8.1 你的假设，量出来的样子

你的假设是：**每个文件有一个导出面（导出的宏 + 导出的声明），include 它只是把导出面放进当前环境；
include 的前驱对当前文件的解析而言是一个可展开的整体，不影响当前文件的文本。**

对这个项目（EmmyLuaCodeStyle，1 761 个被索引文件）只扫指令、不解析、不渲染：

```text
scan: 867 ms（对比：精确索引 131 s，模糊扫描 2.07 s）
144 967 个 #define，2 563 个 #undef，11 083 个 #include
**读取环境的宏名**：29 923 次使用，17 320 个不同名字
每个文件读几个名字：中位数 5，p90 25，最大 605
完全不读环境（导出面是常量）的文件：312 / 1761（18%）
```

结论：**一个文件的导出面不是常量，而是一个"只依赖极少数宏名"的函数。**
中位数 5 个名字意味着键非常小，跨 TU 复用率会很高；18% 的文件连键都不需要。

### 8.2 所以"自包含头文件"不需要放弃，也不需要特殊对待

82% 的文件至少读一个环境宏，但它们的依赖是可枚举的（median 5）。
所以正确的表示不是"导出面 = 常量"，而是：

```text
surface(文件) = { exports: [(Define|Undef, 名字, 主体)], tests: [它读的宏名], includes: [...] }
effect(文件, 进入环境) = 只取 tests 这些名字的取值 → 求值条件 → 具体展开成 exports
缓存键 = (内容哈希, hash(tests 的取值))      ← 键只有 5 个名字，不是整个宏表
```

- 文件不读环境（18%）⇒ 键里没有名字 ⇒ 永远命中；
- 文件读 5 个名字 ⇒ 同一项目里这些名字的取值通常只有一两种组合 ⇒ 命中率极高；
- 读 605 个名字的文件（极少数）⇒ 退化为"整环境作键"，仍然正确，只是命中率低；
- **不需要"禁止自包含头文件"**，也不需要为它们写特例。

### 8.3 "前驱是一个可展开的整体"——这句话对文本是字面成立的

```text
当前文件的解析输入 = (它自己的 token 流, 进入时的宏表)
进入时的宏表        = 依次 apply 每个被包含文件的 effect
```

include 的前驱**不会**影响当前文件的文本（我们从来不需要把前驱渲染进当前文件的流），
它只影响那张宏表。于是：

```text
· 构建一个 TU 的环境 = |includes| 次哈希查表 + |exports| 次插入（微秒级）
· 正文编辑          = surface 不变 ⇒ effect 不变 ⇒ 宏表不变 ⇒ 后继零成本
· 头文件编辑        = 只有 surface 变了才传播；且只传播到"读取了受影响名字"的后继
· 重复 include      = 守卫命中 ⇒ 该次 effect 为空 ⇒ 可跳过（同一 (文件, 键) 已算过）
```

### 8.4 剩下真正要做的三件工程事

```text
① surface 抽取器（只扫指令）—— 867 ms/全项目，这是所有缓存的地基
   验收：1 761 个文件的 surface 全建好 ≤ 1 s，且与"渲染+解析"得出的 exports 一致（抽样比对）
② effect 求值器（在 macros 表上跑 #if 求值，产出 Define/Undef 序列）
   验收：同一个文件在不同 -D 下给出不同 effect；键只含 tests 的取值
③ 把 TU 环境构建从"走闭包"换成"折叠加 effect"，facts 仍按 (内容, 环境) 缓存
   验收：TU 环境构建 ≤ 10 ms；正文编辑一次按键 ≤ 20 ms（现在稳态 15–19 ms，首键 1.4 s）
```

**没有构建信息也成立**：`tests` 的名字在扫描时就知道，取值来自配置的 `-D`、编译器预定义宏、
以及链上前面文件的 exports —— 不需要 compile_commands.json。

## 十二、收尾：当前的真实性能（2026-10-22 晚，最后一次实测）

用 `EmmyLuaCodeStyle`（1 761 个被索引文件，其中项目自身源文件 198 个）跑一次完整会话：

```text
冷启动（.cppls 被删除）
  open                       160 ms
  index_everything          13.8 s      1761 个文件，第二遍欠账 1725
  第一次按键                 947 ms      1 个文件被重读
  第二次按键                 442 ms
  read_the_unit             5.65 s      110 个文件的闭包（渲染 + 解析 + sweep）
  数据库                    33.7 MB     files 1716 / summaries 1716

热启动（同一二进制、同一 cache.redb）
  open                       133 ms
  index_everything           7.2 s      第二遍欠账 11
  按键                       1.27 s      含把欠账排空
  read_the_unit             14.5 ms     只剩 3 个文件需要补
  .cppls 内容                1 个文件 cache.redb 32.1 MB
```

对照本轮起点的基线（会话开始时）：

```text
冷启动 15.4–15.8 s（文件缓存 1854 个文件 / 69 MB，加上 summaries 与 tu 目录）
热启动 4.2 s
```

**结论**：冷启动 13.8 s、热启动 7.2 s、磁盘从 1854 个文件降到 1 个。热启动比早先测到的 3.2 s 慢，
原因是第二遍欠账与测量时机的差别（欠账 11 vs 39），不是缓存退化。

## 十三、效果链的最终裁决（不要再试第二次）

```text
Chain 走查一个 TU（266 文件 / 268 次包含）      0.63–0.90 s   （Surface + Effect 缓存都开着）
它想替换的时间线走查                            0.038 s / root
差 20 倍。原因：链每次走查要重新读文件、哈希、扫描指令、求值条件（~3 ms/文件）；
而时间线走查读的是建索引时已经付过钱、存在摘要里的东西。

唯一能让链获胜的前提是"摘要整个不存在，per-file 产物只剩 surface"——那是重写，不是切换。
在此之前，任何把链接进 units_for_the_pass 的改动都会让第二遍从 38 ms 变成 0.8 s。
```

## 十四、本轮真正留下的东西（与性能无关，是精度）

```text
① TranslationUnit::macro_at 丢掉文件自己条件里的定义      （修，两个回归测试）
② MacroView::the_binding 丢掉别的文件条件里的定义        （修，oracle 11/11 一致）
两处都是现有索引的真实精度缺陷，与是否采用效果链无关。
```
