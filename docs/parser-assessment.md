# parser 评估：够不够好，以及"够好"是对什么而言

这份文档回答一个问题，**只回答一次**：`cpp_parser` 现在处在什么水平，够不够用，不够的地方挡着什么。
所有数字都能用 `std_probe` / `cpp_dump` 重跑（命令见 [`std-library.md`](std-library.md) §实测）。
队列与缺口登记在 [`roadmap.md`](roadmap.md) §2 和 [`grammar-gaps.md`](grammar-gaps.md)，
这一份是**判断**，不是登记处。

---

## 1. 三个语料上的实测（本机 g++ 15.1.0 / libstdc++ + MinGW-w64）

| 语料 | 文件 | 干净 | 报错 | 消息 | parse | 说明 |
|---|---|---|---|---|---|---|
| **分析闭包**（一个 TU 的 include 传递闭包，含未取分支） | **455** | **400 (88%)** | 55 | 352 | 2.0 s / 10.3 MB | 语义层实际读的那一份 |
| 编译器实际读的（同一 TU，`g++ -M`） | 120 | 76 (63%) | 42 | — | — | 同一台机器、同一个 TU |
| libstdc++ 闭包（历史数字都用它） | 128 | 100 (78%) | 28 | 283 | 0.42 s / 2.7 MB | 只有 `<vector>/<string>/<map>/<algorithm>` |

（455 那一行是第十八轮之后的数字：B44/B45/B46 把它从 328/127/3383 推到 335 行那一版，第十七轮六个语法构造（B47–B52）推到 342/113/2359，第十八轮十六条（B53–B68：五条在 `bits/alloc_traits.h` 那条链上、一条是恢复、两条在 GCC 头文件那一族、一条是方言、七条是判据缺证据/接缝/缺规则）推到 400/55/352。）

**最重要的一行对比：我们读 455 个文件，编译器读 120 个。** 多出来的 **342 个是"未取分支里的文件"**——
`#if defined(_WIN32)` 两条路我们都读（这是刻意的：用户在哪个平台上都在写代码）。而那 342 个恰好是
**宏最密、拼写最编译器私有**的一批（`winnt.h`、`_mingw.h`、各种 `*intrin.h`）。所以"干净率"必须连着
"读的是哪一批"一起看：把编译器不读的文件算进来，仍有 72%。

**每文件错误数**（455 文件那份）：`干净 400 | 只有一条 13 | 两到五条 26 | **超过五条 16**`。
54 个文件是**级联**——首错背后还压着好几个不同构造，首错是唯一可行动的那一条（维护约定第 11 条）。

**首错的成因**（55 个失败文件）：**56% 的首错落在"整个闭包定义过的某个宏"出现的那一行**（±2 行的窗口、
按词匹配，是**上界**）；**18% 落在"这个文件自己定义的宏"那一行**（下界）。中间那 44% 就是"宏在别处定义、
用在这里"，也正是外部符号表/宏环境要解的那一格。

## 2. 它好在哪（都有证据，不是感觉）

1. **无损 + 良构**：`tests/invariants.rs` 12 条（逐字节重建、每个节点良构）在所有语料上零例外。
   这是下面一切的底座：树可以**当作文字**用（range 就是 offset）。
2. **容错且不崩**：任何输入都给一棵树和一份事实，没有 panic。历史上唯一一次 panic 是这一轮引入的
   （"向前 rollback"破坏了父子指针），发现方式是语料里 `bits/tuple`，教训记成维护约定第 35 条。
3. **普通项目代码干净**：探针里的 TU、`tests/real_world.cpp`（门禁第四条）、所有 fixture 都是 0 error。
   报错集中在系统头——**不是"读不了 C++"，是"读不了编译器自己的 header 写法"**。
4. **宏这件事上，它做对了一件关键的事**：不猜。宏的名字有证据表（`MacroTable`：本文件的 `#define`）、
   宏的**形状**进了 `MacroBody`（`Statement`/`Specifier`/`Type`/`Expression`/`Block`）、接缝处读成
   `MacroCall`，而不是"看到大写名字就当宏"。第 16 条（约定要换成证据）就是这条的成文法。
5. **纪律**：改动必须带形状断言（`gaps.rs` 15 条），读法登记处 35 条维护约定，`READING_FINGERPRINT`
   让"改了 parser 忘了作废缓存"变成不可能。**这是这个仓库最值钱的部分**，比干净率高多少都值钱。
6. **parse 不是瓶颈**：455 个文件 parse 1.78 s，而 parse + scopes + facts 是 9.74 s——**语义层比 parser 贵
   4.5 倍**。想让它更快，方向不在 parser。

## 3. 它不够好在哪（按"对产品的代价"排序）

1. **宏形状的构造是最大一族**（52%，见上）。这一族的特点是：**不是"少读了一个构造"，而是"一个构造读错，
   整条声明连同它后面的成员一起没了"**。所以它对语义层的伤害是**乘法**：标准库里 `basic_string` 的成员
   曾经因为一个宏形状从 442 条变成 0 条。
2. **伤害有爆炸半径，而且不只是"这个文件的事实不可信"。** 这一轮的实测：`winnt.h` 有 417 条错，代价是
   **指令丢了八条 `#endif`**（扫描器看到 204 个 `#if`、196 个 `#endif`）——于是**条件嵌套本身不可信**，
   而"哪个宏在这里生效"这类分析全部依赖嵌套。安全网（指令不配平时一条都不认）挡住了 184 条**错答案**，
   但代价是那个文件上的条件分析全部降级。**parser 的错会顺着派生分析扩散到"这个文件之外的结论"。**
3. **恢复**（普查看不见，只有形状断言能看）——**两处都在第十二轮修了，但修法不同，值得对照**：
   - 成员访问运算符后面什么都没有时，恢复会吃掉块的 `}`（第 20 条）：**症状修复**，因为症状是可复现的
     （`w.` 之后 `int after;` 变成函数局部），修法是"补一个零宽节点 + 报告 + 别让 `Err` 穿过语句层"；
   - 失败的试探性解析不回滚诊断（`rollback` 不清 `errors`）：**契约修复**。修它之前先量了一遍——
     插桩跑遍两个语料（583 个文件）加 53 段片段，**没有任何输入走到过这条路上（0 次）**。
     所以它的钉子不是文件形状的，而是三条直接驱动 parser 的单测。
     ⚠️ **本评估的初版把这条写成"在 `cast.cpp` 上观察到"，那是错的**：没有任何记录支持它，
     复现也没找到。留着这句话是因为**"记录里没验证过的观察"本身就是一种缺陷**，而且是这份文档要防的那种。
   两处都属于"普查数不出来"的那类（第 29 条），而且**都没让普查的数字动一个**（见 §6）。
4. **现代拼写与 GNU/MS 扩展的长尾**（各 1–3 个文件，但每个都挡着一个类）：模板参数表里的宏（§2.5）、
   `if constexpr` + requires 表达式、推导指引、`__int128` / `__typeof__` / `__attribute__` 的位置、
   `::new` 后面跟宏、指向成员的指针（`->*`）、**函数定义里的 `try`（B42）**、**条件里的声明（B43）**。
5. **我们不知道自己错得多厉害。** 干净率只数报错；**错树率没有任何度量**。唯一的仪器是 `gaps.rs` 的形状断言，
   相对 3.4 MB 的系统头来说很薄。第 29 条（两个数字一起看）说的就是这件事。

---

## 4. 结论：对什么够好

* **对"读用户自己的代码并回答问题"：够。** 项目代码干净；系统头 72%；答不了的地方有 `Unknown` 与
  `DeclFact::clean` 兜着。**但 `clean` 现在没有任何消费者**（§3.4）——也就是说"这条事实读得不干净"
  这件事，语义层看见了却没用上。
* **对"宏处理"：不够，而且不是缺宏机制。** 缺的是三件具体的事：
  1. **定义最常用宏的那些文件读得最差**（`winnt.h` 一族）。这一族直接决定"宏的引用/重命名"能不能从
     "可能"变成"使用"——同一轮里，**能干净解析的文件给出了 333 个定得住的宏名、2 626 条使用**，
     而 `winnt.h` 上的四个宏一条都没有。
  2. **条件结构是从 parse 派生的**（`scan_directives` 只认语法树里的 `PreprocessorDirective` 节点，
     这是刻意的：哪些 `#` 是指令已由 parser 决定）。所以任何"跟条件有关"的宏能力（宏环境、分支结论、
     `#if` 里的定义）都被 parser 的错**间接**挡住。
  3. **恢复的正确性**：宏工作会把树乘以事实。一棵错的树 × 一次展开 = 一个**没有诊断的错答案**，
     而这一层没有别的防线。

## 5. 建议的顺序

1. ~~先修恢复的正确性~~（**第十二轮做完**：第 20 条的症状 + `rollback` 的契约）。
   结论要连着数字一起看——见下面的 §6。
2. ~~再修"宏密集文件"那一族~~（**第十三轮做完三个构造**：B44 链接块里的指令、B45 多声明符 `typedef`、
   B46 类头里的宏）。`winnt.h` 从 417 条错 / 936 条丢失指令变成 **15 条错 / 0 条丢失**，闭包 328 → 335 个干净文件，
   **分支结论第一次在它身上生效**。判据用的是同一批宏的引用数（`examples/find_references.rs`）：
   定得住的宏名 333 → 577，使用 2626 → 4602 条。
3. **下一步是宏环境（P3），而且它现在有了精确的价码**：`winnt.h` 一族剩下的"全部是可能"只剩一个成因——
   `#ifndef NT_INCLUDED / #include <winnt.h> / #endif`，而 `NT_INCLUDED` 在整个 MinGW 头里没有任何 `#define`。
   按形状接受它不行（一个合法的条件包含长得一模一样），所以要判定它就需要宏环境。
4. **宏展开（P4）排在 P3 之后**：展开会把更多宏形状喂进 parser，而恢复的错会被展开放大。

## 6. 第十二轮（恢复）之后的复测：**两个语料一个数字都没动**

```text
                修之前            修之后
128 文件闭包    干净 80 / 报错 48   干净 80 / 报错 48   消息 932 → 932
455 文件闭包    干净 328 / 报错 127 干净 328 / 报错 127 消息 3383 → 3383
```

这不是"修了没用"，而是**这两条缺口的位置本来就不在语料里**：系统头里没有半写完的 `w.`，
也没有任何输入在回退之前报过诊断。它们的收益在**光标**上（`w.` 是补全被问到的那个状态）与**契约**上
（一个被丢掉的读法不该留下抱怨），而判据因此只能是形状断言与直接驱动 parser 的单测——这正是第 29 条
"两个数字一起看"的第二个数字，也是这份评估 §3 第 5 条说的那件事的具体例子。

**顺手量出来的两个真缺口**（B42 函数定义里的 `try`、B43 条件里的声明）**才是会动数字的那一类**：
它们是"53 段合法 C++ 过一遍 parser"这条做法找出来的，已进 `grammar-gaps.md` 与 roadmap §2 的队列。

**一句话**：parser 的语法层对这个项目已经够用，**够不够好取决于"它读得最差的那批文件是不是宏住的那批"——
实测答案是"是"**。所以宏处理的第一步不是宏机制，是把宏住的那几个文件读对。

## 7. 方向鉴定：这套架构赌的是什么，以及它有没有赌对

（第十四轮之后写的。起因是一个很自然的期待：**"基础的 parser + 预处理器应该已经能正确分析了"**。
这一节说的是那句话为什么对 C++ 不成立，以及这套设计真正押的三个注。）

### 7.1 "parser + 预处理器"在 C++ 里不是一个可以分开的两层

预处理器不是我们"跳过的一遍"，而是**它的输出不是文件**：

```text
宏会改变语法        开出 namespace / 顶替一个说明符 / 自带 `;` 或 `{`     ← 11 轮 parser 工作在付这个
宏的身份依赖于谁先被包含   翻译顺序，而不是文件内容                     ← macro_definition 在付这个
条件分支的取舍依赖于环境   486 / 1246 个 include 写在 `#if` 里          ← 这一轮量出来的
```

本仓库自己的数字把这三条钉死了：宽语料里 **52% 的"第一个错"落在某个宏所在的行上**，而那个宏定义在**别的文件**；
最常用的宏（`STDMETHODCALLTYPE`、`WINAPI`…）定义在 `#ifndef` 里；`winnt.h` 的 417 条错里有 936 条丢失指令，
**丢的根本不是声明，是指令**——而条件结构是宏层唯一的输入。

所以"先解析文件、再分析这棵树"这件事，在 C++ 里**不是一个正确的模型**：一个文件的树不等于它在任何一次编译里的
样子。编辑器又不能只保留一个分支（用户在哪个平台上都在写代码），于是只剩两条路：

* **展开**（真的做一个预处理器）——换掉无损、换掉增量、换掉"半写完的文件也能用"；
* **把条件结构当一等数据留着**，等有人问的时候再判定。

这套仓库选的是第二条，而且已经在付它的账：每个条件性答案今天是 `Unknown`，**这不是能靠"把 parser 写好一点"
消掉的**，是模型本身的形状。

### 7.2 三个赌注，各自的证据与代价

| 赌注 | 证据（都能量） | 代价（也在付） |
|---|---|---|
| **无损 + 容错的树**，不做完整解析才交付 | 不变量测试零例外；敌对语料 74% 干净；任何输入都有树与事实、没有 panic | 宏形状的读法要一条一条补（11 轮），而每条只值 1–3 个文件 |
| **按文件存事实、查询时做连接**，不物化翻译单元 | `std_query` 9/9；`basic_string` 442 个成员；引用 4602 条使用；补全 488 个名字 3.3 ms；热启动第一个答案 26 ms | 每次查询要走图（573 → 3.2 ms 那一次就是这账）；有些问题**根本答不了**（模板实例化、算术表达式的类型） |
| **惰性索引**（问到才读） | 第一个答案 32 个文件 vs 整个闭包 459 个 | "还没读到"和"不存在"要上层分开（`pending()` 那条规则） |

三个都是**为编辑器**做的选择，编译器会做相反的选择——这一点 `index-design.md` 写在第 1 节，数字也一直站在它那边。

### 7.3 条件没有值（**已解决**）；现在真正的瓶颈回到了语法

第十四轮量了它的形态（`examples/condition_reach.rs`，459 文件闭包）：

```text
1246 个 include 里 486 个写在 `#if` 里（39%）            ← 路径条件性全部来自这里
  249  ifdef / ifndef NAME（254 次名字测试 / 79 个名字）
        97 次：闭包自己定义过        → 可判定
        26 次：编译器预定义（`_WIN32`…）→ **问一次编译器就有**（`-dM -E`，483 个）
       131 次：哪里都没有定义        → 只有"闭世界"才敢答"没定义"
  149  版本测试（`#if __cplusplus >= 201703L`）            → 工具链连**值**一起给
   47  `__has_include(…)`                                  → 这是**文件**问题，resolver 就能答
   30  `defined(NAME)` / `!defined(NAME)` / 含数字的表达式  → `condition::evaluate` 已经写好了
```

**结论：这个语料里每一种形状都是可判定的**，输入是（闭包事实 + 编译器自己的宏表 + 配置）。**不需要把宏环境
放进缓存键**——原来的 P3 之所以贵，是因为它假设要重算每个文件的摘要；而这里要做的是**在查询时判定**，
用的是索引里已经有的东西，加一次 `-dM`。

**第十五、十六轮做完了它**（做法与实测见 [`index-design.md`](index-design.md) 的"条件求值"各节与
[`std-library.md`](std-library.md) 第十五轮）：摘要存**问题**（分支链、正文范围、嵌套、文件自己的守卫），查询时用
（编译器预定义 483 个 + 编译数据库的 `-D`/`-U` + walk 按翻译顺序喂进来的闭包定义，含单整数字面量的**值**）求值，
得到 `Active`/`Inactive`/`Unknown`。459 文件的闭包里 **486 个条件 include 里 188 个被判定**（127 取到、61 跳过、
298 未知），而"我不知道"现在是一个**独立于"没定义"的答案**（`Lookup::Unanswered`）——这正是下面那条风险要求的
形状：判据不是"默认没定义"，而是"这张表说不出就不算数"。

**第十六轮还量到一条边界，值得记住**：把环境声明成"这就是这次编译的全部定义"（读到编译数据库时才敢这么说）之后，
同一个闭包是 **440/486**；但 walk"一个文件只走一次"会让**先被条件路径包含、后被无条件包含**的文件丢掉确定路径
（`minwindef.h:2594` 的 `#include <winnt.h>` 条件未知，`windef.h:366` 的同一条确定取到，第二次被 `visited` 挡掉），
于是 `__attribute__` 767 条、`STDMETHODCALLTYPE` 4 078 条从"可能"变成"不是引用"。**所以那个声明没有打开**：把诚实
的疑问换成错答案是这一层唯一不能做的事，修法与"一次查询走一遍图"那一节同一类——"更好的答案赢"。

**留下的风险要说清楚**：闭世界判定会把今天的 `Unknown` 换成**可能错的答案**——一个没人告诉我们的 `-D`，
或者索引外的一个头文件，都会让"哪里都没定义"变成假话。所以判据是"**输入齐了才判，缺一样就是 `Unknown` 并带上
原因**"，而不是"默认没定义"。这与 `resolution_still_holds`、`IncludeFact.resolved` 是同一条纪律。今天判定的 188 个
全部来自"闭包确实定义了它"或"编译器确实预定义了它"这类不会缺席的正面输入。

### 7.4 所以：方向合理，但要按这个顺序

**排序在这一轮被一次测量改了**（`examples/macro_shape.rs`，两个语料）：把失败文件的**首错行**按"行上有没有宏、
那个宏的形态索引知不知道"分类，并且真的把闭包的全部宏形态做成一张表喂给 parser 重解析：

```text
128 个文件的闭包（编译器真正读的）     455 个文件的闭包（分析闭包）
  首错 48：行上无宏 38 (79%)            首错 120：行上无宏 76 (63%)
          形态已知   2 ( 4%)                    形态已知   1 ( 1%)
          形态Unknown 8 (17%)                   形态Unknown 43 (36%)
  喂表：干净 80 → 43，消息 941 → 1081    喂表：干净 335 → 290，消息 2551 → 4928
        **变干净 0，变脏 37**                 **变干净 1，变脏 46**
```

（这张表是在**第十六轮结束时**的状态上量的：128 那份首错 48、455 那份 120。第十七轮按它排的队做了六个语法构造
（B47–B52），第十八轮又接着做了十六条（B53–B68），两份清单的首错因此降到 28 / 55——逐批的干净/报错/消息三个数
在 `roadmap.md` §2.0 与 `std-library.md` 里，是把每一批反向应用回工作树实测出来的。）

两件事因此确定下来：**（一）"给 parser 一张（无位置）宏表"不做**——它把"某个头文件里的宏"当成"这里也是宏"的
证据，`_GLIBCXX_BEGIN_NAMESPACE_VERSION` 这种"就是 namespace 开头"的宏被读错，`} // namespace std` 处崩塌；
**（二）剩下的份额大多不在宏上**（79% / 63% 的首错行上一个宏都没有），所以下一步是语法长尾，展开是**有界**的第二
件事（17% / 36%，且只对"形态 Unknown 的函数式宏当语句/声明片段"那一族，并且必须**按位置**做）。

1. ~~**条件求值**~~（**两半都已完成**，见上）：编译器宏表（`-dM -E`，一次进程，和 `discover` 同一处）→
   区域的条件存进摘要（**是文件自己的文字，过"事实"那条判据**，`CODEC_VERSION` 11）→ 查询时判定
   （`parse_condition` + `evaluate` 已经在了）→ walk 按翻译顺序把闭包自己的 `#define`（含值）喂进环境。
   **实测**：486 个条件 include 里 188 个被判定（第十五轮结束时 85）。那 4 000 多条引用**仍然**没有整体变成"使用"
   ——它们卡在 `#ifndef NT_INCLUDED` 上，而"哪儿都没定义"这个结论需要**声明输入完整**，那一步量清了（440/486）
   却故意没打开（见上）。
   **预期错在哪儿值得记住**：第十四轮以为这 189 个条件"大多依赖闭包自己的定义所以可判定"，实际能判定的是 127 个，
   而且它们能被判定**不是因为**闭包的定义被喂了进来，而是因为文件自己的守卫不算条件 + 正面证据。
2. **语法长尾**（§2 的队列）：份额在这里。第十七、十八两轮走了十六条
   （455 那份 120 → **55** 个失败文件，128 那份 48 → **28**），其中收益最大的一条不是读法而是**恢复**
   （B58：一个坏成员不再带走整个类/块/链接块，455 那份的消息一次少了 1570 条）。**方言**（B61）与
   **"花括号体定形参表"**（B62）是紧接着的两条：一条补地基（哪个编译器），一条补一条早就该有的证据。
   下一步回到首错清单：`::new (…) T(args)`、空的第二操作数段 `__asm__ (… ::)`、`_Float16` 的字面量后缀
   （`0.0f16`）、`{ .__v = __A }` 这种指定初始化式、把运算符当宏实参的调用（§2.0 末尾按首错文件数排着）。
3. **让确定路径改写带疑的 `visited`**（§3.5c），然后才谈"输入完整"；随后是 `__has_include`（47 处，`resolver` 能答）。
4. **有界的展开**：只对形态 Unknown 的函数式宏当构造用那一族，按位置做（"这次调用展开成什么"），不是表。
5. **LSP 二进制**：最后。它是协议活，不挡任何语义（客户端通知我们）。

**一句话**：我们赌的是"**不物化翻译单元也能回答大多数问题**"，而到目前为止这个赌注的收益是能数的
（9/9、442、4602、26 ms）。曾经唯一没买的那样——**条件没有值**——两半都买了；而这一轮又把"要不要给 parser 喂一张
宏表"这件一直悬着的事**量死了**，顺手证明剩下的份额主要在语法上。**没有在做大量的 workaround**：绕开的那部分
（读法偏好）有测试钉住、有代价记录，而架构上的每一次"先量再建"都改变过结论——这一次也一样。
