# 索引与语义层的设计（规范）

本文档记录**已经拍板的决策**与**不变量**。它约束 `cpp_code_analysis` 之后的所有工作：写代码时如果与这里冲突，先改这里并说明理由。

## 已定的三件事

| 决策 | 内容 |
|---|---|
| 缓存位置 | **项目内 `.cppls/`**（以后做成可配置项；默认放项目内，便于调试、CI、以及"和仓库一起删"） |
| 索引粒度 | **按文件**（per-file summary），不是按目录、不是按编译单元 |
| 目标范围 | **做完整的语言服务器**：语义推断（名字解析、类型、重载、模板、ADL）最终都要做 |

## 架构分层

```text
cpp_parser      语法：无损 CST、指令节点、宏表（#define 名字）、外部符号表接口
cpp_code_analysis
  preprocess    展开与条件：直接量/宏、guard 三态、Origin、预算
  summary       每文件事实：声明、宏、include、guard、模块   ← 落盘的单位
  resolve       按需查询：名字 → 声明（over include 图与 guard）
  infer         语义推断：类型、重载、模板实例化、ADL        ← 全部在查询时做
```

实际落地的模块名（`summary` 拆成了三层，因为三件事的输入不同）：

| 模块 | 职责 |
|---|---|
| `summary` | **只在数据形状**：`FileSummary` / `DeclFact` / `MacroFact` / `IncludeFact` / `FactGuard` |
| `sema::declarations` | **生产者**：从 scope 树 + 预处理状态 + 语法树产出 `DeclFact`（唯一同时看得到三者）；`declared_type_of`/`declared_bases_of` 同时供查询层直接用，避免两份实现 |
| `index` | **粘合**：`FileIndexer` 把 parse → preprocess → scopes → facts 汇成 `FileSummary`；`write_summary`/`read_summary` 落盘 |
| `summary_codec` | **字节格式**：手写编解码，magic + `CODEC_VERSION` |
| `sema::resolve` | **查询**：不生产数据、只回答问题——游标处的名字 → 声明、限定名 → 作用域、成员访问的形状（单文件） |
| `index::project` | **跨文件查询**：`ProjectIndex` 装摘要 + 派生反向边 + 可见性走查；入口是 `definition_across_files`（名字，含限定名）、`macro_across_files`（宏，位置化）、`member_across_files`（成员，含类型推断） |
| `index::store` | **驱动**：`SummaryStore` 决定"什么时候建、什么时候复用、变了以后哪些要重建"——唯一碰文件系统的索引层 |
| `index::worklist` | **顺序**：`Worklist` 决定"先索引哪个文件"——打开的文件 → 它的 include 闭包 → 其余；一步一个文件，调用方决定节奏 |
| `index::watch` | **监听**：`ChangeBatch` + `WatchFilter` 把文件系统事件归约成"忘掉谁、重读谁、还是全量重来"；不含 OS 绑定、线程、时钟 |
| `cache` | 键与路径 |

## 查询：从单文件到跨文件

单文件那一层（`sema::resolve::definition_at`）问的是"这个名字在本文件里指向哪条声明"，做不到时返回 `Unknown(NotDeclaredHere(名字))`——**那个原因就是跨文件层的入口**：它说的是"名字在别的文件里"，而不是"这个名字不存在"。

`index::project::definition_across_files` 把两层按 C++ 的解析顺序组合起来，**顺序就是正确性**：

```text
1. 本文件的作用域      —— 局部遮蔽头文件里的声明，永远
2. 本文件自己的顶层声明 —— 写在这里的声明不是头文件那条
3. 它 include 的头文件  —— 沿 include 图可达的那些
```

只有 `NotDeclaredHere` 会走到第 3 步；`Ambiguous` **不会**——那说的是"名字就在这里，而且不止一条"，去头文件里找是回答另一个问题。

跨文件查表要过三道判据：

1. **可见性**：声明所在文件必须从查询文件出发**沿 include 图可达**。项目里有 `Widget` 不等于这个文件能看见 `Widget`。
2. **限定名优先**：`a::Widget` 先按限定名匹配，再退到裸名——限定拼写是一个强得多的主张，不该被项目里任何一个 `Widget` 稀释。
3. **条件性**：路径上只要有一步 `#include` 落在 `#if` 里，答案就是 `Unknown(ConditionalCompilation)`，因为走没走那条分支取决于索引没有的宏。有条件路径与无条件路径同时存在时，无条件的那条获胜（它永远在）。

**反向边是派生的，不落盘**：摘要里存的是每个文件**自己写的** `#include`（直接边），"哪些文件包含这个头"是图的属性而不是任何文件的属性，所以它从摘要现算，内存里存。写进磁盘就等于存了一个结论：它没有哪个文件可以跟着一起失效，而它和摘要第一次不一致时是看不出来的。

**`MacroEnvironment` 被删掉了**（曾是 `cache.rs` 里的一个类型 + 键里的 `macro_env_hash`）。它算的是"沿 include 链累积的、定义过宏的文件的 content_hash 集合"，用来让"某个头文件改了宏"这件事传播到它下面每个文件的键上。删它的理由是**它算出来的东西对摘要的内容没有影响，却是唯一一个必须走一遍图才能算的键成分**——于是 `get` 不得不在查盘之前先解析，磁盘缓存因此只省了"写"，从来没省下"解析"。证据是三件关于生产者的事实：`build_scopes` 只吃语法树；`build_facts` 用预处理状态只为**找指令位置**（每条事实记下自己所在的 `#if`，让消费者去判断，这正是 guard 存而不用的原因）；`#include 宏名` 永远解析不出来。详见 `cache.rs` 的模块文档与下面"第三个被测试抓出来的键错误"。**如果哪天摘要开始依赖宏**（在声明里做展开、或者把 `#if` 的未取分支剪掉），环境必须回到键里，并且同一次改动里必须抬 `FORMAT_VERSION`——否则盘上已有的摘要不是"取不到"而是"悄悄错了"。

### 单文件那一半

`sema::resolve::definition_at(scopes, root, offset) -> Known<Binding>`。它问的是"游标下这个名字在本文件里指向哪条声明"，**只看作用域链**：

```text
做：   作用域链（含 `using namespace` 带来的命名空间）
       限定名：`ns::C::f` 里的限定部分当作**作用域**去找，再在这个作用域里查最后一段
不做： 基类、ADL、重载选择、`using Base::m`、任何跨文件的东西
```

不做的那些**不是遗漏，是下一层**——但消费者必须能区分"没找到"和"没找过"，所以答案一律是 `Known`：`Yes(声明)` / `No`（本文件可达作用域里确定没有）/ `Unknown(原因)`。为跨文件这一条新增了 `UnknownReason::NotDeclaredHere(名字)`：名字在别的文件里，这是关于**本文件**的事实，而不是"这个名字不存在"。

### 限定名：限定部分是作用域，不是名字的一部分

`ns::Widget` **不是**一个要去作用域里找的名字，它是"**先找到一个作用域，再在里面找一个名字**"——两件不同的事，答案也不同。把限定部分丢掉、直接找 `Widget`，得到的不是"小一号的正确答案"而是**错答案**：`a::Widget` 和 `b::Widget` 都是"作用域里有个 `Widget`"，只有一个是游标指着的那条。测试里专门有一对文件同时声明 `a::Widget` 和 `b::Widget`，断言 `b::Widget` 跳到 `b`——丢掉限定部分时它会跳到声明顺序靠前的 `a`。

三件事因此被定下来：

- **游标处的限定名要拼出来**（`qualified_name_at`）：沿着名字节点的 token 走到游标所在的那个标识符为止，所以游标停在 `a::b::c` 的 `b` 上问的是 `a::b`——用户指着限定部分时，问的就是限定部分。模板参数列表不算名字的一部分（`ns::Widget<int>` 上的游标问 `ns::Widget`）。
- **前导 `::` 是拼写的一部分**，不是装饰：`::Widget` 问的是全局名字空间，所以只有写在文件作用域的那条能应答。匹配时**保留**这个前缀（`DeclFact.scope.is_none()`）而不是剥掉——剥掉就会把 `ns::Widget` 也算进来，正是这个拼写存在的意义所在。
- **相对限定名从外围作用域锚定**：写在 `namespace a` 里的 `b::count` 指的是 `a::b::count`，所以限定名会**从内到外逐个外围作用域**试一遍。这里与语言有一处刻意的差异并写在函数文档里：C++ 只把**第一段**按外围顺序找一次、之后一路向下不再回头，而这里是每个外围作用域试整个限定名——可能找到语言不会找的那条，但不会漏掉语言会找的那条。

本文件里找不到时，`NotDeclaredHere` 带的是**限定拼写**（`nope::count`），这正是跨文件层能接住它的原因：一条声明事实记着它所在作用域的限定拼写，所以"限定名"是索引能回答的问题（`declaration` 早就先按限定名匹配、再退到裸名）。

**顺带得到的一件事**：类外定义的 `int C::value() const { … }` 会解析回类里那条声明 `int value() const;`——那是 C++ 里最常见的"头文件/实现文件成对"的跳转，它现在就通了。

**排序是答案的一部分**：栈的最后一个是最近的作用域，所以"哪个声明赢"完全由 `scopes_to_search` 的顺序决定。第一版把链先压栈、外围作用域压在上面，结果**最外层每次获胜**——局部遮蔽被跳过了。抓它的是遮蔽测试，别的测试都抓不到。

**一处已知的过度近似**：`using namespace` 的目标按"文件里所有指令命名的命名空间"取，而不是"游标可见的那些"。代价是文件里有两个指向不同命名空间的指令时可能跳错一次；反向收紧的代价是把一个明明可见的名字报成未声明。已写在函数文档里。

## 三条不变量（比功能清单重要）

1. **索引存事实，不存结论。**
   summary 里只有"这个文件写了什么声明/宏/包含"，**任何已解析、已推导、已实例化的结果都不落盘**。理由是可增量性：一个 `#define` 变化会改变依赖它的每个文件里每个名字的含义，一旦把结论写进缓存，一次改动就要全库重算；而事实的失效范围是**可计算的**（反向 include 边 + guard 剪枝）。
2. **`Unknown` 是一等公民，且在完整系统里也保留。**
   文件没索引、正在编辑、解析有错、名字依赖模板参数、展开超预算、`#if` 无法判定——这些都返回 `Known::Unknown(reason)`，而不是猜一个答案。语言服务器的价值在于"**知道自己在哪些地方不知道**"，`UnknownReason` 已经把这套词汇建好了（`DependentName` 等）。
3. **parser 宽容，语义层必须验证来源。**
   parser 是容错的（解析出错也留下无损的树）。语义层只能相信**干净解析**的文件里的声明；有错的文件其声明标记为"部分已知"，参与解析但可以被查询方降权。这是"全都要做"的代价：越往上做精确推断，越要清楚手上这份事实有多可信。

## 事实的形状：两个不得不再三确认的决定

**限定名要存限定路径，不能只存名字。** 一条 `DeclFact` 带 `name` 加 `scope`（声明所在作用域的**限定拼写**，如 `ns::C`）。

- 没有它，`ns::C::f` 查不到：名字本身不标识一条声明——两个文件可以各声明一个 `Widget`，一个文件可以在文件作用域和类里各有一个 `f`。
- 存**拼写**而不是 id，因为 id 是运行期 interner 的下标、重启即失效；拼写还能被 symbol 搜索直接显示。
- 派生它的前提是 `Scope` **记录自己引入的名字**（`Scope::name`），并且 `namespace a::b` 与 `namespace a { namespace b {` 必须产出同一条限定名——两处都有测试钉住。

**`include` 与 `path` 存路径，不存 `FileId`。** 同一个理由，而且更硬：`FileId` 写进磁盘之后，下一次运行读回来的含义是另一回事。反向 include 图因此是**从事实在内存里重建**的，不落盘——那正是"存事实不存结论"的直接推论。

**后来加的两个字段遵守同一条规则**：`DeclFact.type_of`（变量被写成的类型）与 `DeclFact.bases`（类的基类清单）都存**拼写**，不存解析结果——`ns::Widget`、`std::vector<int>`、`public B` 原样存，消费者用既有的限定名机制去解析，解析不到就是 `Unknown`。判断一个字段该不该进事实，问的是同一句话：**头文件改了之后它会失效吗？** 会失效的（解析后的类型、`FileId`、实例化结果）就不是事实。两个字段的边界也写在字段文档里：`type_of` 只对变量/字段/参数（类*是*类型、函数*返回*类型，那是语法的另一个部位），`bases` 不含访问修饰符和 `virtual`（它们决定成员能不能**到达**，属于语义而不是文本事实）。

**第三个字段问题的答案是"不落盘"**：`DeclFact.bases` 只存 `D` 写下的基类拼写，**绝不把继承来的成员写进 `D` 的摘要**。基类链在查询时走（`index::project::members_of`）。物化（把 `B` 的成员摊到 `D` 上）看起来只是省一次查询，实际会制造一类**没有任何东西能发现**的陈旧答案：

```text
1. B 增删成员              —— D 的文字和键都没变，落盘的成员表已经错了
2. D 的基类清单变了        —— 这条能抓到，因为 D 的文字变了
3. 名字 `B` 指的是哪个 `B`  —— D 的文字没变，宏 / include / #undef 一改就换了目标
```

第 3 条是决定性的：`D` 的文字与键都原封不动，任何"按文件失效"的规则都看不见它。测试 `a_member_added_to_a_base_appears_without_reindexing_the_derived_class` 把这条论证变成了断言——它只重建 `b.h`，然后要求 `A` 的成员列表跟着变，并顺手断言 `A` 自己的摘要里**没有** `B` 的成员。

**推论**：事实里没有的东西，查询时就得能算出来。所以"能不能物化"这个问题等价于"查询时能不能走回去"，而走不回去的那种（这一条）恰恰也是最不能存的。

**一处与不变量 1 有张力的地方，摆明在这里**：`IncludeFact.resolved`（`#include "widget.h"` → `/p/widget.h`）**确实是**项目层面的结论，不只是文字的事实——它取决于文件所在目录、include 路径，以及那个文件**到底在不在**。之所以还是存下来，是因为可见性走查（`index::project` 的 `visibility_of` / `includers_of`）只拿得到摘要，而它每问一次名字就要走一遍图；把解析推迟到查询时意味着把 resolver、provider、配置全都搬进 `ProjectIndex`，图的形状会在每次查询里重算。

存它的代价被三件事兜住了：（a）目录和配置进了键（见上）；（b）**解析不到的 include 让摘要不落盘**（见下），所以磁盘上任何一份摘要里的 `resolved` 都是当时真实解析出来的；（c）**盘上的摘要在被相信之前要重新核对一遍**——`SummaryStore::get` 命中时逐条重解析它的 include，任何一条解析结果不同就把整份摘要当成未命中。`resolved` 是关于文件系统的主张，而键必须能从文字算出来，所以"哪些候选路径存在"永远进不了键；那就不能盲信，核对让它从"结论"退回"候选"，代价是命中时每个 include 几次 `exists` 而不是一次解析（实测见下）。

这一条顺带定下监听层的地位：**它是及时性，不是正确性**。遗漏事件只会让答案晚一点变、不会让它错——因为任何一份旧摘要在被用之前都会自己撞上核对。监听层买的是"事件一发生答案就变"，而不是"因为监听了所以对"。

想做干净的那一天，走法是把 `resolved` 从摘要里拿掉、改成查询时解析，那是 schema 变更，值得单独一轮；在那之前 (c) 就是它的替代品。

## 缓存与失效

- 目录：`<project>/.cppls/summaries/<hash 前两位>/<key>.bin`（一文件一摘要，**不要一个大 blob**）。`.cppls/` 已在 `.gitignore` 里——它随 checkout 走是刻意的（CI 拿到同样的热缓存），但派生数据永不入提交。
- 键：**`content_hash + context_hash + format_version`**。三个成分都是**能从文字和路径直接算出来的**——这不是巧合，是要求：只要键需要"先解析才知道"的东西，查盘就必须排在解析之后，缓存也就永远省不下解析。
- `context_hash` = 编译配置（include 路径按 `working_directory` 解析后、`-D`/`-U`、标准、目标）**加上文件自己所在的目录**。配置和目录是同一个问题而不是两个：`#include "widget.h"` 的意思是"**我旁边那个**"，所以同一段文字放在两个目录里是两份不同的编译、会解析到两个不同的文件。
- `format_version` 含 parser 版本号：parser 一升，整库作废。字节格式另有一个 `CODEC_VERSION`（写在文件头里），两者变化的原因不同：加字段两个都动，调整一条记录的字段顺序只动后者。**删掉键里的一个成分只需要动 `CODEC_VERSION`**：旧条目只是取不到（键的名字变了），永远不会被当成新键的答案，因为读回来的键要和刚算出来的键逐字段相等才算命中。
- 写盘是 `.tmp` + rename：崩溃留下的是旧摘要，而不是半份新的——**半份摘要是活的错答案，比没有更糟**。
- 读盘失败（缺失、损坏、版本不符）一律是"重建"的指令，绝不留一个字段取默认值的半份摘要。解码器对截断、超长计数、越界枚举值逐个报错，并且**拒绝尾随字节**。
- 命中不是"读出来就用"：**每一条 `resolved` 都要重新解析一遍**，任何一条不同就当未命中重建（理由见上）。所以命中一次的代价是"读一次文件（算哈希）+ 读一次摘要 + 每个 include 几次 `exists`"，而不是零。
- 启动：只 `stat`，命中即复用；mtime 变了算内容哈希，**哈希命中旧摘要直接复用**（分支切换因此从"全量重解析"变成"只读盘"）。内容真变了才重建，并沿**反向 include 边**做工作集失效。
- 批量变更（切分支/merge/格式化）：两段式——**打开的文件 → 它的 include 闭包 → 其余**，由 `index::worklist` 实现（一步一个文件，调用方决定节奏）；UI 不阻塞，未索引的文件查询返回 Unknown 而不是等。
- 监听：**不接 OS 监听器**。语言服务器由**客户端**通知（LSP 的 `didOpen`/`didChange`/`didSave`/`didClose`/`workspace/didRenameFiles` 本身就是事件源），所以不需要 `notify`、不需要去抖时钟、不需要文件系统轮询。客户端来一批事件就构造一个 `ChangeBatch`、调一次 `respond`，然后按返回的路径跑 `Worklist`——这就是服务器的接入点。过滤与合并规则（`.git/`、缓存目录、构建目录、`compile_commands.json`、`删+建` 的合并）仍然有用，因为客户端也可能报出无关路径。重命名按内容哈希复用（同目录同文字 ⇒ 同键，一次解析都不用重来），但**监听层不负责把新路径加进索引**——那是文件清单和 include 图的活。

### 驱动层：`SummaryStore` 的四条规则

`index::store` 做四件事：`get(path)`（现在是文件**当前**该有的摘要）、`index_includes_from(entry, budget)`
（**一个文件及其闭包**——顺着摘要里的 `resolved` 边走边问缓存，返回 `IncludeIndex`）、`invalidate(path)`
（改了以后的工作集）、`stats()`（命中率）。它不监听文件系统、不排调度、不碰线程——和 `FileIndexer` 对解析
的态度一样。

**闭包那一条是"打开一个项目"的入口**，也是 P0 的搜索路径发现第一次真正兑现的地方：`#include <vector>`
解析得出来之后，这一个调用就会把 185 个标准头索引进缓存。实测本机一个含 `<vector>`/`<string>` 的
`main.cpp`：冷 309 个文件 3.6 s，热 307 个命中 262 ms、盘上 1.5 MB。它**不是一个新层**：闭包的结构不需要
重新解析，因为摘要里已经记着每条 include 解析到了哪个路径，所以循环就是"问 store 要一个文件 → 从答案里
读它包含谁 → 再来"。预算（文件数 + 深度）两条，且**截断要报告**（`not_indexed` 带原因），因为"没有更多了"
和"可能还有"是两句话。

**规则一：先查盘，后建。** 顺序是：读文字 → 算键（哈希 + 语境，两者都不需要解析）→ 盘上有就直接用 → 没有才建、落盘。命中时**连 include 都不去找**（有测试用 provider 的探测量钉住这一点）。这条规则是宏环境离开键之后才成立的，见上；它也是"缓存到底省了什么"的答案：省的是解析，不只是写。

**规则二：记录了"没找到某个头文件"的摘要绝不落盘。** 那是一条关于**文件系统**的事实，而键必须能从文字算出来，于是键里没有"哪些候选路径存在"这一项——存下去就会在头文件出现之后继续说"找不到"，没有任何东西会发现。这种摘要照建照返回，只是不写，并计入 `StoreStats::unstored`：理由和不变量 2 是同一条，错的条目比没有的条目糟。注意规则只管**解析失败**，不管"包含的文件还没被索引"——后者是关于索引的事实，不是关于这份文字的事实，而且它自己会好。

**规则三：文件不能读不是错误。** 被删掉的文件、不是文件的路径，`get` 一律返回 `None`：调用方问的是一个不存在的文件，答案是"关于它没什么可说的"。**读得到但解析有错**是另一回事，照建摘要：parser 是容错的，一份带错文件的摘要正是半可用的编辑器要的东西。写盘失败同理（不报错）——只读 checkout 是完全正常的用法，它不该把编辑器变成坏的。

### 顺序层：`Worklist` 的两段与两个队列

`index::worklist` 只回答一个问题：**下一个索引哪个文件**。它是 `step()` 一步一个文件的驱动，不是返回 `Vec<PathBuf>` 的计划——因为**一个还没被索引的文件的 include 是不知道的**：每一步摘要到手，才多知道一层下一轮要做什么。这一步的形状同时决定了它的用法：编辑器每个空闲 tick 走一步，后台线程循环到 `None`，有预算的调用方随时停手（列表保持状态，没走到的文件查询返回 `Unknown` 而不是等）。

**两段，两个队列，不是因为两段代码不一样，而是因为一个队列会错。** 两半做的事完全相同（从种子出发的广度优先，跟着 include 走），只有一个队列看起来更简单，但那样一来"调用方列了一万个项目文件"就把"用户正开着的那个文件的闭包"挤到了最后——而那正是第一段存在的理由。有测试用一个比闭包更长的项目列表钉住这一点。

**第二段也跟 include，因为调用方的清单通常只有翻译单元。** `compile_commands.json` 里只有 `.cpp`，头文件一个都没有；不跟 include 的话，索引里除了"某个打开的文件恰好够得着的头"以外什么头文件都不会有。代价要说明白：**工作列表是它拿到的种子的传递闭包**——一个 include 了 `<vector>` 的根，在有系统 include 路径的机器上会把那些头也拉进来。要收窄就收窄种子（或者停手），这一层不对"哪些目录值得索引"发表意见。

**去重与终止**：按规范化路径建 `seen`，所以菱形包含只走一次、循环包含会终止、`open` 与 `project` 里同时出现的文件**只走一次且落在第一段**（它确实是"用户正看着的文件"，这就是第一段存在的理由）。

**一步的结果不问 store，而是看计数器的位移。** `StoreStats` 是累积的，所以 `StepOutcome` 是"这一步期间计数器往前挪了多少"——正因为如此它才是 `Copy` 且可比较的：store 自己的账就是唯一的一份账，另存一份在 `Worklist` 里就是第二个要同步的东西。`Unstored` 蕴含 `Built`（先建了才发现不该落盘），顺序按这个读。

### 监听层：事件 → 工作

`index::watch` 把一批文件系统事件变成三句话："**忘掉**这些"、"**重读**这些"、"**全量重来**"。它**没有** OS 绑定、没有线程、没有时钟——`notify` 那一类适配器只负责产出事件，而"一批什么时候算结束"是个时钟问题（编辑器一秒写同一个文件好几次，切分支是一阵爆发），两者都是这个模块外面的一层薄壳。加不加 `notify` 这个依赖，这一层不强加给任何人。

**"改了"是最无聊的一个，这正是重点。** 文件文字变了只需要重读它自己，**别的什么都不用**：摘要是"这个文件自己的文字 + 目录 + 配置"的函数（`SummaryKey` 就是这么定的，宏环境离开键也是因为这个），它不依赖被包含者的内容。所以改一个头文件是重读一个文件，不是重读包含它的五十个。（查询的答案会变，但查询走的是内存里那份活的索引，头文件摘要一换，新声明立刻可见。）

反过来说，**只有"出现"和"消失"才会让一份摘要失效而它的文字没变**——因为摘要记着 include **解析到了哪里**，那是关于文件系统的事实：

```text
a.cpp:  #include "generated.h"     ->  resolved: None          （那时还没这个文件）
……      generated.h 被创建          ->  a.cpp 的摘要是错的，而它的文字一个字没改
```

**"出现了"能被精确算出来，不需要存候选列表。** 一个 include 的拼写、它写在哪个目录、以及配置里的 include 路径，三者合起来决定了它试过的每一个候选路径；拼写在摘要里，目录来自文件自己的路径和配置。所以判断的方式是**从每个文件那边**枚举它试过的路径（用 resolver 自己的 `join_normalized` 拼），再拿这批"刚出现的路径"的集合去查——这样一批一千个创建也只是一遍扫描，而不是一千遍。同一套判断还回答另一半：`p` 出现在当前解析结果**更前面**的位置时会接管（`#include "x.h"` 原本解析到 `-I/inc` 里的那份，直到有人在文件旁边建了一个）。排序用的就是 resolver 自己的名次，不是对它的猜测；`#include "..."` 与 `<...>` 的区别也照搬 resolver——尖括号不搜文件自己所在的目录，所以旁边新建的文件不会"修好"它。唯一的近似是 `#include_next`：resolver 从"这个文件当初是在哪找到的"之后开始搜，而那个位置没存，所以这里从头枚举——这只会**多**算几个文件（多一次重建），不会漏。

**过滤里只有两件是正确性，其余都是优化。** 正确性的是**缓存目录**（索引往那里写摘要，不过滤就等于拿自己的写当输入，永远重索引）和 **`compile_commands.json`**（它不是源文件，而是"配置变了"的信号）。`.git/` 和构建目录是优化，而且值得说清楚它优化的是什么：**没有任何文件包含、索引也从没持有过的路径，出什么事都是空操作**，所以真正省下的是那一批事件的大小——一次 `git checkout` 会在 `.git/` 下产生几千个事件。同理**没有扩展名过滤**：`#include <vector>` 根本没有扩展名，一张"C++ 扩展名"白名单会恰好丢掉索引最需要的文件。

**"这个文件配不配有摘要"不是看名字回答的**，所以监听层也回答不了：它只在三种情况下把文件放进工作集——索引已经持有它、有文件解析到了它、或者有文件的 include 正在等它。其余的新文件由**文件清单**（扫描目录 / `compile_commands.json`）和 **include 图**（`Worklist` 会跟着 include 走）带进来。这就是为什么重命名一个 `.cpp` 不会让监听层有任何动静，而它依然免费：同目录同文字就是同一个键，谁去问都是命中。

**合并规则是保守的那个**：一条路径上最后一个事件决定它**在不在**，而这一批里出现过任何一次创建就决定它**可能是新的**。编辑器真实的写法正好落在这两条上：`删+建`（写临时文件再改名覆盖）→ 文件在，而且可能是新出现的；`建+改` → 同上；`建+删`（临时文件来了又走）→ 不在。至于**一批什么时候结束**，那是调用方的时钟。

**一批过大就不值得一条一条问了**：切分支会来几千个事件，超过阈值（256）时"向项目要文件清单、跑一遍 `Worklist`"更便宜，而且并不更差——没变的文件都是命中。配置变更走同一条路：配置进了每一份摘要的键，所以一个 `-I` 就能让全项目的键一起移动，此时要的是从文件清单重来，而不是问这一批里的路径。

### 宏查询：翻译顺序就是答案

`macro_across_files(index, root, path, offset)` 回答"游标下的这个名字是哪个宏、在哪里定义"。它是**第一个不需要作用域的语义查询**——宏不是名字查找，而是**翻译顺序**问题：预处理器把整个翻译单元读成一条流（本文件的每一行，每个 `#include` 处原地粘贴整个被包含文件，递归），某一点上生效的宏就是**最后一个走过的** `#define` 或 `#undef`。

所以一条宏事实的位置不是偏移量，而是一条**偏移量链**：把它拉进来的那个 `#include`，再是*那个文件里*的 `#include`……最后是它自己的偏移量。**两条链按字典序比较就是比较它们在流里的先后**——这就是为什么"写在这里"和"写在头文件里"不需要两套规则：

```text
a.cpp:  #define MAX 1        位置 [0]        → 头文件那条更晚，获胜
a.cpp:  #include "x.h"       位置 [10, 4]
a.cpp:  #include "x.h"                        → 本地那条更晚，获胜
a.cpp:  #define MAX 1         位置 [0]
```

`#undef` 因此也是**一条事实**（`MacroKind::Definition | Undefinition`，`CODEC_VERSION` 4），而不是一条注释：链条最后一个如果是 `#undef`，说明这个名字在这里是普通标识符，答案就是 `Unknown(UndefinedHere(名字))`——**不是**指向那个已经失效的 `#define`（那是错答案而不是缺答案），也不是 `Known::No`（索引只看到翻译单元的一部分，`#undef` 之后被包含的头文件仍可能重新定义它）。`UndefinedHere` 是这一轮新加的 `UnknownReason`,因为消费者对它的处理和"没人定义过这个名字"完全不同：前者不该报"未知宏"。

**四个答案**：`Yes(定义)` / `Unknown(UndefinedHere)` / `Unknown(ConditionalCompilation)`（能决定它的每条事实都在 `#if` 里，或者要经过一个在 `#if` 里的 `#include`）/ `Unknown(NotDeclaredHere)`（索引里没有任何文件碰过这个名字——**不是**"这个宏不存在"）。

**优先取无条件的那条**，和声明查询同一条规则、同一个理由：`#define` 在上面、被 `#if` 包住的 `#define` 在下面时，这个名字**确定**是宏，报 `ConditionalCompilation` 等于拒绝回答一个有答案的问题。残留的不确定性写在文档里而不是藏起来：无条件 `#define` **之后**那条被 `#if` 包住的 `#undef`，按"没发生过"处理。

**两处刻意的近似**（都写进了函数文档）：一个文件在一次查询里只展开一次（这保证了 include 环会终止；代价是"同一个头文件被两条路径包含"时，它可能被放在两次位置里较早的那次——但它报告的事实是同一条）；`#undef` 的位置是整条指令的范围，因为指令读取器不记录 `#undef` 的名字范围（跳过去看到的是那一行，够用）。

**没有 `Ambiguous`**：两条不同的链不可能相等，所以"同一个名字有多个定义"这件事在这里不是歧义而是有确定答案的——这正是宏查询比名字查询简单的地方。

### 成员访问：第一个需要**类型**的查询

`index::project::member_across_files` 回答 `widget.size` 里的 `size` 指向哪条声明。它不是"在作用域里找 `size`"——是**在 `widget` 的类型里找 `size`**。三步，每一步都已经存在：

```text
1. 读出形状        —— 对象表达式 + 成员拼写（sema::resolve::member_access_at）
2. 推断对象的类型  —— 它的声明的 type_of，先问本文件，再问索引
3. 在类型里找成员  —— 按限定名 `<类型>::<成员>` 查，索引本来就能匹配限定名
```

**第 3 步是它便宜的原因**：声明事实本来就记着所在作用域的限定拼写，所以"`Widget::size`"是既有查询能回答的问题。新增的只有第 2 步，而这是 `infer` 层的开头，刻意很窄：**对象必须是一个名字**。

为了让第 2 步有可能，声明事实第一次带上了"它声明的是什么类型"（`DeclFact.type_of`，`CODEC_VERSION` 5）。三个限制都是刻意的，写在字段文档里：**存拼写不存解析结果**（`ns::Widget`、`std::vector<int>` 原样存，消费者用既有的限定名机制去解析，解析不了就是 `Unknown`）；**只对变量/字段/参数**（类*是*一个类型、函数*返回*一个类型，那是语法的另一个部位）；**声明修饰符剥掉**（`static const Widget` 记成 `Widget`，而 `unsigned long` 保留——那几个词就是类型）。

类型名字的规范化（`base_type_name`）也在文档里写清了它拿掉了什么：模板实参（`std::vector<int>` → `std::vector`，主模板的成员就是最有用且无需实例化的答案）、尾部的 `*`/`&`、以及 `struct`/`class` 这类 elaborated 关键字。`unsigned long` 不动：那里的词就是类型，而且它不指向任何类。

**四个答案**：`Yes(成员)` / `Unknown(UnknownType)`（对象不是名字、对象找不到、或者类型拼写解析不到东西——**新加的 `UnknownReason`**,因为对这一条的处置和"名字缺失"完全不同：不该报"未知成员"，而是"这个形状的类型还推不出来"）/ `Unknown(NotDeclaredHere)`（类型知道、成员不在里面——仍不是确定否定：可能是基类、模板、或没人索引的头文件）/ `Unknown(UnparsableName)`（游标不在成员访问上）。

**基类成员的查找按层进行**：先看类自己，再看直接基类，再看它们的基类……**第一个有答案的层决定结果**——类自己的成员遮蔽基类的，近的基类遮蔽远的，这就是 C++ 的规则。同一层里有两条就是 `Unknown(Ambiguous)`（菱形继承的两边都声明了这个名字），**报歧义而不是挑一个**：挑一个就是跳到用户分辨不出的另一个实体上。基类拼写来自 `DeclFact.bases`（`class D : public B` → `["B"]`；访问修饰符和 `virtual` 不在里面——它们决定一个成员**能不能到达**，那是语义而不是文本事实，要它们就得要整套语义）。环靠 visited 集合终止：手误的文件写得出环，而挂死比答错更糟。

**类型推断是递归的，因为表达式就是递归的**。核心是 `type_of_expression`，它认识的形状目前有三种：

```text
一个名字      `widget`       → 它的声明的 type_of（先问本文件，再问索引）
`this`        `this->size`   → 包住它的那个类的作用域，不需要任何推断
一个成员访问  `a.b`          → 递归：在 `a` 的类型里找到 `b`，读 `b` 自己的 type_of
```

第三种让 `a.b.size` 通了——内层访问用**同一个查询**定型，外层再问内层"你是什么"。`this` 是其中最便宜的一格：作用域链本来就知道当前是哪个类（嵌套类里取最近的那个，有测试钉住），所以它一格推断都不需要。剩下的一律是 `UnknownType` 并带上表达式拼写：调用 `f().size`、解引用 `(*p).size`、下标、算术表达式——那些需要**算**出一个类型而不是从声明上**读**一个，是另一件大得多的事。

**失败原因会原样传上去，而不是压平成 `UnknownType`**：`a.nope.size` 报的是 `NotDeclaredHere("Outer::nope")`——"`Outer` 里没有 `nope`"直接告诉消费者该改什么，而"`a.nope` 的类型未知"只说了有问题。（这条测试的第一版期望就是压平后的答案：实现比期望更对。）

**已知的窄边界**（都有测试钉住，答案都是 `Unknown` 而不是猜）：`f().size`、`(*p).size`（对象要算类型）；基类成员、模板参数的成员、运算符重载。

**一处结构上的发现值得记**：parser 把 `w.size` 读成 **`IndexExpr`**（和 `arr[0]` 同一种节点，只是括号换成了 `.`），而不是 `MemberExpr`。所以"这是不是成员访问"必须看**运算符**，不能看节点种类——形状读取函数因此按 `.`/`->` 的文本判断，并同时接受三种节点。`a.b` 上的游标在 `a` 上时**不是**成员访问（那问的是 `a` 这个名字，是名字查询的活），这一点由"标识符必须在运算符之后"来判。

### 成员列表：把基类链留到查询时

`index::project::members_of` 是成员访问的**列表形式**：那个问"`size` 在哪条声明"，这个只给一个类型、问"有哪些名字"。补全就是它。**顺序是答案的一部分**：类自己的成员在前，然后一层一层往外——这正是 C++ 遮蔽的顺序；同一层内按**名字**排。之所以要强加顺序而不是沿用它来的样子：本文件的 scope tree 里 binding 是**按名字排**的（`add_binding` 的二分查找要用），而索引里的事实是**按偏移排**的，不统一就会出现"同一个类在缓冲区里和在头文件里列出来不一样"。近层已经贡献过的名字在远层被丢掉——隐藏按**名字**而不是按签名，所以 `D::f(int)` 会遮住 `B::f(double)`。

**歧义不丢条目**：同一层两个基类都声明 `value` 时，两条都在列表里、都带 `ambiguous` 标记。单名字查询在那里报 `Unknown(Ambiguous)`（"跳到哪一条"没有答案），而列表回答的是"有哪些名字"，丢掉任何一条都是替用户选。**重载不算歧义**：算的是**不同的声明类**个数，不是声明条数，所以 `void f(); void f(int);` 是一个名字。

**列表从来不是一个完整性主张**。`MemberList.unlisted` 列出**走不进去的基类**和原因（没人声明的基类是 `NotDeclaredHere`，只经由守卫 `#include` 到达的是 `ConditionalCompilation`）——`unlisted` 为空是说"这一步走到的基类都读到了"，不是"编译器看到的就这些"。一个悄悄少了几项的补全列表就是这个字段存在的理由。为此 `bases_of` 从返回 `Vec` 改成了返回 `Known<Vec>`：**"这个类没有基类"和"这里没人说得出它继承什么"是两句不同的话**，而成员**查找**可以把两者当同一件事（够不到的基类两边都不贡献成员，继续往前走），成员**列表**不能。

**基类拼写要当名字用**：`public Base<int>` 找的是类 `Base`——模板实参说的是继承了哪个**类型**，不是哪些成员归谁声明；不实例化就等于"主模板写着的那些成员"，那也是唯一不需要实例化的答案。这一条顺带补掉了单名字查询里同样的洞：`bases_of` 以前把 `Base<int>` 原样拼进 `Base<int>::size`，谁都匹配不到（模板基类的成员一直查不到，有测试钉住了现在的结果）。

**已知的窄边界**（刻意的，不是漏）：不做访问检查（`private` 基类的成员照样列出来——访问不在事实里，见 `DeclFact.bases`）；不实例化模板；不处理 `using Base::f;` 与虚函数覆盖（前者不算"自己声明了一个成员"，这一层还没有这个模型）；**构造函数与无 `virtual` 的析构函数不在列表里**，因为作用域层根本没绑定它们（`grammar-gaps.md` 第 19 条，那里同时记着这一轮查出来的那个把**类名读成析构函数名**的静默 bug）。

### 补全：把游标接到成员列表上

`index::project::member_completions_at` 是**第三个需要类型的查询**，也是前两个（`member_across_files` 找单个成员、`members_of` 列成员）铺垫出来的那一个。三步全是既有的，所以它很短：

```text
1. 读形状   —— 对象表达式 + 成员已经写了多少（sema::resolve::member_access_at）
2. 推类型   —— type_of_expression，成员**查找**本来就在用的那套递归推断
3. 列成员   —— members_of，含基类声明的那部分
```

**它存在的那个状态是 `w.`**——运算符打完了、后面什么都没有。那一下按键**就是**提问，而 parser 把它读成"成员为空的成员访问"而不是别的构造（`~Widget();` 那种形状问题见 `grammar-gaps.md` 第 19 条），所以这里不需要第二个形状读取器，也不需要重解析这一行。`member_access_at` 因此把"成员还没写"当成一种**真实状态**返回：`member` 为空串，`member_range` 是紧贴运算符之后的一个**空区间**。同一个答案覆盖 `w.si`，区别只是区间盖住了已写的前缀。

**空区间是有意的，不是偷懒**："在一个点插入"和"替换一段前缀"是同一次编辑，用一个字段表达两件事，消费者就不必在"点还是段"上分支——而唯一会分错的那一次，恰好就是点后面那一下按键。同理，`prefix` 与 `member_range` 分工明确：**range 是被替换的（整个 `size`），prefix 是被匹配的（光标之前的部分）**。游标停在词中间时（`w.si|ze`）两者不一样，用同一个值做两件事的写法会在用户明明在打字的时候给出空列表，所以有一条测试专门钉这一格。

**定义查询与补全查询对同一个形状给不同答案**：`member_across_files` 拿到成员为空的访问时返回 `UnparsableName`——"跳转"需要有个东西可跳，而还没有名字可写。宽容放在形状读取器里，判断放在各自的查询里，这样只有一处知道 `w.` 长什么样。

**一个尚未修的上游问题，记在这里因为它影响体验**：`w.` 现在会报一个"expected identifier after member access operator"的错，而错误恢复**吃掉了当前块的 `}`**，于是这个函数之后、文件其余部分被并进了函数体（实测：`void f() { Widget w; w. } int after; void g() { }` 里 `int after;` 变成了局部声明）。补全在**那个游标处**照样工作（对象和运算符都在 `IndexExpr` 里，见上），但同一个文件里后续代码的作用域是错的。这是 parser 的恢复策略问题，不是查询的问题，已记进 `grammar-gaps.md`。

### 三个被测试抓出来的键错误

三个都是**看起来在工作的错答案**，都靠"重启后重新打开应该命中"这一类端到端断言暴露：

1. **占位键被原样存了下来。** `SummaryStore` 当初必须先建摘要才能算环境，于是给 `FileIndexer` 传了一个占位键 `SummaryKey::new(0, 0, 0)`；而 `FileIndexer` 把调用方的键**原样**存进摘要。结果整个项目每份摘要的 `content_hash` 都是 `0`——全项目共用一个缓存条目。缓存**看起来是好的**：一个文件写进去，一个文件读出来，命中率 100%。它回答的是另一个文件。修法是让 `FileIndexer::index_tree` 用**它手里那段文字**覆盖 `content_hash`。**症状的形态值得记住**：`let _ = source;` 这种"参数收下了但没用"就是它的气味。今天这个 bug 已经不可能发生——键在解析之前就算好了，没有占位键可传——但覆盖那一条留着，它是"谁更清楚这段文字"的答案。
2. **目录不在键里。** 摘要里存的不只是"文字说了什么"，还有它的 include **解析到了哪里**；而 `#include "shared.h"` 的解析结果取决于**文件自己的目录**。于是 `a.h` 和 `sub/b.h` 内容相同时共用一个条目，第二个文件拿到第一个文件的解析结果——一个跳到它根本没包含的头文件上的定义跳转。修法是把目录并进 `context_hash`，并把 `config_hash` 改名为 `context_hash`。
3. **宏环境在键里，而它不该在。** 它不是错的答案，而是**不可能命中的缓存**：要在查盘之前算它，就得先解析，于是每一次"命中"都已经付过解析的代价。修法是删掉它（连同 `MacroEnvironment`），键变成两个成分，`get` 变成"先查盘"。这一条被记在这里而不是当作"优化"，因为它推翻的是本文档自己写下的键的定义。

顺带定下的一条：**相对 `-I` 按 `working_directory` 解析后参与哈希**。这样"换个目录跑编译器但 `-I` 一个没变"仍然命中（命中率），"相对 `-I` 在不同工作目录下指向不同目录"则不会共用条目（正确性）。两个方向都有测试。

### 被删掉的东西：`key_for`

`SummaryStore::key_for(path, source)` 曾经回答"这段文字在磁盘上有没有现成摘要"。它**要么不健全、要么没用**，所以删了：

- 它只用**已经持有的**摘要算宏环境，所以当 `source` 与持有的文字不同时，它给出的键**不是 `get` 会给出的那个**——它的文档承诺（"`path` 以 `source` 为内容时会有的键"）根本无法兑现；
- 而当 `source` 与持有的文字相同时，那份摘要**已经在内存里了**，这个键什么也没多说。

能兑现这个承诺的只有 `get`——而且现在它兑现得很便宜：键在解析之前就能算出来，所以"这个文件现在该是什么键、盘上有没有"不再是一个需要单独 API 的问题。

## "全都做"的顺序（以及为什么）

按依赖排，不能跳：

1. **事实层**（summary + include 图 + 反向边）——其他一切的地基；
2. **名字解析**：作用域链、`using`/限定名、跨文件（include 图上的可见性）；
3. **类型与重载**：需要准确的声明集，因此依赖 1、2 的完整性；
4. **模板实例化**：需要前两者 + 精确预处理；这一步开始"出错的文件"会明显影响结果；
5. **ADL**：需要完整可见性模型。

每一层加的是**查询**，不是索引字段——这条与不变量 1 是同一条。每层都必须能降级：下层缺失时上层返回 `Unknown(reason)`，而不是返回一个低置信度的猜测（猜测只在**读法**层允许，那是 parser 的形状偏好，且已经被测试钉住）。

## 索引与 parser 的关系：先不接

`cpp_parser::SymbolTable` 接口已经存在，而且 **`impl SymbolTable for ScopeTree` 已经能跑**——parser 今天就能吃真实语义信息。但跨文件的那一半**故意还没接**，理由是接口的形状：

`kind_of(&str)` 是**无位置**的，而 `#include` 的可见性是**有位置**的：

```text
第 3 行:  g(1, 2);        // 此刻 g 只是个没见过的名字
第 12 行: #include <x.h>  // x.h 里声明了 void g(int, int);
```

把"闭包内所有名字的并集"喂给一张无位置的表，第 3 行的 `g(1,2)` 会被读成**声明**（按 `g` 是类型），而它其实是调用。表仍然只影响读法、不影响结构（`tests/symbols.rs` 钉住了这一点），但**读法是错的**——正是 A0 类问题。

三条路：

- **(a) TU 级并集**：零成本，对绝大多数真实代码正确，在上面那个形状上误读；
- **(b) 位置感知表**（`kind_of_at(name, offset)`）：正确，代价是每次查询一次区间/链查询。`preprocess` 已有同形的 `PositionalMacros`，模式是现成的；
- **(c) 只服务导航，不给 parser 喂跨文件结果**（当前选择）。

**选 (c) 的理由**：本项目最贵的资产是 **parser 读法的稳定性**——`grammar-gaps.md` 1300+ 行、41 个已修条目、14 条维护约定都是围绕"读法可解释、可钉住"积累的。跨文件表一旦接入，同一份源码会因索引状态不同而解析成不同形状，所有形状断言的语境都变了。而导航（跳定义、找引用、符号列表、补全）**根本不需要 parser 知道任何事**——它要的是"名字 → 声明 + 可见性"，是另一种数据结构。

等 (c) 跑出真实的 `Unknown` 比例之后再决定 (a)/(b)：那个数字本来就是用来决定"回头改范围还是继续加功能"的。

## 先量四个数（再铺开）

1. 每文件摘要构建耗时；2. 1 万文件的常驻内存与缓存体积；3. 切分支后的缓存命中率（目标 >90%）；4. **`Unknown` 比例**（若大多数查询以 Unknown 结束，说明该回头改范围而不是加功能）。

第 3 个数现在才**真的**是"命中率"：宏环境在键里的时候，每次"命中"都已经付过解析的代价，`reused` 计的是写盘被省下的次数。今天 `reused` 数的就是被省下的解析次数，`hit_rate()` 的分母是"读过且需要回答的文件数"。

第 1 个数的第一次测量有工具了——`cargo run --release -p cpp_code_analysis --example measure -- [file.cpp] [轮数] [-I 目录]`，它用同一个文件量"建一次"和"命中一次"的比值（每次命中都新开一个 store，因为已经答过的 store 把摘要留在内存里，而重启要付的是查盘）：

| fixture | 构建 | 命中 | 倍数 |
|---|---|---|---|
| 合成单元，581 KB / 24000 条声明 / 2002 个宏 / 1 个 include | 376 ms | 3.4 ms | **111x** |
| 同上但 **100 个 include**（核对的开销就长在这里） | 429 ms | 5.9 ms | **73x** |
| `cpp_parser/tests/real_world.cpp`，3 KB / 31 条声明（另给 `-I` 让它能落盘） | 2.4 ms | 0.28 ms | 8.5x |

小文件那个倍数低是应该的：命中的代价是"读 + 解码一份摘要 + 逐条核对 `resolved`"，前两项跟摘要大小走、第三项跟 include 个数走；构建的代价跟解析工作量走。**100 个 include 让倍数从 111x 掉到 73x**，这就是那道核对的价钱：每个 include 大约 24 µs，也就是一次解析的 0.6%。这个价钱换来的是"监听层可以漏事件"。

顺带一个副产品：这个例子在 fixture 的 include 解析不出来时会**明说"这个文件不会被缓存"并列出没解析到的头文件**，而不是报一个 0% 的命中率——那条规则值得让用的人看见。

## 下一步：宏、标准库、语义索引与语义查询

索引与驱动层的骨架已经能跑（事实层 + 缓存 + 顺序 + 事件响应，905 个测试）。**从这一轮起重心转向语义**：不再在文件系统/进程/监听这些事情上消耗，因为语言服务器由客户端通知，那些事情没有真正的消费者。已经拿下的语义查询：名字（含限定名）、宏（位置化）、成员访问（第一个需要类型的查询）、成员列表、补全（游标 → 类型 → 列表）；环境发现这一层落了工具链搜索路径（[`std-library.md`](std-library.md) 的 P0）。

按依赖排，接下来要做的：

1. **宏（已开始）**：`macro_across_files` 落地之后，同一个位置化模型可以直接长出另外三个查询，都不需要类型系统：
   - **找引用/重命名一个宏**：反过来问"哪些位置的名字解析到这条事实"——需要一个"名字 → 位置"的查询，是 `files_declaring` 的位置化版本；**注意**这条比看起来贵：摘要里没有标识符位置，所以要么逐文件解析（先用文本子串筛一遍再解析），要么在事实里加一份 token 位置表；
   - **`#undef` 的跨文件语义补齐**：现在"`#undef` 在被包含的头文件里、用在别的文件"这一格是靠位置链自然覆盖的，但"文件 A 定义、文件 B 取消、A 再被包含"这种来回还没测过；
   - **宏展开进索引**：`preprocess::expand` 已有预算和 `Origin`，把展开后的声明位置（`BindingOrigin::MacroExpansion` 已经建好了词汇）纳入事实，是"真正的宏"的最后一块——也是最贵的一块（循环、参数、`#`/`##`）。
2. **限定名（已完成）**：`definition_at` 现在把限定部分当作用域解析（本文件内），找不到时把**限定拼写**交给索引，索引按 `DeclFact.qualified_name()` 匹配；前导 `::` 是"全局名字空间"的拼写并被保留。
3. **成员访问与类型推断（`infer` 层，已开始）**：`member_across_files` + `DeclFact.type_of` 让 `widget.size`、`p->size`、`ns::Widget` 的对象、跨头文件的类都能解析，共用限定名那套查询；`type_of_expression` 是**递归**的，所以 `this->member` 和嵌套的 `a.b.size` 也通了；`DeclFact.bases` 让**基类成员**按层查找（含歧义与环）。**成员列表 `members_of`**（基类链在查询时走、不物化）与**补全入口 `member_completions_at`**（游标 → 类型 → 列表）都已落地。接下来按"能答的边界"往外推：
   - **作用域名补全**：`ns::`、`this->` 之外的裸名补全、以及 `Widget::` 静态成员——和成员列表共用 `ProjectIndex::declarations_in`，但输入是**一次作用域查找**而不是一个类型，所以是另一条查询而不是这一条的延伸；
   - `f().size`、`*p`、`arr[i]`（要**算**表达式类型而不是读声明的拼写，最大的一块——它会需要函数返回类型，而 `DeclFact.type_of` 现在只覆盖变量，所以第一步是把返回类型也记进事实）；
   - 模板实参的成员（`std::vector<int>::iterator`——需要实例化，属于更后面）。
4. **标准库**：目标不是打包一份 std 的声明，而是让 `#include <vector>` **能解析**——也就是在没有 `compile_commands.json` 时也知道搜索路径（问工具链，`g++ -E -v` / `clang++ -E -v` 的输出就能拿到；或读环境变量与常见安装位置）。解析出来了，增量索引会顺着 include 图把需要的头文件读进来，不需要预先索引整个 C++ 标准库。这一条和"项目文件清单"是同一个性质的东西（都是"从环境里发现配置"），应该一起做、一起缓存进配置维度。

   **施工图在 [`std-library.md`](std-library.md)**：本机实测闭包 185 个文件 / 111k 行 / 3.5 MB，冷索引 ≈1 s、热读 11 ms、盘上 326 KB（所以"按需索引闭包 + 按文件缓存"可行，不需要 std 特殊通道）；而闭包今天只有 26% 干净解析，134 个报错文件里 58% 的第一个错所在行有闭包**别的文件**定义的宏（只有 4% 是本文件自己定义的）——**所以起作用的是外部符号表，不是文件自己的 `MacroNames`**。那条线还带出一个到期决定：标准库的宏在 `#if` 两个分支里展开成不同的东西（`_GLIBCXX_BEGIN_NAMESPACE_CONTAINER` 在一个分支里开出 `namespace`、另一个里什么都没有），"这个宏是什么"因此是（文件+分支+位置）的属性——正是下面"两条曾经踩过的坑"里那条"哪天要把 `-D` 喂进去，键里必须同时把宏环境加回来，并且抬 `FORMAT_VERSION`"。标准库就是"哪天"。
5. **语义索引本身**：`files_declaring` 现在是"遍历所有摘要、逐个文件比较名字"，O(文件数 × 声明数)。一万文件时这是每次查询的开销，应该做成增量维护的倒排表（名字 → 声明位置）。先量再改（`examples/measure.rs` 已经能量构建与命中的代价，缺的是万文件规模的内存与查询耗时）。

**已经搁置的**（记下来，不再投入）：OS 监听器（客户端通知）、`stat` 先行的 mtime 优化（要等语义查询跑起来之后看真实的启动耗时）、项目文件清单扫描（等标准库/环境发现那一轮一起做）。

### 五条不能破的约定

1. **`Unknown` 是一等答案，而且要说清为什么。** 任何"我不知道"都必须带上 `UnknownReason`，不能猜一个最近的答案。新增一种"不知道"就新增一个 reason——`UndefinedHere`、`UnknownType` 都是这么做出来的。判据是：**消费者对不同的 reason 处置不同**（不该把"宏被 `#undef` 了"报成"未知宏"），否则说明你加错了。
2. **事实存拼写，不存结论。** `DeclFact.scope`/`type_of`/`bases`、`IncludeFact.resolved`、`FileSummary.path` 存的都是**文字里写着的东西**；没有一个 `FileId`、没有一个解析后的类型、没有一个已实例化的模板。理由是可增量性（见"三条不变量"）。**要往事实里加字段之前先问**：这个字段在头文件被改之后会失效吗？会，就不是事实。
3. **键（`SummaryKey`）的每个成分都必须能从文字和路径算出来。** 这是"先查盘、后解析"的前提，也是宏环境被删掉的原因。往键里加任何需要先解析才知道的东西，就等于取消了磁盘缓存的意义（`cache.rs` 的模块文档记着这次教训）。
4. **改了 schema 就抬版本号。** 加字段 → `CODEC_VERSION`（字节格式变了）；**答案会变错** → 也抬 `FORMAT_VERSION`（它在键里，会让整库作废）；只是让旧条目取不到（比如键少一个成分）→ 只抬 `CODEC_VERSION`。两个常量旁边都写着为什么。
5. **文档是规范，同一次改动里更新。** `docs/index-design.md`（索引/语义层的决策与不变量）、`docs/grammar-gaps.md`（parser 的读法、缺漏与维护约定）。**下游按上游形状写的判据要在 grammar-gaps 里留痕**（第 18 条就是这么来的：`w.size` 读成 `IndexExpr`）。

### 一条很好用的工作方式：把测试写成"能力落地那天会失败"

这个仓库里已经有两条这样的测试，都如期失败过，改动因此都是**有意的**：

- `a_qualified_name_from_outside_its_namespace_is_unknown_rather_than_wrong` ——限定名落地那天失败，改成断言正确行为；
- `a_nested_member_access_asks_about_the_last_name` ——递归推断落地那天失败，同上。

给一个还答不了的问题写测试时，**断言当前边界并写明"这是在等什么"**，比不写测试好得多：下一个接手的人会知道边界在哪，而且能力一旦落地，测试会自己找上门。反过来，**不要**为了让测试通过而把边界写死成永远的行为。

### 两条曾经踩过的坑（读代码时会看到痕迹）

- **`Binding.range` 是 declarator，不是整条声明**（`Widget w;` 里只有 `w`）。任何"名字之前的文本就是类型"的写法都会静默地得到空字符串。要类型就**从根往下走到声明处，取 `DeclSpecifierSeq`**（`declared_type_of`）。
- **`FileIndexer` 只给 parser 喂 `ParserConfig::default()`**：`-D`/`-std` 不参与解析，所以摘要与宏环境无关（这就是键里没有宏环境的原因）。哪天要把 `-D` 喂进去，**键里必须同时把宏环境加回来**，并且抬 `FORMAT_VERSION`——`cache.rs` 与"第三个被测试抓出来的键错误"都记着。
