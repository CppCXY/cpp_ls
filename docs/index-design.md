# 索引与语义层的设计（规范）

本文档记录**已经拍板的决策**与**不变量**。它约束 `cpp_code_analysis` 之后的所有工作：写代码时如果与这里冲突，先改这里并说明理由。

## 已定的三件事

| 决策 | 内容 |
|---|---|
| 缓存位置 | **项目内 `.cppls/`**（以后做成可配置项；默认放项目内，便于调试、CI、以及"和仓库一起删"） |
| 索引粒度 | **按文件**（per-file summary），不是按目录、不是按编译单元 |
| 目标范围 | **做完整的语言服务器**：语义推断（名字解析、类型、重载、模板、ADL）最终都要做 |

## 架构分层

```text
cpp_parser      语法：无损 CST、指令节点、宏表（#define 名字）、外部符号表接口
cpp_code_analysis
  preprocess    展开与条件：直接量/宏、guard 三态、Origin、预算
  summary       每文件事实：声明、宏、include、guard、模块   ← 落盘的单位
  resolve       按需查询：名字 → 声明（over include 图与 guard）
  infer         语义推断：类型、重载、模板实例化、ADL        ← 全部在查询时做
```

实际落地的模块名（`summary` 拆成了三层，因为三件事的输入不同）：

| 模块 | 职责 |
|---|---|
| `summary` | **只在数据形状**：`FileSummary` / `DeclFact` / `MacroFact` / `IncludeFact` / `FactGuard` |
| `sema::declarations` | **生产者**：从 scope 树 + 预处理状态 + 语法树产出 `DeclFact`（唯一同时看得到三者）；`declared_type_of`/`declared_bases_of` 同时供查询层直接用，避免两份实现 |
| `index` | **粘合**：`FileIndexer` 把 parse → preprocess → scopes → facts 汇成 `FileSummary`；`write_summary`/`read_summary` 落盘 |
| `summary_codec` | **字节格式**：手写编解码，magic + `CODEC_VERSION` |
| `sema::resolve` | **查询**：不生产数据、只回答问题——游标处的名字 → 声明、限定名 → 作用域、成员访问的形状（单文件） |
| `index::project` | **跨文件查询**：`ProjectIndex` 装摘要 + 派生反向边 + 可见性走查；入口是 `definition_across_files`（名字，含限定名）、`macro_across_files`（宏，位置化）、`member_across_files`（成员，含类型推断）、`member_completions_at` / `name_completions_at`（补全，两个位置） |
| `index::store` | **驱动**：`SummaryStore` 决定"什么时候建、什么时候复用、变了以后哪些要重建"——唯一碰文件系统的索引层 |
| `index::worklist` | **顺序**：`Worklist` 决定"先索引哪个文件"——打开的文件 → 它的 include 闭包 → 其余；一步一个文件，调用方决定节奏 |
| `index::references` | **找引用**：`macro_references` 回答"这个名字在项目里出现在哪些位置"——唯一需要**读文件正文**的查询（摘要里没有标识符位置）；四级阶梯：候选集 → 文本预筛 → 词法 → 精确判定，外加 `rename()` 给出的编辑表 |
| `index::watch` | **监听**：`ChangeBatch` + `WatchFilter` 把文件系统事件归约成"忘掉谁、重读谁、还是全量重来"；不含 OS 绑定、线程、时钟 |
| `session` | **驱动**：`Session` 把上面几层串成一个开着的项目——开项目（发现工具链 + 编译数据库 + 扫描）、`did_open`/`did_change`/`did_close`/`changed(事件)`、`advance(n)` 惰性索引、`view(路径)` + 五个查询。它**不碰协议**（位置是字节 offset），也**不含线程与时钟**（客户端就是事件源） |
| `cache` | 键与路径 |
| `build.rs` | **编译期**：把语法与本层源码的文本哈希成键里的 `reading_fingerprint`——"parser 一升整库作废"不再靠人记住（见"缓存与失效"） |

## 查询：从单文件到跨文件

单文件那一层（`sema::resolve::definition_at`）问的是"这个名字在本文件里指向哪条声明"，做不到时返回 `Unknown(NotDeclaredHere(名字))`——**那个原因就是跨文件层的入口**：它说的是"名字在别的文件里"，而不是"这个名字不存在"。

`index::project::definition_across_files` 把两层按 C++ 的解析顺序组合起来，**顺序就是正确性**：

```text
1. 本文件的作用域      —— 局部遮蔽头文件里的声明，永远
2. 本文件自己的顶层声明 —— 写在这里的声明不是头文件那条
3. 它 include 的头文件  —— 沿 include 图可达的那些
```

只有 `NotDeclaredHere` 会走到第 3 步；`Ambiguous` **不会**——那说的是"名字就在这里，而且不止一条"，去头文件里找是回答另一个问题。

跨文件查表要过三道判据：

1. **可见性**：声明所在文件必须从查询文件出发**沿 include 图可达**。项目里有 `Widget` 不等于这个文件能看见 `Widget`。
2. **限定名优先**：`a::Widget` 先按限定名匹配，再退到裸名——限定拼写是一个强得多的主张，不该被项目里任何一个 `Widget` 稀释。
3. **条件性**：路径上只要有一步 `#include` 落在 `#if` 里，答案就是 `Unknown(ConditionalCompilation)`，因为走没走那条分支取决于索引没有的宏。有条件路径与无条件路径同时存在时，无条件的那条获胜（它永远在）。

   **一处例外，而且正是它让标准库能被问到：文件自己的 include guard 不算条件。** 头文件把整个身体包在 `#ifndef _GLIBCXX_STRING` 里，于是"每个 `#include` 都落在 `#if` 里"——按上面那条规则，标准库的每一个跨文件答案都是 `ConditionalCompilation`。但那个条件的含义是"`_GLIBCXX_STRING` 还没定义"，而**包含这个文件本身就是定义它的那一刻**：任何一次真正读进内容的包含都走了那个分支，没走的那种是"已经读过一遍"，而声明在那一次也已经可见了。所以落在**文件自身守卫**里的事实被记成 `Unconditional`（`index::deguard_the_files_own_guard`，靠 `detect_guard` 判定，只认**包住整个文件**的守卫）。测量：`examples/std_query.rs`，加这条规则之前 7 个再普通不过的成员查询**全部**返回 `ConditionalCompilation`。

   这条规则没有擦掉 `#if` 这个事实：region 仍然记在 `SummaryGuards::regions` 里，守卫宏仍然是文件的宏之一；改的只是"它是否让内容可能不可见"。

**反向边是派生的，不落盘**：摘要里存的是每个文件**自己写的** `#include`（直接边），"哪些文件包含这个头"是图的属性而不是任何文件的属性，所以它从摘要现算，内存里存。写进磁盘就等于存了一个结论：它没有哪个文件可以跟着一起失效，而它和摘要第一次不一致时是看不出来的。

**`MacroEnvironment` 被删掉了**（曾是 `cache.rs` 里的一个类型 + 键里的 `macro_env_hash`）。它算的是"沿 include 链累积的、定义过宏的文件的 content_hash 集合"，用来让"某个头文件改了宏"这件事传播到它下面每个文件的键上。删它的理由是**它算出来的东西对摘要的内容没有影响，却是唯一一个必须走一遍图才能算的键成分**——于是 `get` 不得不在查盘之前先解析，磁盘缓存因此只省了"写"，从来没省下"解析"。证据是三件关于生产者的事实：`build_scopes` 只吃语法树；`build_facts` 用预处理状态只为**找指令位置**（每条事实记下自己所在的 `#if`，让消费者去判断，这正是 guard 存而不用的原因）；`#include 宏名` 永远解析不出来。详见 `cache.rs` 的模块文档与下面"第三个被测试抓出来的键错误"。**如果哪天摘要开始依赖宏**（在声明里做展开、或者把 `#if` 的未取分支剪掉），环境必须回到键里，并且同一次改动里必须抬 `FORMAT_VERSION`——否则盘上已有的摘要不是"取不到"而是"悄悄错了"。

### 单文件那一半

`sema::resolve::definition_at(scopes, root, offset) -> Known<Binding>`。它问的是"游标下这个名字在本文件里指向哪条声明"，**只看作用域链**：

```text
做：   作用域链（含 `using namespace` 带来的命名空间）
       限定名：`ns::C::f` 里的限定部分当作**作用域**去找，再在这个作用域里查最后一段
不做： 基类、ADL、重载选择、`using Base::m`、任何跨文件的东西
```

不做的那些**不是遗漏，是下一层**——但消费者必须能区分"没找到"和"没找过"，所以答案一律是 `Known`：`Yes(声明)` / `No`（本文件可达作用域里确定没有）/ `Unknown(原因)`。为跨文件这一条新增了 `UnknownReason::NotDeclaredHere(名字)`：名字在别的文件里，这是关于**本文件**的事实，而不是"这个名字不存在"。

### 限定名：限定部分是作用域，不是名字的一部分

`ns::Widget` **不是**一个要去作用域里找的名字，它是"**先找到一个作用域，再在里面找一个名字**"——两件不同的事，答案也不同。把限定部分丢掉、直接找 `Widget`，得到的不是"小一号的正确答案"而是**错答案**：`a::Widget` 和 `b::Widget` 都是"作用域里有个 `Widget`"，只有一个是游标指着的那条。测试里专门有一对文件同时声明 `a::Widget` 和 `b::Widget`，断言 `b::Widget` 跳到 `b`——丢掉限定部分时它会跳到声明顺序靠前的 `a`。

三件事因此被定下来：

- **游标处的限定名要拼出来**（`qualified_name_at`）：沿着名字节点的 token 走到游标所在的那个标识符为止，所以游标停在 `a::b::c` 的 `b` 上问的是 `a::b`——用户指着限定部分时，问的就是限定部分。模板参数列表不算名字的一部分（`ns::Widget<int>` 上的游标问 `ns::Widget`）。
- **前导 `::` 是拼写的一部分**，不是装饰：`::Widget` 问的是全局名字空间，所以只有写在文件作用域的那条能应答。匹配时**保留**这个前缀（`DeclFact.scope.is_none()`）而不是剥掉——剥掉就会把 `ns::Widget` 也算进来，正是这个拼写存在的意义所在。
- **相对限定名从外围作用域锚定**：写在 `namespace a` 里的 `b::count` 指的是 `a::b::count`，所以限定名会**从内到外逐个外围作用域**试一遍。这里与语言有一处刻意的差异并写在函数文档里：C++ 只把**第一段**按外围顺序找一次、之后一路向下不再回头，而这里是每个外围作用域试整个限定名——可能找到语言不会找的那条，但不会漏掉语言会找的那条。

本文件里找不到时，`NotDeclaredHere` 带的是**限定拼写**（`nope::count`），这正是跨文件层能接住它的原因：一条声明事实记着它所在作用域的限定拼写，所以"限定名"是索引能回答的问题（`declaration` 早就先按限定名匹配、再退到裸名）。

**顺带得到的一件事**：类外定义的 `int C::value() const { … }` 会解析回类里那条声明 `int value() const;`——那是 C++ 里最常见的"头文件/实现文件成对"的跳转，它现在就通了。

**排序是答案的一部分**：栈的最后一个是最近的作用域，所以"哪个声明赢"完全由 `scopes_to_search` 的顺序决定。第一版把链先压栈、外围作用域压在上面，结果**最外层每次获胜**——局部遮蔽被跳过了。抓它的是遮蔽测试，别的测试都抓不到。

**一处已知的过度近似**：`using namespace` 的目标按"文件里所有指令命名的命名空间"取，而不是"游标可见的那些"。代价是文件里有两个指向不同命名空间的指令时可能跳错一次；反向收紧的代价是把一个明明可见的名字报成未声明。已写在函数文档里。

## 三条不变量（比功能清单重要）

1. **索引存事实，不存结论。**
   summary 里只有"这个文件写了什么声明/宏/包含"，**任何已解析、已推导、已实例化的结果都不落盘**。理由是可增量性：一个 `#define` 变化会改变依赖它的每个文件里每个名字的含义，一旦把结论写进缓存，一次改动就要全库重算；而事实的失效范围是**可计算的**（反向 include 边 + guard 剪枝）。
2. **`Unknown` 是一等公民，且在完整系统里也保留。**
   文件没索引、正在编辑、解析有错、名字依赖模板参数、展开超预算、`#if` 无法判定——这些都返回 `Known::Unknown(reason)`，而不是猜一个答案。语言服务器的价值在于"**知道自己在哪些地方不知道**"，`UnknownReason` 已经把这套词汇建好了（`DependentName` 等）。
3. **parser 宽容，语义层必须验证来源。**
   parser 是容错的（解析出错也留下无损的树）。语义层只能相信**干净解析**的文件里的声明；有错的文件其声明标记为"部分已知"，参与解析但可以被查询方降权。这是"全都要做"的代价：越往上做精确推断，越要清楚手上这份事实有多可信。

   **落地形态（已实现）：不是"文件干净不干净"，而是每条声明一个 `DeclFact::clean`。** 判据是"这条事实写在哪条声明里、那条声明里有没有落进一个诊断"：取**包含该名字的最内层声明节点**（节点种类就是 `scopes::declaring_kinds`，和符号层读声明用的是同一张表，所以"什么算声明"不会两边漂移）。粒度是量出来的，在 `<vector>` 闭包（279 文件 / 8499 条声明，其中 5388 条来自有错的文件）上：

   | 问的是哪一段 | 判为不可信 |
   |---|---|
   | 这条事实自己的 range（= 声明符） | 106 |
   | **最内层声明节点（采用）** | **214** |
   | 任何包含该名字的声明节点 | 2907 |
   | 整个文件 | 5388 |

   第二行比第一行多出的 108 条正是要买的：按节点种类拆开，89 条是 `Declaration`、19 条是 `TemplateDecl`——也就是**类型部分**和**模板头**，都在声明符之外、都在声明之内，而 `type_of` 就是从那段文本读的。第三行看着最简单却不能要：类体里一个错会连坐它的每个成员，超过标准库一半的声明。**这一条是"诚实"而不是"能力"**：标准库今天答不出 `std::vector` 的原因是解析没读下来（没有这条事实），不是因为它的声明被标成不可信——`clean` 决定的是"已经读到的这些能不能用"，把不可用的事实指出来，好过让调用方以为它们都对。

## 事实的形状：两个不得不再三确认的决定

**限定名要存限定路径，不能只存名字。** 一条 `DeclFact` 带 `name` 加 `scope`（声明所在作用域的**限定拼写**，如 `ns::C`）。

- 没有它，`ns::C::f` 查不到：名字本身不标识一条声明——两个文件可以各声明一个 `Widget`，一个文件可以在文件作用域和类里各有一个 `f`。
- 存**拼写**而不是 id，因为 id 是运行期 interner 的下标、重启即失效；拼写还能被 symbol 搜索直接显示。
- 派生它的前提是 `Scope` **记录自己引入的名字**（`Scope::name`），并且 `namespace a::b` 与 `namespace a { namespace b {` 必须产出同一条限定名——两处都有测试钉住。

**`include` 与 `path` 存路径，不存 `FileId`。** 同一个理由，而且更硬：`FileId` 写进磁盘之后，下一次运行读回来的含义是另一回事。反向 include 图因此是**从事实在内存里重建**的，不落盘——那正是"存事实不存结论"的直接推论。

**后来加的字段遵守同一条规则**：`DeclFact.type_of`（变量被写成的类型）、`DeclFact.returns`（函数返回的类型）与 `DeclFact.bases`（类的基类清单）都存**拼写**，不存解析结果——`ns::Widget`、`std::vector<int>`、`public B` 原样存，消费者用既有的限定名机制去解析，解析不到就是 `Unknown`。判断一个字段该不该进事实，问的是同一句话：**头文件改了之后它会失效吗？** 会失效的（解析后的类型、`FileId`、实例化结果）就不是事实。字段的边界也写在字段文档里：`type_of` 只对变量/字段/参数、`returns` 只对函数（类*是*类型、函数*返回*类型，两者互斥——`make` 不是 `Widget`，对**名字**做成员访问没有东西可查，而对**调用**有），`bases` 不含访问修饰符和 `virtual`（它们决定成员能不能**到达**，属于语义而不是文本事实）。

**`returns` 有一个 `type_of` 没有的问题：尾置返回类型。** `auto make() -> Widget` 把类型写在参数表**之后**，所以说明符序列给的是 `auto`——一个不是类的词。字段因此记的是"文件**声明过**的返回类型"：尾置返回类型优先（它才是文件说的那个），而**推导**出来的 `auto` 记 `None`（`auto make() { return Widget{}; }` 记 `None`，因为"我不知道"才是真话，"类型 `auto` 里没有成员"会把一句话说得像是答案）。实测：`<string>` 闭包 291 个文件 / 8659 条声明里 1174 个函数，**1145 个（97.5%）**记到了返回类型。

**同一句话还回答了一个更细的问题：`scope` 为 `None` 的声明有几种？** 两种，而事实一度分不出来——**文件作用域**的（`void helper();`，每一个包含这个文件的文件都能用）和**函数体里的**（`int __first = 0;`，外面谁也用不了）。补全那一轮撞上了它：跨文件的名字查找只能按名字匹配，而标准库头文件里叫 `__first`、`n` 的局部声明有成千上万，于是"多给几个候选"变成了"给用户看不见的名字"。修法是加 `DeclFact.local`（`CODEC_VERSION` 8），答案来自**作用域链**（链上有没有函数体/块/lambda）而不是声明的形状——`void f() { }` 和 `void f() { int x; }` 的区别不在声明的形状里。它同时修掉了 `definition_across_files` 会跳到别的文件函数体里的那条旧账，理由和判断字段该不该进事实的规则是同一个：**这条信息在查询时算不出来**（索引里没有"这条声明在哪个函数里"）。

**第三个字段问题的答案是"不落盘"**：`DeclFact.bases` 只存 `D` 写下的基类拼写，**绝不把继承来的成员写进 `D` 的摘要**。基类链在查询时走（`index::project::members_of`）。物化（把 `B` 的成员摊到 `D` 上）看起来只是省一次查询，实际会制造一类**没有任何东西能发现**的陈旧答案：

```text
1. B 增删成员              —— D 的文字和键都没变，落盘的成员表已经错了
2. D 的基类清单变了        —— 这条能抓到，因为 D 的文字变了
3. 名字 `B` 指的是哪个 `B`  —— D 的文字没变，宏 / include / #undef 一改就换了目标
```

第 3 条是决定性的：`D` 的文字与键都原封不动，任何"按文件失效"的规则都看不见它。测试 `a_member_added_to_a_base_appears_without_reindexing_the_derived_class` 把这条论证变成了断言——它只重建 `b.h`，然后要求 `A` 的成员列表跟着变，并顺手断言 `A` 自己的摘要里**没有** `B` 的成员。

**推论**：事实里没有的东西，查询时就得能算出来。所以"能不能物化"这个问题等价于"查询时能不能走回去"，而走不回去的那种（这一条）恰恰也是最不能存的。

**一个看起来像"结论"、其实过了同一条判据的字段：`MacroFact::settles_the_name`**（`CODEC_VERSION` 10）。它记的是"这条 `#define` 所在的条件块，每个分支都同意这个名字是什么"——一条**从本文件自己的指令算出来**的结论，所以问那句话（"头文件改了它会失效吗"）答案是**不会**：别的文件怎么变都改不了这个文件里 `#if` 的写法。它和"解析后的类型"那种结论的区别正在这里，规则见上面"找引用"那一节。

**一处与不变量 1 有张力的地方，摆明在这里**：`IncludeFact.resolved`（`#include "widget.h"` → `/p/widget.h`）**确实是**项目层面的结论，不只是文字的事实——它取决于文件所在目录、include 路径，以及那个文件**到底在不在**。之所以还是存下来，是因为可见性走查（`index::project` 的 `visible_files` / `includers_of`）只拿得到摘要，而它每问一次名字就要走一遍图；把解析推迟到查询时意味着把 resolver、provider、配置全都搬进 `ProjectIndex`，图的形状会在每次查询里重算。

存它的代价被三件事兜住了：（a）目录和配置进了键（见上）；（b）**解析不到的 include 让摘要不落盘**（见下），所以磁盘上任何一份摘要里的 `resolved` 都是当时真实解析出来的；（c）**盘上的摘要在被相信之前要重新核对一遍**——`SummaryStore::get` 命中时逐条重解析它的 include，任何一条解析结果不同就把整份摘要当成未命中。`resolved` 是关于文件系统的主张，而键必须能从文字算出来，所以"哪些候选路径存在"永远进不了键；那就不能盲信，核对让它从"结论"退回"候选"，代价是命中时每个 include 几次 `exists` 而不是一次解析（实测见下）。

这一条顺带定下监听层的地位：**它是及时性，不是正确性**。遗漏事件只会让答案晚一点变、不会让它错——因为任何一份旧摘要在被用之前都会自己撞上核对。监听层买的是"事件一发生答案就变"，而不是"因为监听了所以对"。

想做干净的那一天，走法是把 `resolved` 从摘要里拿掉、改成查询时解析，那是 schema 变更，值得单独一轮；在那之前 (c) 就是它的替代品。

## 缓存与失效

- 目录：`<project>/.cppls/summaries/<hash 前两位>/<key>.bin`（一文件一摘要，**不要一个大 blob**）。`.cppls/` 已在 `.gitignore` 里——它随 checkout 走是刻意的（CI 拿到同样的热缓存），但派生数据永不入提交。
- 键：**`content_hash + context_hash + format_version + reading_fingerprint`**。四个成分都是**能从文字、路径和二进制本身直接算出来的**——这不是巧合，是要求：只要键需要"先解析才知道"的东西，查盘就必须排在解析之后，缓存也就永远省不下解析。
- `context_hash` = 编译配置（include 路径按 `working_directory` 解析后、`-D`/`-U`、标准、目标）**加上文件自己所在的目录**。配置和目录是同一个问题而不是两个：`#include "widget.h"` 的意思是"**我旁边那个**"，所以同一段文字放在两个目录里是两份不同的编译、会解析到两个不同的文件。
- `format_version` 含 parser 版本号：parser 一升，整库作废。字节格式另有一个 `CODEC_VERSION`（写在文件头里），两者变化的原因不同：加字段两个都动，调整一条记录的字段顺序只动后者。**删掉键里的一个成分只需要动 `CODEC_VERSION`**：旧条目只是取不到（键的名字变了），永远不会被当成新键的答案，因为读回来的键要和刚算出来的键逐字段相等才算命中。
- **`reading_fingerprint` 是"读者"的指纹，由 `build.rs` 算出来**（`cpp_parser/src` 与 `cpp_code_analysis/src` 的源码文本，含路径与内容的 FNV-1a）。这一条是补一个**写在文档里、却一直没有机制**的规则：上一行那句"parser 一升，整库作废"靠人记着，而它**没有被记住**——语法改了十几轮，`FORMAT_VERSION` 一直是 1，盘上每一份摘要都是一个更早的读者写的，并且被照常端上去。**错的答案，不是缺的答案**。指纹把"记得抬版本号"换成了"二进制自己知道"：源码一动，键就变，整库取不到，下一次查询重建。它没有把宏环境那个错误带回来——它**不需要解析**就能算，是二进制的常量（`build.rs` 只在编译时读文件，运行时不读）。`FORMAT_VERSION` 因此退回它真正独占的职责：**源码里看不出来的变化**（依赖升级、构建输入不同）。副作用要认下来：改一行注释也会让缓存作废，代价是一次闭包重建（秒级）。
- 写盘是 `.tmp` + rename：崩溃留下的是旧摘要，而不是半份新的——**半份摘要是活的错答案，比没有更糟**。
- 读盘失败（缺失、损坏、版本不符）一律是"重建"的指令，绝不留一个字段取默认值的半份摘要。解码器对截断、超长计数、越界枚举值逐个报错，并且**拒绝尾随字节**。
- 命中不是"读出来就用"：**每一条 `resolved` 都要重新解析一遍**，任何一条不同就当未命中重建（理由见上）。所以命中一次的代价是"读一次文件（算哈希）+ 读一次摘要 + 每个 include 几次 `exists`"，而不是零。
- 启动：只 `stat`，命中即复用；mtime 变了算内容哈希，**哈希命中旧摘要直接复用**（分支切换因此从"全量重解析"变成"只读盘"）。内容真变了才重建，并沿**反向 include 边**做工作集失效。
- 批量变更（切分支/merge/格式化）：两段式——**打开的文件 → 它的 include 闭包 → 其余**，由 `index::worklist` 实现（一步一个文件，调用方决定节奏）；UI 不阻塞，未索引的文件查询返回 Unknown 而不是等。
- 监听：**不接 OS 监听器**。语言服务器由**客户端**通知（LSP 的 `didOpen`/`didChange`/`didSave`/`didClose`/`workspace/didRenameFiles` 本身就是事件源），所以不需要 `notify`、不需要去抖时钟、不需要文件系统轮询。客户端来一批事件就交给 `session::Session::changed`（它内部构造一个 `ChangeBatch`、调一次 `respond`，再把返回的路径**排进自己的队列**——这就是服务器的接入点）。过滤与合并规则（`.git/`、缓存目录、构建目录、`compile_commands.json`、`删+建` 的合并）仍然有用，因为客户端也可能报出无关路径。重命名按内容哈希复用（同目录同文字 ⇒ 同键，一次解析都不用重来），但**监听层不负责把新路径加进索引**——那是文件清单和 include 图的活。

### 驱动层：`SummaryStore` 的四条规则

`index::store` 做四件事：`get(path)`（现在是文件**当前**该有的摘要）、`index_includes_from(entry, budget)`
（**一个文件及其闭包**——顺着摘要里的 `resolved` 边走边问缓存，返回 `IncludeIndex`）、`invalidate(path)`
（改了以后的工作集）、`stats()`（命中率）。它不监听文件系统、不排调度、不碰线程——和 `FileIndexer` 对解析
的态度一样。

**闭包那一条是"打开一个项目"的入口**，也是 P0 的搜索路径发现第一次真正兑现的地方：`#include <vector>`
解析得出来之后，这一个调用就会把 185 个标准头索引进缓存。实测本机一个含 `<vector>`/`<string>` 的
`main.cpp`（含 `clean` 字段的这一轮之后重测）：冷 310 个文件 4.5 s，热 308 个命中 255 ms、盘上 1836 KB。它**不是一个新层**：闭包的结构不需要
重新解析，因为摘要里已经记着每条 include 解析到了哪个路径，所以循环就是"问 store 要一个文件 → 从答案里
读它包含谁 → 再来"。预算（文件数 + 深度）两条，且**截断要报告**（`not_indexed` 带原因），因为"没有更多了"
和"可能还有"是两句话。

**规则一：先查盘，后建。** 顺序是：读文字 → 算键（哈希 + 语境，两者都不需要解析）→ 盘上有就直接用 → 没有才建、落盘。命中时**连 include 都不去找**（有测试用 provider 的探测量钉住这一点）。这条规则是宏环境离开键之后才成立的，见上；它也是"缓存到底省了什么"的答案：省的是解析，不只是写。

**规则二：记录了"没找到某个头文件"的摘要绝不落盘。** 那是一条关于**文件系统**的事实，而键必须能从文字算出来，于是键里没有"哪些候选路径存在"这一项——存下去就会在头文件出现之后继续说"找不到"，没有任何东西会发现。这种摘要照建照返回，只是不写，并计入 `StoreStats::unstored`：理由和不变量 2 是同一条，错的条目比没有的条目糟。注意规则只管**解析失败**，不管"包含的文件还没被索引"——后者是关于索引的事实，不是关于这份文字的事实，而且它自己会好。

**规则三：文件不能读不是错误。** 被删掉的文件、不是文件的路径，`get` 一律返回 `None`：调用方问的是一个不存在的文件，答案是"关于它没什么可说的"。**读得到但解析有错**是另一回事，照建摘要：parser 是容错的，一份带错文件的摘要正是半可用的编辑器要的东西。写盘失败同理（不报错）——只读 checkout 是完全正常的用法，它不该把编辑器变成坏的。

### 宏体推导出的事实：**记证据，不进键**（B120，那条陷阱的答案）

`cache.rs` 的模块注释把条件写得很清楚："**如果这有一天不再成立**——声明里真的展开宏，或者按条件裁掉未选中的
分支——环境就必须回到这里，而且 `FORMAT_VERSION` **必须在同一次改动里**抬起来。"这一轮就是那一天，而原因是量出
来的：MSVC 的 `<vector>` 里**没有一处**字面 `namespace std`，只有一行 `_STD_BEGIN`，它的体 `namespace std {`
在 `yvals_core.h` 里；`std::vector` 能不能查出来，取决于这个体。

**陷阱给的两条路，选第一条，并把它做得更具体一点：读法连同它的来源记进摘要，键一个字不改。**

为什么不是第二条（把宏/体指纹加回键）：那条路的代价不是"多一个哈希"，而是这个仓库花过一整轮才拿回来的两个性质。

```text
1  键的每一个成分都能从文字和路径算出来 ⇒ 查盘发生在解析之前（cache.rs 的模块注释记着上一次丢掉它的后果：
   缓存"省下的是写，不是解析"，而写从来不是瓶颈）
2  一份摘要**不依赖它所包含的文件的内容** ⇒ 改一个头文件是一个文件要重读，不是五十个（store.rs 的 invalidate
   注释把这条当作 watcher 便宜的原因写下来了）。宏环境一旦进键，这条就没了
```

为什么第一条不是"把问题藏起来"：摘要记的不是结论，是**证据**——这一次读法用到了哪个宏（名字、调用点偏移）、
当时它的体是什么。于是它和 `SummaryGuards` 是同一个形状（那儿存的是每个 `#if` **问的问题**，答案在查询时给），
也和 `resolution_still_holds` 是同一个位置（命中之后**重新问一遍**那些"键看不见的事实"，不同就重建而不是照用）。
能重新问的消费者必须问（`ProjectIndex::macro_environment` + `body_text_of`/`body_text_in_force` 就是那条路，
`index/references.rs` 每次查询已经在走）；问不到的消费者至少知道这个答案是从哪来的，这比一个裸事实多。

**要认下来的代价（写在前面，不留给下一个人发现）：**

```text
· 记了宏体证据的那些文件，**确实**依赖被包含文件的文字 ⇒ 那个头文件改了，它们要失效。今天 watcher 对普通编辑
  不调 invalidate()（理由就是上面第 2 条），这一条因此要改成"这个文件，**加上**记了它体证据的那些 includer"。
  范围是有界的，而且是量出来的：整个 MSVC include 树里写 `_STD_BEGIN` 的有 134 个文件，`<vector>`/`<string>`/
  `<map>` 那个 109 文件的闭包里是 **33** 个（39 处调用）——名单是"真读到体的文件"，不是"整个闭包"
· `FORMAT_VERSION` **不抬**：键没有变，旧条目按旧键仍然命中；它们的读法来自另一份环境、而且**带着证据**，
  所以是可查的，不是静默错的。这一条如果哪天不成立（比如证据没记全），那一次改动才需要抬版本号
· 证据只记**真的用到的**宏体：一个文件里没有 `_STD_BEGIN`，它的摘要就与今天逐字节相同——所以这不是"全库作废"
```

**落地状态（写给接手的人）**：


### 顺序层：`Worklist` 的两段与两个队列

`index::worklist` 只回答一个问题：**下一个索引哪个文件**。它是 `step()` 一步一个文件的驱动，不是返回 `Vec<PathBuf>` 的计划——因为**一个还没被索引的文件的 include 是不知道的**：每一步摘要到手，才多知道一层下一轮要做什么。这一步的形状同时决定了它的用法：编辑器每个空闲 tick 走一步，后台线程循环到 `None`，有预算的调用方随时停手（列表保持状态，没走到的文件查询返回 `Unknown` 而不是等）。

**两段，两个队列，不是因为两段代码不一样，而是因为一个队列会错。** 两半做的事完全相同（从种子出发的广度优先，跟着 include 走），只有一个队列看起来更简单，但那样一来"调用方列了一万个项目文件"就把"用户正开着的那个文件的闭包"挤到了最后——而那正是第一段存在的理由。有测试用一个比闭包更长的项目列表钉住这一点。

**第二段也跟 include，因为调用方的清单通常只有翻译单元。** `compile_commands.json` 里只有 `.cpp`，头文件一个都没有；不跟 include 的话，索引里除了"某个打开的文件恰好够得着的头"以外什么头文件都不会有。代价要说明白：**工作列表是它拿到的种子的传递闭包**——一个 include 了 `<vector>` 的根，在有系统 include 路径的机器上会把那些头也拉进来。要收窄就收窄种子（或者停手），这一层不对"哪些目录值得索引"发表意见。

**去重与终止**：按规范化路径建 `seen`，所以菱形包含只走一次、循环包含会终止、`open` 与 `project` 里同时出现的文件**只走一次且落在第一段**（它确实是"用户正看着的文件"，这就是第一段存在的理由）。

**一步的结果不问 store，而是看计数器的位移。** `StoreStats` 是累积的，所以 `StepOutcome` 是"这一步期间计数器往前挪了多少"——正因为如此它才是 `Copy` 且可比较的：store 自己的账就是唯一的一份账，另存一份在 `Worklist` 里就是第二个要同步的东西。`Unstored` 蕴含 `Built`（先建了才发现不该落盘），顺序按这个读。**这条判据是 `outcome_of` 一个函数**，`Worklist` 与会话层共用——见下一节。

### 会话层：`Session`——驱动不是一个函数，而是一个类型

`session::Session` 是"一个开着的项目"：配置、队列、已经读到的事实、以及**编辑器开的那些缓冲区**。它把四层串起来，一层都不是新的：

```text
Session::open(root, &files, filter)   发现工具链 + 读 compile_commands.json + 扫描源文件 → 队列的种子
did_open / did_change / did_close     缓冲区成为该路径的文本；旧摘要丢掉；该文件进"开着的"那半边队首
did_save（带文本时同理）               保存不改变分析读的东西：缓冲区本来就是文本，现在磁盘也一致了
changed(事件)                         客户端的文件系统事件 → ChangeBatch → respond → 排进队列
advance(n)                            n 个文件，一步一个；顺序就是 Worklist 那条
view(路径) + 五个查询                  缓冲区（有则）解析出树与作用域，再拿索引一起回答
```

**provider 归调用方所有，这是借用检查器逼出来的形状，也是对的形状。** `SummaryStore` 借 provider 过活，所以 `Session` 只能借那串 `OverlayFiles<OpenDocuments, DiskFiles>`；缓冲区放在 `Arc<RwLock<…>>` 里，于是 `did_change` 能在 store 还活着的时候改文本。`SummaryStore` 若改成**拥有** provider，测试就没法在事后读 provider 的读日志（`MemoryFiles` 的 clone 各自持有一份文件表），而自引用结构 Rust 没有安全写法。

**队列是自己的，不是 `Worklist`。** 两条理由：会话的队列**活过一批**（通知会重新播种），而 `Worklist` 可变借用 store——拿着它的会话在两步之间答不了任何查询。顺序是同一条，`StepOutcome` 的判据也共用（`outcome_of`）。

**两个半边 + 升级**，这是这一层唯一一个不显然的规则：项目扫描在开项目时把所有文件放进 rest 半边，用户随后打开其中一个——如果不管它，被打开的文件就排在"项目其余"后面，**而所有"从不打开任何文件"的测试都会是绿的**。所以路径带 standing（`Queued(Open)` / `Queued(Rest)` / `Worked`）：升级只加一条队列项、不重复计一个文件，旧的那条浮上来时被跳过（有测试钉住"它不会被读第二遍"）。`again`（用户正在等的文件变了 → 队首）与 `requeue`（整个键空间作废 → 队尾）都会清掉 standing——`add` 的职责恰恰是拒绝已经读过的路径，而"变了"必须越过它。

**惰性索引让 `NotDeclaredHere` 有两个意思，这一层不假装能分开。** "这里没有"和"还没读到"在查询层是同一个答案（`ProjectIndex::definition` 的文档写着索引永远是全集的一个子集、从不声称"哪儿都没有"），所以分界线交给上层：**`pending() > 0` 时不要报"名字不存在"，`pending() == 0` 时它才是关于项目的结论**。`is_indexed(路径)` 是同一个问题的单文件版本。

**"这个文件配不配有摘要"在会话层多了一个答案：配，因为用户开着它。** 监听层答不了这个问题（它只在"索引已持有 / 有文件解析到它 / 有 include 在等它"三种情况下动），而会话层知道缓冲区——这正是"打开一个从未保存过的新文件"能立刻被 include 解析到的原因。

**测到的**（`examples/open_project.rs`，release）：冷启动开项目 72 ms（其中工具链发现是大头），`s.size` 的成员在第 **32** 个文件后答出来、耗时 2.58 s，整个闭包 454 个文件 9.4 s；**热启动**同样 32 个文件但只用 **26 ms**，其余 422 个文件里 3 个解析、451 个从盘上读回（命中率 99%）。"第一个答案"和"整个项目就绪"差的 420 个文件就是惰性索引省下的东西。

### 监听层：事件 → 工作

`index::watch` 把一批文件系统事件变成三句话："**忘掉**这些"、"**重读**这些"、"**全量重来**"。它**没有** OS 绑定、没有线程、没有时钟——`notify` 那一类适配器只负责产出事件，而"一批什么时候算结束"是个时钟问题（编辑器一秒写同一个文件好几次，切分支是一阵爆发），两者都是这个模块外面的一层薄壳。加不加 `notify` 这个依赖，这一层不强加给任何人。

**"改了"是最无聊的一个，这正是重点。** 文件文字变了只需要重读它自己，**别的什么都不用**：摘要是"这个文件自己的文字 + 目录 + 配置"的函数（`SummaryKey` 就是这么定的，宏环境离开键也是因为这个），它不依赖被包含者的内容。所以改一个头文件是重读一个文件，不是重读包含它的五十个。（查询的答案会变，但查询走的是内存里那份活的索引，头文件摘要一换，新声明立刻可见。）

反过来说，**只有"出现"和"消失"才会让一份摘要失效而它的文字没变**——因为摘要记着 include **解析到了哪里**，那是关于文件系统的事实：

```text
a.cpp:  #include "generated.h"     ->  resolved: None          （那时还没这个文件）
……      generated.h 被创建          ->  a.cpp 的摘要是错的，而它的文字一个字没改
```

**"出现了"能被精确算出来，不需要存候选列表。** 一个 include 的拼写、它写在哪个目录、以及配置里的 include 路径，三者合起来决定了它试过的每一个候选路径；拼写在摘要里，目录来自文件自己的路径和配置。所以判断的方式是**从每个文件那边**枚举它试过的路径（用 resolver 自己的 `join_normalized` 拼），再拿这批"刚出现的路径"的集合去查——这样一批一千个创建也只是一遍扫描，而不是一千遍。同一套判断还回答另一半：`p` 出现在当前解析结果**更前面**的位置时会接管（`#include "x.h"` 原本解析到 `-I/inc` 里的那份，直到有人在文件旁边建了一个）。排序用的就是 resolver 自己的名次，不是对它的猜测；`#include "..."` 与 `<...>` 的区别也照搬 resolver——尖括号不搜文件自己所在的目录，所以旁边新建的文件不会"修好"它。唯一的近似是 `#include_next`：resolver 从"这个文件当初是在哪找到的"之后开始搜，而那个位置没存，所以这里从头枚举——这只会**多**算几个文件（多一次重建），不会漏。

**过滤里只有两件是正确性，其余都是优化。** 正确性的是**缓存目录**（索引往那里写摘要，不过滤就等于拿自己的写当输入，永远重索引）和 **`compile_commands.json`**（它不是源文件，而是"配置变了"的信号）。`.git/` 和构建目录是优化，而且值得说清楚它优化的是什么：**没有任何文件包含、索引也从没持有过的路径，出什么事都是空操作**，所以真正省下的是那一批事件的大小——一次 `git checkout` 会在 `.git/` 下产生几千个事件。同理**没有扩展名过滤**：`#include <vector>` 根本没有扩展名，一张"C++ 扩展名"白名单会恰好丢掉索引最需要的文件。

**"这个文件配不配有摘要"不是看名字回答的**，所以监听层也回答不了：它只在三种情况下把文件放进工作集——索引已经持有它、有文件解析到了它、或者有文件的 include 正在等它。其余的新文件由**文件清单**（扫描目录 / `compile_commands.json`）和 **include 图**（`Worklist` 会跟着 include 走）带进来。这就是为什么重命名一个 `.cpp` 不会让监听层有任何动静，而它依然免费：同目录同文字就是同一个键，谁去问都是命中。

**合并规则是保守的那个**：一条路径上最后一个事件决定它**在不在**，而这一批里出现过任何一次创建就决定它**可能是新的**。编辑器真实的写法正好落在这两条上：`删+建`（写临时文件再改名覆盖）→ 文件在，而且可能是新出现的；`建+改` → 同上；`建+删`（临时文件来了又走）→ 不在。至于**一批什么时候结束**，那是调用方的时钟。

**一批过大就不值得一条一条问了**：切分支会来几千个事件，超过阈值（256）时"向项目要文件清单、跑一遍 `Worklist`"更便宜，而且并不更差——没变的文件都是命中。配置变更走同一条路：配置进了每一份摘要的键，所以一个 `-I` 就能让全项目的键一起移动，此时要的是从文件清单重来，而不是问这一批里的路径。

### 宏查询：翻译顺序就是答案

`macro_across_files(index, root, path, offset)` 回答"游标下的这个名字是哪个宏、在哪里定义"。它是**第一个不需要作用域的语义查询**——宏不是名字查找，而是**翻译顺序**问题：预处理器把整个翻译单元读成一条流（本文件的每一行，每个 `#include` 处原地粘贴整个被包含文件，递归），某一点上生效的宏就是**最后一个走过的** `#define` 或 `#undef`。

所以一条宏事实的位置不是偏移量，而是一条**偏移量链**：把它拉进来的那个 `#include`，再是*那个文件里*的 `#include`……最后是它自己的偏移量。**两条链按字典序比较就是比较它们在流里的先后**——这就是为什么"写在这里"和"写在头文件里"不需要两套规则：

```text
a.cpp:  #define MAX 1        位置 [0]        → 头文件那条更晚，获胜
a.cpp:  #include "x.h"       位置 [10, 4]
a.cpp:  #include "x.h"                        → 本地那条更晚，获胜
a.cpp:  #define MAX 1         位置 [0]
```

`#undef` 因此也是**一条事实**（`MacroKind::Definition | Undefinition`，`CODEC_VERSION` 4），而不是一条注释：链条最后一个如果是 `#undef`，说明这个名字在这里是普通标识符，答案就是 `Unknown(UndefinedHere(名字))`——**不是**指向那个已经失效的 `#define`（那是错答案而不是缺答案），也不是 `Known::No`（索引只看到翻译单元的一部分，`#undef` 之后被包含的头文件仍可能重新定义它）。`UndefinedHere` 是这一轮新加的 `UnknownReason`,因为消费者对它的处理和"没人定义过这个名字"完全不同：前者不该报"未知宏"。

**四个答案**：`Yes(定义)` / `Unknown(UndefinedHere)` / `Unknown(ConditionalCompilation)`（能决定它的每条事实都在 `#if` 里，或者要经过一个在 `#if` 里的 `#include`）/ `Unknown(NotDeclaredHere)`（索引里没有任何文件碰过这个名字——**不是**"这个宏不存在"）。

**优先取无条件的那条**，和声明查询同一条规则、同一个理由：`#define` 在上面、被 `#if` 包住的 `#define` 在下面时，这个名字**确定**是宏，报 `ConditionalCompilation` 等于拒绝回答一个有答案的问题。残留的不确定性写在文档里而不是藏起来：无条件 `#define` **之后**那条被 `#if` 包住的 `#undef`，按"没发生过"处理。

**两处刻意的近似**（都写进了函数文档）：一个文件在一次查询里只展开一次（这保证了 include 环会终止；代价是"同一个头文件被两条路径包含"时，它可能被放在两次位置里较早的那次——但它报告的事实是同一条）；`#undef` 的位置是整条指令的范围，因为指令读取器不记录 `#undef` 的名字范围（跳过去看到的是那一行，够用）。

**没有 `Ambiguous`**：两条不同的链不可能相等，所以"同一个名字有多个定义"这件事在这里不是歧义而是有确定答案的——这正是宏查询比名字查询简单的地方。

### 找引用：四级阶梯，以及"位置表为什么没做"

`macro_references(index, files, name, budget)` 回答反过来的问题——**这个名字在项目里出现在哪些位置**——而它是**唯一需要读文件正文**的查询：摘要里存的是声明与指令，没有标识符位置。重命名要的就是这个列表。

**设计问题因此变成"一个项目里找一次引用要读多少东西"，答案是一段四级阶梯，每一级都比上一级便宜，而且每一级都是可靠的（不是启发式）**：

```text
1. 候选集    只有能看见某个定义的文件才可能是用户：定义所在文件 + 它们的传递反向 include 闭包
2. 文本预筛  text.contains(名字) —— 精确：标识符的文本一定是正文的子串，所以没有这个名字的文件一个标识符都不可能有
3. 词法      CppLexer 一遍：注释是一个 token、字符串是一个 token，两类最大的假阳性根本进不了标识符过滤
4. 精确判定  每个命中问"这个名字在这里是不是宏、是哪条 #define"（macro_environment，见下）
```

**第 3 级是这一层能成立的关键**，也是"要不要在摘要里存一张标识符位置表"这个问题的答案。实测（`examples/find_references.rs`，标准库闭包 454 文件，问用得最多的四个宏）：词法要 **14–27 ms**，同样这些文件**解析**要 **448–932 ms**（**17–56 倍**），而整条查询 **25–40 ms**；整个闭包有 **630 278 个标识符**，一张"名字 → 位置"的表约 **4.9 MB**，现有摘要一共 5.4 MB。**要存的位置比要存的事实还多，而查询并不慢**——所以位置表不做，这条结论是量出来的，不是偏好。

**写这份查询时先写错了一次，量出来才发现，这条要记住**：第一版每个命中单独调一次 `macro_definition`，于是每个命中都走一遍同一张 include 图。`STDMETHODCALLTYPE` 的 4 079 个命中 = **3.77 s**。改成"每个文件算一次**宏环境**（`ProjectIndex::macro_environment`），再按偏移问它（`MacroEnvironment::at`）"之后是 **35 ms**，**106 倍**，而两次答案逐条相同。这个拆分之所以可能，是因为"走到哪些事实"与偏移无关，而"哪条事实在生效"只与偏移有关：链在构建时算一次，偏移只用来过滤和比较。

**答案的形状**：每条命中只有三种归宿——确定是它（`Definition` / `Undefinition` / `Use { resolved_to }`）、确定不是（计数进 `rejected`：同名变量、`#undef` 之后的普通标识符）、可能但说不准（`Uncertain(ConditionalCompilation)`）。`rename()` **只改确定的那两种**：不确定的位置可能是别的实体，改它是改用户没让它改的代码；要显示它们由调用方决定。计数器是阶梯本身（`candidates()` / `looked_at` / `without_the_name` / `lexed()` / `not_looked_at` / `unreadable`），全部有 accessor——第一版探针自己算错过一次（把跳过的文件加进了读过的），有测试钉住它们相加等于阶梯。

**两处顺带修掉的"读错了一半"**，都是旧字段不够用而不是新功能：`#undef` 的事实带的是**整条指令**的范围（指令读取器不记名字在哪），于是重命名会把 `#undef API` 整行换掉——现在用词法给出的名字范围补上；`name_at` 在**指令里**答 `None`（`#define FOO` 是 token，不是名字节点），于是"在 `#define` 上右键找引用"这条路本来是断的（新增 `name_at_including_directives`）。

**边界：标准库上几乎每条命中都是"可能"，而原因量清楚了。** MinGW 的 `winnt.h:450` 把 `STDMETHODCALLTYPE` 定义在 `#ifndef STDMETHODCALLTYPE` 里（"define-once"惯例，不是文件守卫），所以"这个名字在这里是不是宏"取决于分析没有的宏环境。

**这一条已经用一条定理解决了**（`MacroFact::settles_the_name`，`CODEC_VERSION` 10）：

```text
#if 的每个分支都写了同一个名字、同一种 kind，而且要么有 #else、要么是单分支的 #ifndef NAME / #define NAME
   ⇒  这个条件块之后，这个名字的宏状态与分支无关
特例（最常见的形状）：#ifndef NAME / #define NAME / #endif
  条件成立 → 这里定义了；条件不成立 → 它已经被别的头文件定义过。两种情况之后它都是宏
镜像：#ifdef NAME / #undef NAME / #endif ⇒ 之后它一定不是宏
```

**定理是对的，所以它不是猜**：`#ifndef NAME` 的条件**就是**"NAME 还没定义"，这正是它和别的 `#if` 的区别。它被记在**事实层**（每个 `#define` 一个布尔字段，由本文件自己的指令算出——头文件怎么变都不会让它过期，这是"事实"那条不变量的判据），而**只有引用查询读它**：定义查询问的是"哪一条 `#define` 在生效"，那确实仍然有条件——两个问题，两个答案。

**量到的**（同一台机器、同一个 454 文件的闭包）：闭包里 **333 个宏名**有"定得住"的定义；其中有引用的 100 个一共给出 **2 626 条"使用"**、只剩 **417 条"可能"**：

```text
_HRESULT_TYPEDEF_                     1394 uses,  41 still uncertain
__mingw_ovr                            263 uses,   0
WSABASEERR                             178 uses,   0
__MINGW_ATTRIB_DEPRECATED_SEC_WARN      123 uses,   0
```

**而探针里那四个宏一个都没被救到，原因也量出来了**：定义它们的文件**解析不干净**（`winnt.h` 417 条错），而错的代价是**指令丢了八条 `#endif`**——`scan_directives` 只认语法树里的 `PreprocessorDirective` 节点（这是刻意的：哪些 `#` 是指令已经由 parser 决定，重猜就是第二份实现）。嵌套一旦不平衡，这条规则读到的父子链就不是文件的父子链，而**偏短的方向会让它多认一个"定得住"**。所以有一条安全网：**指令不配平的文件，一条都不认**（`#endif` 对不上任何 `#if`，或者文件结束时还有没关的区域）。量出来它挡掉了 184 条本来会认的——**那 184 条正是错答案**。

### 条件求值：摘要存**问题**，答案在查询时给

上面那条定理回答的是"这个名字**是不是**宏"；它故意不回答"**哪个分支**被取到了"，因为那需要宏环境。这一节是后者——`#if` 到底成不成立——而它的形状是本文档三条不变量的直接推论：

```text
摘要里存什么   每个条件区间：分支链（kind + 条件文本）、每个分支守卫的正文范围、外层区间编号（parent）
                `SummaryGuards { regions, conditionals }`，`CODEC_VERSION` 11
查询时算什么   把条件文本用**同一个 CppLexer** 读回 token，`parse_condition` + `eval`，得到
                `Visibility::{Active, Inactive, Unknown}`
谁来提供环境   `ProjectIndex::macros`（一个 `Marked`）：编译器 `-dM` 预定义的 483 个名字 + 编译数据库的
                `-D`/`-U` + 被问文件在该点之上的**无条件** `#define`
```

**为什么不把答案存进摘要**：条件成不成立取决于**怎么编译**（`-std=` 决定 `__cplusplus` 的值），而摘要的键只由文字和路径算出。存答案等于把 `-D` 塞进键里，也就取消了"先查盘、后解析"——这正是第 3 个键错误（宏环境进键）教过的那一课。所以存的是**问题**，答案是查询期的、用完即弃的。

**这一层真正新增的概念是"答案的强度"**（`condition::Lookup`）：

```text
Defined(&MacroDef)       定义了，而且拿得到 body（编译器预定义 / 命令行）
DefinedWithoutAValue     确定是宏，但 body 不在手上（摘要只存事实不存 body）→ `#if NAME` 是 Unknown
Undefined                确定没定义（本文件无条件 `#undef` 过，或 `-U`）
Unanswered               这张表**说不出** —— 既不是 0，也不是 false
```

`Unanswered` 不是锦上添花，它是**一个已修的错误**：标准的"未定义标识符是 `0`"是对**完整输入**说的，而索引读过的永远只是全集的一部分。在它出现之前，`#ifdef FOO` 有一个 `is_unknown` 特判（`Marked` 里），而 `#if defined(FOO)` 与 `#if FOO` 会把"我不知道"静默读成 `0`——**同一件事的两种拼写，一个谨慎一个闯祸**。现在三种拼写共用一条规则：`defined` 只看 `is_defined()`，标识符只看 body 拿不拿得到。

**判据（哪一格算"知道"）**：一个名字只要来自（编译器预定义 ∪ 命令行 ∪ 本文件该点之上的无条件 `#define` ∪ 该点之上的无条件 `#undef`）就算知道；不在其中就是 `Unanswered`。**头文件定义的宏一律不知道**，因为"闭包里没有"不等于"没定义"——闭包里有未解析的 include、有没索引的文件、有没人告诉我们的 `-D`。`NT_INCLUDED` 正是这一格：它不在任何地方，所以 `#ifndef NT_INCLUDED` 是 `Unknown`，include 照旧带疑跟进，而不是被当成"没定义"跳过。

**两个方向都用得上，而且方向不同**：`Active` 让一条路径不再带疑（`path_conditional = false`，因此后面的引用从"可能"变成"确定"）；`Inactive` 让**一个 include 整条不跟进**，也让**被它包住的 `#define` 直接不进候选集**（`#if 0` 后面的东西不在翻译单元里，一个编译器根本不会读它——所以它既不是"可能"也不是"确定"，而是不存在）。`Unknown` 保持这一层出现之前的行为——这就是为什么它能一次落地而不需要重写任何查询。

**量到的**（459 个文件的闭包，`examples/condition_reach.rs`）：**486 个条件 include 里 85 个被判定**（24 个 `Active`、61 个 `Inactive`），其余 401 个 `Unknown`；按名字来源分，254 个名字测试里 26 个靠编译器预定义、97 个靠闭包自己的定义（这一格今天**还答不了**，见下）、131 个两头都没有。

### 闭包自己的宏：按翻译顺序边走边喂

上面那 85 个全部来自"编译器预定义 ∪ 命令行"——**头文件自己写的 `#define` 一个都没用上**，而 `_GLIBCXX_USE_CXX11_ABI`、`_GLIBCXX_USE_DUAL_ABI` 这类 feature 宏恰恰是标准库条件的全部内容。补上它的机器就是同一个 walk（`ProjectIndex::macro_candidates`），只多了三件事：

```text
1  文件的事实与 include 合成**一条按偏移排序的流**，边走边把事实喂进状态
   一个 #define 只有走到它之后才在状态里，一个 include 只有走到它才展开——这就是翻译顺序
2  每条事实只喂**确定的**东西：
     整个路径无条件 且 事实所在区间取到        → 名字 + 值（MacroFact::value：一个整数字面量）
     区间说不清但 settles_the_name            → 只喂"是宏"，值不喂（两个分支定义的值可以不同）
     其它（区间 Unknown、或路径本身带疑）      → 这个名字进 Marked::uncertain：之后问它就是 Unknown
3  文件自己的 include guard **不是条件**：SummaryGuards::own_guard 记下它开的区间，链上跳过它
```

第 2 条那个"不确定"集合（`Marked::uncertain`）是这一轮的关键：`#ifdef SETTING / #define WIDE 1 / #endif` 之后的 `#if WIDE == 1` **不能**因为"状态里没有 WIDE"就答 `0`——它得答 `Unknown`，因为那个分支没人能判。粗粒度地给整份状态打上"不完整"会把所有后续条件一起废掉，按名字记才既安全又有用。

第 3 条是被实测逼出来的：`bits/c++config.h` 的第一条指令是它自己的守卫，`#define _GLIBCXX_USE_CXX11_ABI 1` 嵌在 `#if __cplusplus` 里、`#if __cplusplus` 又嵌在守卫里。链上带着守卫求值时，守卫的名字**已经**被它自己的 `#define` 定义了，于是 `#ifndef <守卫>` 读成 false ⇒ 整份文件"取不到" ⇒ `_GLIBCXX_USE_CXX11_ABI` 求值成 `0`（实测：`string:71` 的 `#if __cplusplus >= 201703L && _GLIBCXX_USE_CXX11_ABI` 被读成"不取"，而正确答案是取）。

**量到的**（同一台机器、同一个 459 文件闭包）：**486 个条件 include 里 188 个被判定**（127 取到、61 不取、298 Unknown）——比上一节多 103 个，而且**一个否定结论都没用上**：每一格都只依赖"某个文件确实定义了它"或"编译器确实预定义了它"。

**"输入完整吗"这一格还没有打开**，而这一轮量清了打开它意味着什么：

```text
把环境声明成"这就是这次编译的全部定义"（读到 compile_commands.json 时才敢这么说）
  同一个闭包：486 里 **440 个**被判定（332 取到、108 不取、46 Unknown——剩下的几乎全是 __has_include）
  代价：__attribute__ 767 条、STDMETHODCALLTYPE 4 078 条"可能"变成"不是引用"
```

那两条不是判定变强，是**路径被切断了**，原因定位到一行：`minwindef.h` 在 **2594** 处包含 `winnt.h`（条件 Unknown），`windef.h` 在 **366** 处也包含它（条件 Active），而 walk 里**一个文件只走一次**——第一次是带疑的那条，第二次（确定的）被 `visited` 挡掉，于是 `winnt.h` 的宏全部"不确定"，定义不再是候选。这与"一次查询走一遍 include 图"那一节记过的 `visible_files` 旧 bug 是同一类（先被条件路径找到的文件不会再被无条件路径改善），当时的修法是"更好的答案赢"；这里要做的是同一件事：**`visited` 要记住"是怎么进来的"，确定路径要能改写带疑的那次访问**。在它能改写之前，这个强声明会把诚实的疑问变成错答案，所以 `Session` 现在**不**声明它（`configured = false`，理由写在那一行旁边）。

**风险写在明处**：判定用的是**配置**。`Session::open` 从编译数据库取 `-std=`/`-D`，没有数据库时用编译器的默认（本机 g++ 15 = C++17）。用 `-std=c++20` 构建却没有数据库的项目会被按 C++17 读，`>= 202002L` 的块会被判成"不取"而跳过——**配置的错，以"少了声明"的形式出现**，所以这一句同时写在 `std-library.md` 第十五轮和 `Session` 的配置来源旁边。

### 位置化的宏，第二个消费者：**parser**（B81，parser 侧已落地）

上面那一节的流是给**条件求值**用的。同一个流还有第二个消费者，而它一直是缺的：**parser**。

原因写在 `roadmap.md` §2.0 的开头——**一张无位置的宏表是负收益**（干净 80 → 43，消息 941 → 1081，46 个文件变脏）："某个头文件定义了这个名字"被读成"**这里**这个名字是宏"，而 `_GLIBCXX_BEGIN_NAMESPACE_VERSION` 在一个位置是 `namespace __8 {`、在另一个位置什么都没有。**一个名字的形态不是这个名字的属性**，是它在翻译顺序中那个位置的属性。

现在 parser 侧接上了这个流的**形状**，也就是把"位置"这件事变成了类型：

```rust
/// 某个 `#include` 带进来的宏，从它自己的偏移起生效。
pub struct IncludedMacro {
    pub from_offset: usize,       // 这条 `#include` 结束的位置
    pub name: Box<str>,
    pub definition: Option<SymbolKind>,   // `None` = 从这里起 `#undef`
}

/// 一个文件的包含贡献的全部宏，按偏移查。
pub struct MacroEnvironment { /* name -> [(offset, definition)] 有序 */ }
impl MacroEnvironment {
    pub fn from_included_macros(entries: impl IntoIterator<Item = IncludedMacro>) -> Self;
    pub fn kind_of(&self, name: &str, offset: usize) -> Option<SymbolKind>;  // 二分，O(log n)
}
```

`ParserConfig::with_macros_from_includes(&env)` 把它交给 parser，而 `macro_evidence` 的证据次序变成：

```text
1  本文件自己的 `#define`          —— 就在被解析的文字里，最新鲜
2  包含在**这个偏移**上贡献的宏     —— 位置化，唯一能说"这里"的那种
3  调用方的平面表                  —— 留给已经有表的调用方
4  没有证据                        —— 退回形状偏好
```

第 2 条的**否定答案也算答案**：包含说"这个名字在这里不是宏"（或一条 `#undef` 把它拿走了）时，不再去问平面表——否则 Plane 表会把一个已经被位置证据否掉的名字重新说成宏。

**现在做到了哪一步**（写清楚，免得下一轮重新猜）：

```text
✔ parser 侧：IncludedMacro / MacroEnvironment / ParserConfig::with_macros_from_includes
✔ 证据次序、按偏移生效、`#undef` 撤销、乱序输入自行排序  —— 单元测试
✔ 端到端：`BOOL_OPTION(flag)` 在证据生效时读成 `MacroCall`（无诊断），
  把 `#include` 写在调用**之后**时读法退回"漏了 `;`"（有诊断）—— tests/symbols.rs
✔ seeds 的计算：`macros_from_direct_includes`（直接包含、取 `#include` 的偏移、只取无条件事实、带 `#undef`）
✔ 语料实测（探针 `--seeds`）：**35 510 条 seeds、257 个文件 —— 干净 433 / 报错 22 / 消息 95 一条没动**
```

**那次实测的结论是"没动"，而它比一次"动了"更值钱**，因为两件事同时被量了出来：

1. **仪器先说清自己**：探针现在打印 `positional macro evidence: N seeds over M files`。第一版用的是便利函数
   `summarize`（内部是 `NoFiles`，**一个 include 都不解析**），于是 seeds 恒为 0、两次普查逐字相同——
   "没效果"和"没接线"在输出上无法区分。这一行就是为那次沉默加的。
2. **"有证据"会**压掉**那条没有证据的形状规则**：`at_a_macro_call_begins_the_declaration`（B73）明确要求
   `macro_evidence(...).is_none()`，因为"文件自己 `#define` 过"或"调用方的表有描述"时应当走有体的那条路。
   把 35 510 条证据铺上去之后，剩下那 22 个文件里恰好有几条（`STDMETHOD`、`_GLIBCXX_NOEXCEPT_PARM`、
   `_GLIBCXX_MATH_NS`）**从形状规则手里被拿走**，而证据给的形态（多半是 `Unknown`，有些还是"同一个名字两种形态"）
   并没有替上。这正是 `macro_shape` 探针量的那 168 个"一个名字多种形态"的名字。

**形态分布量出来了，而它把问题钉死在一个地方：**

```text
positional macro evidence: 35079 seeds over 249 files
seed shapes: Unknown 27925 (80%) | Expression 2295 | Block 47 | Specifier 20 | Statement 14 | Type 1
```

**80% 的证据只说"这个名字是宏"，一个字都没说"它能站在哪"。** 而 parser 里**读形态的地方只有两处**
（`may_be_a_statement_without_a_semicolon` 与"能否独立成一个成员"），两处都只认 `Statement`/`Block`——整个语料里
这样的 seeds 一共 **61 条（0.17%）**。也就是说：证据**到达了、按位置生效了，而它说的话不是任何规则要听的话**。

**两个假设都被量过、都被否掉**（这是这一轮真正的产出）：

```text
假设 1  "证据压掉了形状规则"    把 `at_a_macro_call_begins_the_declaration` 的门槛从"有证据"改成
                              "证据带形态"（`Unknown` 不算）→ 带 seeds 的普查仍是 433 / 22 / 95
                              → **否掉**，改动已撤回（不凭信念保留）
假设 2  "形态推断不够细"        80% 是 Unknown，可 `Specifier`/`Type`/`Expression` 这些**没有任何消费者**，
                              推断得再细也不会有读数变化 → **否掉**
```

**结论：缺的不是证据，也不是形态的名字，而是"形态 → 规则"的这一段。** 剩下那 22 个文件需要的形态，按首错行归类，
没有一个落在现有六个变体里：

```text
_GLIBCXX_NOEXCEPT_PARM      形参表的一个**片段**（`, noexcept`）
STDMETHOD(method)           声明符的头（`virtual HRESULT STDMETHODCALLTYPE method`——名字在实参里）
_GLIBCXX_MATH_NS            一个**命名空间名**（`std::__math`），用在 `::` 左边
STDAPICALLTYPE *            调用约定 + 指针声明符（`typedef HRESULT (STDAPICALLTYPE *LPFN…) (…)`）
__attribute((dllimport))    属性（现有的 `Specifier` 只覆盖 `__declspec(...)` 的拼写）
```

这一族要真的买下来，是**新变体 + 消费它们的规则**，或者干脆是**按位置的展开**（把体的 token 真的代入）——
也就是 `roadmap.md` §2.0 一开始就写下的那句"展开是有界的第二件事、且必须是按位置的"。现在这句话有了**账单**：
5 种形态、约 8–10 个文件，而位置化的管道（B81/B82）已经在手。

seeds 的来源不是新东西：`ProjectIndex` 已经在按翻译顺序走"文件的事实 + include"合成流（见上一节），第 2 步只是把同一个 walk 的输出再喂一个消费者。
### 展开：按位置、按调用点、**有来源**（B84 起）

位置化证据（B81/B82）把"这个宏在这个偏移上是什么"接通了，B83 又量出它的天花板：**80% 的条目形态是 `Unknown`，
而 parser 只在一个地方读形态，且只认 `Statement`/`Block`**（全语料 61 条）。缺的不是证据也不是形态的名字，而是
**"形态 → 规则"那一段**——换句话说，**要把宏体真正展开出来读**。

好消息是：**展开机已经在仓库里**，只是从来没接到 parser 上：

```text
preprocess::macros::{MacroDef, MacroBody{tokens, stringize, paste}, Parameter}   ← 展开需要的形式
preprocess::expand::{expand, expand_with_budget, substitute}                     ← 带预算的展开器
preprocess::expand_range / expand_node / expand_line_at                          ← 现在只服务语义查询
MacroFact{ name, function_like, body, value, range, guard }                      ← 每个文件的事实
MacroEnvironment{ kind_of, body_text_of }                                        ← 按位置问（B81/B82/B84）
```

**设计：三层，各管一段，互不越界。**

```text
1  可见性（已做）     MacroEnvironment：某个名字在**这个偏移**上是不是宏、形态是什么、体是什么
2  展开（引擎已有）   expand(MacroDef, args) → token 流；参数代入、# / ##、预算与递归上限
3  读数（新的）       parser 在**调用点**问"它展开成什么"，然后**按那个构造读文件自己的 token**
```

第 3 层的关键决定，也是与 clang 分道扬镳的地方：**展开的 token 不进树**。parser 不构造"合成缓冲区"，而是把
展开结果当成**读法的证据**——体是 `namespace __8 {`，那么这次调用就按**命名空间头**读，花括号与后面的声明仍按
**文件自己的 token** 读进同一个 `NamespaceDef`；体是 `virtual HRESULT STDMETHODCALLTYPE method`，那么这次调用
按**声明符的头**读，声明符的名字取宏自己的实参。于是：

```text
✔ 无损不变：树里的每个 token 仍然是**这个文件**的 token，`to_source_text() == source` 照旧
✔ 事实的区间不变：`DeclFact` 的 range 仍指向用户写的那个名字（hover / 跳转都对）
✔ 容错不变：展开读不出来时，退回今天那条形状规则，再退回"宏调用"这个诚实的节点
✔ 递归与预算：展开器早有 `expand_with_budget`，展开结果**只用于一次决策**，不递归进树
✘ 不做的事：不展开 include（一次查询走一遍 include 图，见上文）、不把展开结果当源码、不改写 token
```

**为什么这是"预处理"而不是"又一条形状规则"**：形状规则是**猜**（`MACRO(args) name(…)` 看起来像声明），
展开是**读**（宏体里就写着 `namespace __8 {`）。B83 的账单上那五种形态——形参表片段、声明符的头、命名空间名、
调用约定 + 指针声明符、属性——每一种都能从体里读出来，而它们今天都只能靠猜或者读不出。

**"展开不进树"不等于"树不可用"，而代价必须算清（这一节是回答"是不是要两棵树"的）。**

先看一个具体的：`WINOLEAPI_(void) CoFreeLibrary (HINSTANCE hInst);`

```text
树里能表达的（全部是**文件自己的 token**）：
  Declaration
    DeclSpecifierSeq > MacroCall(NameExpr "WINOLEAPI_", ArgumentList "(void)")     ← 宏站在说明符的位置
    InitDeclarator > Declarator(NameExpr "CoFreeLibrary", ParameterList "(HINSTANCE hInst)")

树里表达不了的（展开才知道的）：
  这条声明的**类型**是 `EXTERN_C DECLSPEC_IMPORT HRESULT STDAPICALLTYPE`
  ⇒ 它属于**事实**，不属于语法：`DeclFact{ type_text: HRESULT, provenance: MacroBody{ file: combaseapi.h:35,
     invocation: objbase.h:96 } }`
```

于是分工是清楚的：**树负责"文件写下的形状"，事实负责"它实际上是什么"并带上来源。** 一个消费者问"这个函数的
返回类型是什么"，答案来自事实(带 provenance)；问"这个宏站在哪、它的实参是什么"，答案来自树。两边都不需要对方。
这不是妥协，正是这个仓库一开始就定的"事实，不是结论"。

**"两棵树"这条路要看清它到底贵在哪。** 唯一真正需要"展开后的树"的情形，是**宏体自己有语法要看**——而它的正确
粒度不是"每个文件一棵展开树"，而是**每个宏定义一棵**：

```text
✘ 按文件展开再解析    文本翻倍、区间失效(每个 offset 都要 origin map)、编辑/补全要映射回去、
                      一次 parse 的代价变成两次 —— 这正是 clang 的账，它付得起，因为它有 Sema 与
                      一整套 SourceManager；我们没有，也不该有
✔ 按定义懒解析        只有**真的被结构化使用**的宏才需要体树，几十个而不是三万两千个；
                      同一个定义的每次调用**共享**那一棵；缓存的键是"定义的位置"，与调用点无关
✔ 更省的一层          大多数决策根本不需要树——只需要**体的前几个 token**（`namespace` + 名字 + `{`、
                      `virtual` + …+ 名字、`,` + `noexcept`）。模式匹配 O(体长)、按定义缓存，
                      连一次 fragment parse 都不需要
```

**量到的（B85，第一个数——它决定方案是否成立）：**

```text
455 个文件 / 310k 行：37 357 次"这个名字是什么宏"的提问 | 最忙的文件 4 684 次
parse alone 2.86 s（与加计数器之前同量级）
```

提问数远小于 token 数（310k 行 ≈ 千万级 token），最忙的文件也只有 4 684 次；而**同一个宏的重复提问在展开时按
`(定义位置, 实参序列)` 记忆化**，所以真正要算的展开次数还要再降一个量级。计数器本身在
`CppParser::parse_with_audit` 的 `EventStreamAudit::{macro_questions, macro_question_names}` 里（两个
`Cell`/`RefCell` 计数，任何构建都开着），所以这个数随时可重测。
**代价模型（下一轮要量的东西，不是猜的）：**

```text
每次 parse 的额外工作 = Σ(需要展开的**决策点**) × O(体长)，按**定义**记忆化
  · 决策点很少：声明头、说明符序列、形参表、模板实参、命名空间头 —— 每个文件几十个量级
  · 记忆化的键是 (定义位置, 实参 token 序列)，所以同一个宏用一百次只算一次（实参不同才算新的）
```

### 成员访问：第一个需要**类型**的查询

`index::project::member_across_files` 回答 `widget.size` 里的 `size` 指向哪条声明。它不是"在作用域里找 `size`"——是**在 `widget` 的类型里找 `size`**。三步，每一步都已经存在：

```text
1. 读出形状        —— 对象表达式 + 成员拼写（sema::resolve::member_access_at）
2. 推断对象的类型  —— 它的声明的 type_of，先问本文件，再问索引
3. 在类型里找成员  —— 按限定名 `<类型>::<成员>` 查，索引本来就能匹配限定名
```

**第 3 步是它便宜的原因**：声明事实本来就记着所在作用域的限定拼写，所以"`Widget::size`"是既有查询能回答的问题。新增的只有第 2 步，而这是 `infer` 层的开头，刻意很窄：**对象必须是一个名字**。

为了让第 2 步有可能，声明事实第一次带上了"它声明的是什么类型"（`DeclFact.type_of`，`CODEC_VERSION` 5）。三个限制都是刻意的，写在字段文档里：**存拼写不存解析结果**（`ns::Widget`、`std::vector<int>` 原样存，消费者用既有的限定名机制去解析，解析不了就是 `Unknown`）；**只对变量/字段/参数**（类*是*一个类型、函数*返回*一个类型，那是语法的另一个部位）；**声明修饰符剥掉**（`static const Widget` 记成 `Widget`，而 `unsigned long` 保留——那几个词就是类型）。

类型名字的规范化（`base_type_name`）也在文档里写清了它拿掉了什么：模板实参（`std::vector<int>` → `std::vector`，主模板的成员就是最有用且无需实例化的答案）、尾部的 `*`/`&`、以及 `struct`/`class` 这类 elaborated 关键字。`unsigned long` 不动：那里的词就是类型，而且它不指向任何类。

**四个答案**：`Yes(成员)` / `Unknown(UnknownType)`（对象不是名字、对象找不到、或者类型拼写解析不到东西——**新加的 `UnknownReason`**,因为对这一条的处置和"名字缺失"完全不同：不该报"未知成员"，而是"这个形状的类型还推不出来"）/ `Unknown(NotDeclaredHere)`（类型知道、成员不在里面——仍不是确定否定：可能是基类、模板、或没人索引的头文件）/ `Unknown(UnparsableName)`（游标不在成员访问上）。

**基类成员的查找按层进行**：先看类自己，再看直接基类，再看它们的基类……**第一个有答案的层决定结果**——类自己的成员遮蔽基类的，近的基类遮蔽远的，这就是 C++ 的规则。同一层里有两条就是 `Unknown(Ambiguous)`（菱形继承的两边都声明了这个名字），**报歧义而不是挑一个**：挑一个就是跳到用户分辨不出的另一个实体上。基类拼写来自 `DeclFact.bases`（`class D : public B` → `["B"]`；访问修饰符和 `virtual` 不在里面——它们决定一个成员**能不能到达**，那是语义而不是文本事实，要它们就得要整套语义）。环靠 visited 集合终止：手误的文件写得出环，而挂死比答错更糟。

**类型推断是递归的，因为表达式就是递归的**。核心是 `type_of_expression`，它认识的形状目前有四种：

```text
一个名字      `widget`       → 它的声明的 type_of（先问本文件，再问索引）
`this`        `this->size`   → 包住它的那个类的作用域，不需要任何推断
一个调用      `make()`       → 被调用者的声明的 returns，或者它声明的那个类（`Widget()` 是临时量）
一个成员访问  `a.b`          → 递归：在 `a` 的类型里找到 `b`，读 `b` 自己的 type_of
```

第三种让 `a.b.size` 通了——内层访问用**同一个查询**定型，外层再问内层"你是什么"。`this` 是其中最便宜的一格：作用域链本来就知道当前是哪个类（嵌套类里取最近的那个，有测试钉住），所以它一格推断都不需要。

**调用那一格是这一轮加的，而它有两种答案，因为 C++ 有两种**：`make()` 有 `make` 返回的东西，而 `Widget()` 是 `Widget` 的一个**临时量**——token 完全一样，只有声明能把函数和类分开。三种被调用者各走既有的查找：一个名字（`make`、`ns::make`）走名字查询，一个成员访问（`fac.build`）走成员查找，一个类名（`Widget`）是同一次查找的另一半答案。查询之前还有一步是**这一轮才抽出来的**：`declaration_of_expression` 把"这个表达式指的是哪条声明"在两层之间调和一次（缓冲区给 `Binding`、索引给 `DeclFact`），否则同一句话会长出两套规则。解引用 `(*p).size` 与下标 `arr[i].size` 是**同一层里的算术**（`*` 去掉一个指针运算符、下标去掉最后一对方括号，都不是查找），`&x` 是前者的另一个方向；剩下的一律是 `UnknownType` 并带上表达式拼写：算术表达式、**类**的下标（要实例化模板）、以及**推导出来的 `auto`**（`auto make() { … }` 记 `None`，因为"文件没说"才是真话）。

**失败原因会原样传上去，而不是压平成 `UnknownType`**：`a.nope.size` 报的是 `NotDeclaredHere("Outer::nope")`——"`Outer` 里没有 `nope`"直接告诉消费者该改什么，而"`a.nope` 的类型未知"只说了有问题。（这条测试的第一版期望就是压平后的答案：实现比期望更对。）

**已知的窄边界**（都有测试钉住，答案都是 `Unknown` 而不是猜）：算术表达式的类型、`auto` 推导的调用结果、**类类型**的下标（`v[0]`——它要实例化模板，见 `element_type_name`）；基类成员、模板参数的成员、运算符重载。还有一条**不是**这一层的边界但在这里会撞上：`type_of`/`returns` 存的是**拼写**，而写的是 `std::string` 时那个拼写是一个 **typedef**——成员查找是按名字找类，不跟着 typedef 走到 `basic_string`，所以 `s.substr(1).size` 报的是 `NotDeclaredHere("std::string::substr")`。这是"存拼写不存解析结果"的代价，记账在这里而不是藏起来。

**一处结构上的发现值得记**：parser 把 `w.size` 读成 **`IndexExpr`**（和 `arr[0]` 同一种节点，只是括号换成了 `.`），而不是 `MemberExpr`。所以"这是不是成员访问"必须看**运算符**，不能看节点种类——形状读取函数因此按 `.`/`->` 的文本判断，并同时接受三种节点。`a.b` 上的游标在 `a` 上时**不是**成员访问（那问的是 `a` 这个名字，是名字查询的活），这一点由"标识符必须在运算符之后"来判。

### 成员列表：把基类链留到查询时

`index::project::members_of` 是成员访问的**列表形式**：那个问"`size` 在哪条声明"，这个只给一个类型、问"有哪些名字"。补全就是它。**顺序是答案的一部分**：类自己的成员在前，然后一层一层往外——这正是 C++ 遮蔽的顺序；同一层内按**名字**排。之所以要强加顺序而不是沿用它来的样子：本文件的 scope tree 里 binding 是**按名字排**的（`add_binding` 的二分查找要用），而索引里的事实是**按偏移排**的，不统一就会出现"同一个类在缓冲区里和在头文件里列出来不一样"。近层已经贡献过的名字在远层被丢掉——隐藏按**名字**而不是按签名，所以 `D::f(int)` 会遮住 `B::f(double)`。

**歧义不丢条目**：同一层两个基类都声明 `value` 时，两条都在列表里、都带 `ambiguous` 标记。单名字查询在那里报 `Unknown(Ambiguous)`（"跳到哪一条"没有答案），而列表回答的是"有哪些名字"，丢掉任何一条都是替用户选。**重载不算歧义**：算的是**不同的声明类**个数，不是声明条数，所以 `void f(); void f(int);` 是一个名字。

**列表从来不是一个完整性主张**。`MemberList.unlisted` 列出**走不进去的基类**和原因（没人声明的基类是 `NotDeclaredHere`，只经由守卫 `#include` 到达的是 `ConditionalCompilation`）——`unlisted` 为空是说"这一步走到的基类都读到了"，不是"编译器看到的就这些"。一个悄悄少了几项的补全列表就是这个字段存在的理由。为此 `bases_of` 从返回 `Vec` 改成了返回 `Known<Vec>`：**"这个类没有基类"和"这里没人说得出它继承什么"是两句不同的话**，而成员**查找**可以把两者当同一件事（够不到的基类两边都不贡献成员，继续往前走），成员**列表**不能。

**基类拼写要当名字用**：`public Base<int>` 找的是类 `Base`——模板实参说的是继承了哪个**类型**，不是哪些成员归谁声明；不实例化就等于"主模板写着的那些成员"，那也是唯一不需要实例化的答案。这一条顺带补掉了单名字查询里同样的洞：`bases_of` 以前把 `Base<int>` 原样拼进 `Base<int>::size`，谁都匹配不到（模板基类的成员一直查不到，有测试钉住了现在的结果）。

**已知的窄边界**（刻意的，不是漏）：不做访问检查（`private` 基类的成员照样列出来——访问不在事实里，见 `DeclFact.bases`）；不实例化模板；不处理 `using Base::f;` 与虚函数覆盖（前者不算"自己声明了一个成员"，这一层还没有这个模型）；**构造函数与无 `virtual` 的析构函数不在列表里**，因为作用域层根本没绑定它们（`grammar-gaps.md` 第 19 条，那里同时记着这一轮查出来的那个把**类名读成析构函数名**的静默 bug）。

### 补全：把游标接到成员列表上

`index::project::member_completions_at` 是**第三个需要类型的查询**，也是前两个（`member_across_files` 找单个成员、`members_of` 列成员）铺垫出来的那一个。三步全是既有的，所以它很短：

```text
1. 读形状   —— 对象表达式 + 成员已经写了多少（sema::resolve::member_access_at）
2. 推类型   —— type_of_expression，成员**查找**本来就在用的那套递归推断
3. 列成员   —— members_of，含基类声明的那部分
```

**它存在的那个状态是 `w.`**——运算符打完了、后面什么都没有。那一下按键**就是**提问，而 parser 把它读成"成员为空的成员访问"而不是别的构造（`~Widget();` 那种形状问题见 `grammar-gaps.md` 第 19 条），所以这里不需要第二个形状读取器，也不需要重解析这一行。`member_access_at` 因此把"成员还没写"当成一种**真实状态**返回：`member` 为空串，`member_range` 是紧贴运算符之后的一个**空区间**。同一个答案覆盖 `w.si`，区别只是区间盖住了已写的前缀。

**空区间是有意的，不是偷懒**："在一个点插入"和"替换一段前缀"是同一次编辑，用一个字段表达两件事，消费者就不必在"点还是段"上分支——而唯一会分错的那一次，恰好就是点后面那一下按键。同理，`prefix` 与 `member_range` 分工明确：**range 是被替换的（整个 `size`），prefix 是被匹配的（光标之前的部分）**。游标停在词中间时（`w.si|ze`）两者不一样，用同一个值做两件事的写法会在用户明明在打字的时候给出空列表，所以有一条测试专门钉这一格。

**定义查询与补全查询对同一个形状给不同答案**：`member_across_files` 拿到成员为空的访问时返回 `UnparsableName`——"跳转"需要有个东西可跳，而还没有名字可写。宽容放在形状读取器里，判断放在各自的查询里，这样只有一处知道 `w.` 长什么样。

**一个尚未修的上游问题，记在这里因为它影响体验**：`w.` 现在会报一个"expected identifier after member access operator"的错，而错误恢复**吃掉了当前块的 `}`**，于是这个函数之后、文件其余部分被并进了函数体（实测：`void f() { Widget w; w. } int after; void g() { }` 里 `int after;` 变成了局部声明）。补全在**那个游标处**照样工作（对象和运算符都在 `IndexExpr` 里，见上），但同一个文件里后续代码的作用域是错的。这是 parser 的恢复策略问题，不是查询的问题，已记进 `grammar-gaps.md`。

### 名字补全：游标不在成员访问上时

`index::project::name_completions_at` 是补全的另一半。`w.` 那一种是"一个类型的成员"，这一种是**名字**——而"什么名字能用"有四种位置，前三种问的是同一件事，第四种是它的链式版本：

```text
ns::         一个作用域：`ns` 里直接写的名字
Widget::     一个作用域，**加上基类**——基类声明的 typedef 通过派生类照样能写
::           只要全局名字空间：前导 `::` 问的就是这个
loc          没有限定符：从游标所在的作用域往外，每一层能用的名字
```

形状读取器是 `sema::resolve::name_position_at`，它回答的三件事和成员那一个刻意同形（`scope` / `written` / `range`）：`scope` 是**查找键**（`::` 保留，因为"全局名字空间"不是"没有限定符"），`written` 是被匹配的前缀，`range` 是被替换的区间——`ns::` 时它是紧贴 `::` 之后的**空区间**，与 `w.` 那一格的道理完全一样。`w.` 与 `ns::` 的分工写在读取器里而不是查询里：`IndexExpr` **不算**名字节点（那是成员访问的地盘），所以两种补全各自只有一个读者。

**两层在这里不是"二选一"，而是"按作用域的种类决定"**：

* **类**定义一次，成员只能来自一个地方：缓冲区的作用域树有就用它，没有就查索引（和 `direct_members` 同一条规则）；
* **namespace** 可以被每个文件重新打开，所以缓冲区的名字和头文件里的名字**都要**，同名的以缓冲区为准。`::` 也走这一条——被包含的头文件全都写在全局名字空间里；
* 于是 `#include "ns.h"` 之后再写 `namespace ns { int in_the_buffer; }`，`ns::` 补全能同时给出两边（有测试钉住）。

**它不会给出的东西，以及为什么必须是一个字段**：别的文件里的**局部**声明。索引是"一个文件有哪些声明"的列表，说不出一个局部属于哪个函数，所以名字查找在那里只能猜；而猜错的代价不是"少一个候选"而是"给一个用户看不见的名字"——标准库头文件里叫 `__first`、`n` 的局部声明有成千上万。这就是 `DeclFact.local`（`CODEC_VERSION` 8）存在的原因：`scope` 为 `None` 的声明有**两种**，文件作用域的（每个包含它的文件都能用）和函数体里的（外面谁也用不了），而事实里原本没有任何东西能把它们分开。加了它之后，跨文件的名字查找**跳过**局部声明（`definition_across_files` 也因此不再跳到别的文件的函数体里），而**本文件**的局部照常给出——那来自缓冲区自己的作用域树，是唯一知道它在哪个函数里的东西。

**实测**（`<vector>` + `<string>` 的闭包，308 个文件）：`std::vec` 给出 **488** 个名字，**3.3 ms**；`main` 里的裸名字给出 **1218** 个（局部 `result` 排在最前，其余是各头文件写在全局名字空间里的名字——真实 C++ 文件确实能看见它们，客户端按 `prefix` 过滤），**5.1 ms**。两个数字都要看得懂：数量大是语义如此，耗时可接受是这一轮修出来的（见下）。

### 一次查询走一遍 include 图，不是每个文件走一遍

上面那两个耗时在修之前是 **573 ms**（`std::vec` 那一个），而 573 ms 对一个"每次按键都问"的查询是不可用的。原因不在新查询里，而在它**第一个用到**的那条老路上：`visible_declarations` 对索引里**每一份摘要**调用一次 `visibility_of`，而后者每次都从查询文件开始重新走一遍 include 图。308 个文件 = 308 次广度优先搜索，只为回答一个问题。

修法是把它反过来：**图先走一遍**，得到"能看见哪些文件、各自是怎么被包含进来的"（`ProjectIndex::visible_files`），然后那一份列表被套用到所有摘要上。573 ms → 3.2 ms，答案一个字没变（有既有的可见性测试兜着）。顺带修掉一个此前没有被注意到的近似：旧的单目标版本用 `visited` 记住"第一次到达"，于是**先被条件包含找到的文件不会再被无条件路径改善**，而它的文档写的却是"两条路径都存在时报无条件"。新版本按"更好的答案赢"松弛，注释里写明了原因是菱形——每个头文件保护宏都会造出菱形。

**还剩下的那一半**：`visible_declarations` 仍然要遍历**所有**摘要的所有事实（308 个文件约一万条），在这一轮的量级上是几十微秒。一万个文件时它才是瓶颈，那时要的倒排表（名字 → 声明位置、作用域 → 声明位置）仍然是"下一步"里那一项，这一轮只是把"每个文件一次图搜索"这个更大的常数先拿掉了。

### 三个被测试抓出来的键错误

三个都是**看起来在工作的错答案**，都靠"重启后重新打开应该命中"这一类端到端断言暴露：

1. **占位键被原样存了下来。** `SummaryStore` 当初必须先建摘要才能算环境，于是给 `FileIndexer` 传了一个占位键 `SummaryKey::new(0, 0, 0)`；而 `FileIndexer` 把调用方的键**原样**存进摘要。结果整个项目每份摘要的 `content_hash` 都是 `0`——全项目共用一个缓存条目。缓存**看起来是好的**：一个文件写进去，一个文件读出来，命中率 100%。它回答的是另一个文件。修法是让 `FileIndexer::index_tree` 用**它手里那段文字**覆盖 `content_hash`。**症状的形态值得记住**：`let _ = source;` 这种"参数收下了但没用"就是它的气味。今天这个 bug 已经不可能发生——键在解析之前就算好了，没有占位键可传——但覆盖那一条留着，它是"谁更清楚这段文字"的答案。
2. **目录不在键里。** 摘要里存的不只是"文字说了什么"，还有它的 include **解析到了哪里**；而 `#include "shared.h"` 的解析结果取决于**文件自己的目录**。于是 `a.h` 和 `sub/b.h` 内容相同时共用一个条目，第二个文件拿到第一个文件的解析结果——一个跳到它根本没包含的头文件上的定义跳转。修法是把目录并进 `context_hash`，并把 `config_hash` 改名为 `context_hash`。
3. **宏环境在键里，而它不该在。** 它不是错的答案，而是**不可能命中的缓存**：要在查盘之前算它，就得先解析，于是每一次"命中"都已经付过解析的代价。修法是删掉它（连同 `MacroEnvironment`），键变成两个成分，`get` 变成"先查盘"。这一条被记在这里而不是当作"优化"，因为它推翻的是本文档自己写下的键的定义。

顺带定下的一条：**相对 `-I` 按 `working_directory` 解析后参与哈希**。这样"换个目录跑编译器但 `-I` 一个没变"仍然命中（命中率），"相对 `-I` 在不同工作目录下指向不同目录"则不会共用条目（正确性）。两个方向都有测试。

### 被删掉的东西：`key_for`

`SummaryStore::key_for(path, source)` 曾经回答"这段文字在磁盘上有没有现成摘要"。它**要么不健全、要么没用**，所以删了：

- 它只用**已经持有的**摘要算宏环境，所以当 `source` 与持有的文字不同时，它给出的键**不是 `get` 会给出的那个**——它的文档承诺（"`path` 以 `source` 为内容时会有的键"）根本无法兑现；
- 而当 `source` 与持有的文字相同时，那份摘要**已经在内存里了**，这个键什么也没多说。

能兑现这个承诺的只有 `get`——而且现在它兑现得很便宜：键在解析之前就能算出来，所以"这个文件现在该是什么键、盘上有没有"不再是一个需要单独 API 的问题。

## "全都做"的顺序（以及为什么）

按依赖排，不能跳：

1. **事实层**（summary + include 图 + 反向边）——其他一切的地基；
2. **名字解析**：作用域链、`using`/限定名、跨文件（include 图上的可见性）；
3. **类型与重载**：需要准确的声明集，因此依赖 1、2 的完整性；
4. **模板实例化**：需要前两者 + 精确预处理；这一步开始"出错的文件"会明显影响结果；
5. **ADL**：需要完整可见性模型。

每一层加的是**查询**，不是索引字段——这条与不变量 1 是同一条。每层都必须能降级：下层缺失时上层返回 `Unknown(reason)`，而不是返回一个低置信度的猜测（猜测只在**读法**层允许，那是 parser 的形状偏好，且已经被测试钉住）。

## 索引与 parser 的关系：先不接

`cpp_parser::SymbolTable` 接口已经存在，而且 **`impl SymbolTable for ScopeTree` 已经能跑**——parser 今天就能吃真实语义信息。但跨文件的那一半**故意还没接**，理由是接口的形状：

`kind_of(&str)` 是**无位置**的，而 `#include` 的可见性是**有位置**的：

```text
第 3 行:  g(1, 2);        // 此刻 g 只是个没见过的名字
第 12 行: #include <x.h>  // x.h 里声明了 void g(int, int);
```

把"闭包内所有名字的并集"喂给一张无位置的表，第 3 行的 `g(1,2)` 会被读成**声明**（按 `g` 是类型），而它其实是调用。表仍然只影响读法、不影响结构（`tests/symbols.rs` 钉住了这一点），但**读法是错的**——正是 A0 类问题。

三条路：

- **(a) TU 级并集**：零成本，对绝大多数真实代码正确，在上面那个形状上误读；
- **(b) 位置感知表**（`kind_of_at(name, offset)`）：正确，代价是每次查询一次区间/链查询。`preprocess` 已有同形的 `PositionalMacros`，模式是现成的；
- **(c) 只服务导航，不给 parser 喂跨文件结果**（当前选择）。

**选 (c) 的理由**：本项目最贵的资产是 **parser 读法的稳定性**——`grammar-gaps.md` 2800+ 行、69 个已修条目、36 条维护约定都是围绕"读法可解释、可钉住"积累的。跨文件表一旦接入，同一份源码会因索引状态不同而解析成不同形状，所有形状断言的语境都变了。而导航（跳定义、找引用、符号列表、补全）**根本不需要 parser 知道任何事**——它要的是"名字 → 声明 + 可见性"，是另一种数据结构。

**这个"等数据再定"的选择后来被实测钉死了**（`examples/macro_shape.rs`，两个语料）：把闭包里**所有**宏的形态做成一张无位置的表喂给 parser 重解析——

```text
128 个文件的闭包   干净 80 → 43，消息 941 → 1081，**变干净 0 个，变脏 37 个**
455 个文件的闭包   干净 335 → 290，消息 2551 → 4928，**变干净 1 个（find.h），变脏 46 个**
只喂"形态在闭包里无冲突"的名字也一样（80 → 43）：问题不是表不自洽，是**答案没有位置**
```

机制是探针点出来的：`bits/bit.h` 的 `_GLIBCXX_BEGIN_NAMESPACE_VERSION` / `_GLIBCXX_END_NAMESPACE_VERSION`
**就是** namespace 的开与关，而表一旦说"这个名字是宏"，`at_a_macro_member` 对 `Described { .. }` 一律回答"可以独立
成一个成员"（`grammar/cpp/decls.rs:3196`），namespace 嵌套就在 `} // namespace std` 处崩塌——正是上面那句
"A0 类问题"的形状，只是这次量到了代价。所以 **(a) 不做**；(b) 也只有在能回答"这个位置的值是什么"之后才谈得上，
而那种问法（"**这次调用**展开成什么"）已经不是一张表，是**带 origin 的展开片段**。

同一次测量还说明**剩下的份额大多不在宏上**：失败文件里首错行一个宏都没有的占 **79% / 63%**（例：
`alloc_traits.h:454 template<typename _Tp>`、`amxtileintrin.h:56 __asm__ volatile ("tilerelease" ::)`）。
所以这条线暂时放下，队列回到语法，展开只留有界的一格（形态 Unknown 的函数式宏当语句/声明片段：17% / 36%）。

## 先量四个数（再铺开）

1. 每文件摘要构建耗时；2. 1 万文件的常驻内存与缓存体积；3. 切分支后的缓存命中率（目标 >90%）；4. **`Unknown` 比例**（若大多数查询以 Unknown 结束，说明该回头改范围而不是加功能）。

第 3 个数现在才**真的**是"命中率"：宏环境在键里的时候，每次"命中"都已经付过解析的代价，`reused` 计的是写盘被省下的次数。今天 `reused` 数的就是被省下的解析次数，`hit_rate()` 的分母是"读过且需要回答的文件数"。

第 1 个数的第一次测量有工具了——`cargo run --release -p cpp_code_analysis --example measure -- [file.cpp] [轮数] [-I 目录]`，它用同一个文件量"建一次"和"命中一次"的比值（每次命中都新开一个 store，因为已经答过的 store 把摘要留在内存里，而重启要付的是查盘）：

| fixture | 构建 | 命中 | 倍数 |
|---|---|---|---|
| 合成单元，581 KB / 24000 条声明 / 2002 个宏 / 1 个 include | 376 ms | 3.4 ms | **111x** |
| 同上但 **100 个 include**（核对的开销就长在这里） | 429 ms | 5.9 ms | **73x** |
| `cpp_parser/tests/real_world.cpp`，3 KB / 31 条声明（另给 `-I` 让它能落盘） | 2.4 ms | 0.28 ms | 8.5x |

小文件那个倍数低是应该的：命中的代价是"读 + 解码一份摘要 + 逐条核对 `resolved`"，前两项跟摘要大小走、第三项跟 include 个数走；构建的代价跟解析工作量走。**100 个 include 让倍数从 111x 掉到 73x**，这就是那道核对的价钱：每个 include 大约 24 µs，也就是一次解析的 0.6%。这个价钱换来的是"监听层可以漏事件"。

顺带一个副产品：这个例子在 fixture 的 include 解析不出来时会**明说"这个文件不会被缓存"并列出没解析到的头文件**，而不是报一个 0% 的命中率——那条规则值得让用的人看见。

## 下一步：宏、标准库、语义索引与语义查询

索引与驱动层的骨架已经能跑（事实层 + 缓存 + 顺序 + 事件响应 + **会话** + **找引用**，996 个测试）。**从这一轮起重心转向语义**：不再在文件系统/进程/监听这些事情上消耗，因为语言服务器由客户端通知，那些事情没有真正的消费者。已经拿下的语义查询：名字（含限定名）、宏（位置化与**找引用/重命名**）、成员访问（第一个需要类型的查询，而"类型"现在包括**调用**：`f().size` 靠 `DeclFact.returns`、**解引用与下标**：`(*p).size`/`arr[0].empty` 靠 `type_of_expression` 的两格）、成员列表、**成员补全与名字补全**（游标 → 类型/作用域 → 列表）；环境发现这一层落了工具链搜索路径（[`std-library.md`](std-library.md) 的 P0），可信度这一层落了 `DeclFact::clean`（每条声明回答"这条读得干不干净"，见上面的不变量 3），跨文件可见性把"每个文件一次图搜索"改成了"一次查询一遍图"（573 ms → 3.2 ms，见上面那一节），而**驱动层**（`session::Session`）把它们串成了"一个开着的项目"——开项目、收通知、惰性索引、按光标回答，见上面"会话层"那一节。

按依赖排，接下来要做的：

1. **宏（已开始）**：`macro_across_files` 落地之后，同一个位置化模型直接长出了另外三个查询，都不需要类型系统：

3. **成员访问与类型推断（`infer` 层，已开始）**：`member_across_files` + `DeclFact.type_of` 让 `widget.size`、`p->size`、`ns::Widget` 的对象、跨头文件的类都能解析，共用限定名那套查询；`type_of_expression` 是**递归**的，所以 `this->member` 和嵌套的 `a.b.size` 也通了；`DeclFact.bases` 让**基类成员**按层查找（含歧义与环）。**成员列表 `members_of`**（基类链在查询时走、不物化）与**补全入口 `member_completions_at`**（游标 → 类型 → 列表）都已落地。接下来按"能答的边界"往外推：

外加一条只与 parser 有关的：`crates/cpp_parser/tests/real_world.cpp` 必须 **0 error**（它被 `tests/ast.rs` 与 `tests/doc.rs` 读进去断言）。改了 parser 的读法，先跑 `cargo run -p cpp_parser --bin cpp_dump -- <文件>` 把树打出来看，别猜形状——**文件有错时加 `--tree`**，否则它只打诊断；排查缺规则要问的正是"这个构造被读成了什么节点"。

### 五条不能破的约定

1. **`Unknown` 是一等答案，而且要说清为什么。** 任何"我不知道"都必须带上 `UnknownReason`，不能猜一个最近的答案。新增一种"不知道"就新增一个 reason——`UndefinedHere`、`UnknownType` 都是这么做出来的。判据是：**消费者对不同的 reason 处置不同**（不该把"宏被 `#undef` 了"报成"未知宏"），否则说明你加错了。
2. **事实存拼写，不存结论。** `DeclFact.scope`/`type_of`/`bases`、`IncludeFact.resolved`、`FileSummary.path` 存的都是**文字里写着的东西**；没有一个 `FileId`、没有一个解析后的类型、没有一个已实例化的模板。理由是可增量性（见"三条不变量"）。**要往事实里加字段之前先问**：这个字段在头文件被改之后会失效吗？会，就不是事实。
3. **键（`SummaryKey`）的每个成分都必须能从文字和路径算出来。** 这是"先查盘、后解析"的前提，也是宏环境被删掉的原因。往键里加任何需要先解析才知道的东西，就等于取消了磁盘缓存的意义（`cache.rs` 的模块文档记着这次教训）。
4. **改了 schema 就抬版本号。** 加字段 → `CODEC_VERSION`（字节格式变了）；**答案会变错** → 也抬 `FORMAT_VERSION`（它在键里，会让整库作废）；只是让旧条目取不到（比如键少一个成分）→ 只抬 `CODEC_VERSION`。两个常量旁边都写着为什么。
5. **文档是规范，同一次改动里更新。** `docs/index-design.md`（索引/语义层的决策与不变量）、`docs/grammar-gaps.md`（parser 的读法、缺漏与维护约定）。**下游按上游形状写的判据要在 grammar-gaps 里留痕**（第 18 条就是这么来的：`w.size` 读成 `IndexExpr`）。

### 一条很好用的工作方式：把测试写成"能力落地那天会失败"

这个仓库里已经有两条这样的测试，都如期失败过，改动因此都是**有意的**：

- `a_qualified_name_from_outside_its_namespace_is_unknown_rather_than_wrong` ——限定名落地那天失败，改成断言正确行为；
- `a_nested_member_access_asks_about_the_last_name` ——递归推断落地那天失败，同上。

给一个还答不了的问题写测试时，**断言当前边界并写明"这是在等什么"**，比不写测试好得多：下一个接手的人会知道边界在哪，而且能力一旦落地，测试会自己找上门。反过来，**不要**为了让测试通过而把边界写死成永远的行为。

### 两条曾经踩过的坑（读代码时会看到痕迹）

- **`Binding.range` 是 declarator，不是整条声明**（`Widget w;` 里只有 `w`）。任何"名字之前的文本就是类型"的写法都会静默地得到空字符串。要类型就**从根往下走到声明处，取 `DeclSpecifierSeq`**（`declared_type_of`）。
- **`FileIndexer` 只给 parser 喂 `ParserConfig::default()`**：`-D`/`-std` 不参与解析，所以摘要与宏环境无关（这就是键里没有宏环境的原因）。哪天要把 `-D` 喂进去，**键里必须同时把宏环境加回来**，并且抬 `FORMAT_VERSION`——`cache.rs` 与"第三个被测试抓出来的键错误"都记着。
