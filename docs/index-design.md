# 索引与语义层的设计（规范）

本文档记录**已经拍板的决策**与**不变量**。它约束 `cpp_code_analysis` 之后的所有工作：写代码时如果与这里冲突，先改这里并说明理由。

## 已定的三件事

| 决策 | 内容 |
|---|---|
| 缓存位置 | **项目内 `.cppls/`**（以后做成可配置项；默认放项目内，便于调试、CI、以及"和仓库一起删"） |
| 索引粒度 | **按文件**（per-file summary），不是按目录、不是按编译单元 |
| 目标范围 | **做完整的语言服务器**：语义推断（名字解析、类型、重载、模板、ADL）最终都要做 |

## 架构分层

```text
cpp_parser      语法：无损 CST、指令节点、宏表（#define 名字）、外部符号表接口
cpp_code_analysis
  preprocess    展开与条件：直接量/宏、guard 三态、Origin、预算
  summary       每文件事实：声明、宏、include、guard、模块   ← 落盘的单位
  resolve       按需查询：名字 → 声明（over include 图与 guard）
  infer         语义推断：类型、重载、模板实例化、ADL        ← 全部在查询时做
```

实际落地的模块名（`summary` 拆成了三层，因为三件事的输入不同）：

| 模块 | 职责 |
|---|---|
| `summary` | **只在数据形状**：`FileSummary` / `DeclFact` / `MacroFact` / `IncludeFact` / `FactGuard` |
| `sema::declarations` | **生产者**：从 scope 树 + 预处理状态产出 `DeclFact`（唯一同时看得到两者的地方） |
| `index` | **粘合**：`FileIndexer` 把 parse → preprocess → scopes → facts 汇成 `FileSummary`；`write_summary`/`read_summary` 落盘 |
| `summary_codec` | **字节格式**：手写编解码，magic + `CODEC_VERSION` |
| `sema::resolve` | **查询**：第一个不生产数据、只回答问题的模块——游标处的名字 → 声明（单文件） |
| `index::project` | **跨文件查询**：`ProjectIndex` 装摘要 + 派生反向边 + 可见性走查；`definition_across_files` 是组合两层的入口 |
| `index::store` | **驱动**：`SummaryStore` 决定"什么时候建、什么时候复用、变了以后哪些要重建"——唯一碰文件系统的索引层 |
| `index::worklist` | **顺序**：`Worklist` 决定"先索引哪个文件"——打开的文件 → 它的 include 闭包 → 其余；一步一个文件，调用方决定节奏 |
| `cache` | 键与路径 |

## 查询：从单文件到跨文件

单文件那一层（`sema::resolve::definition_at`）问的是"这个名字在本文件里指向哪条声明"，做不到时返回 `Unknown(NotDeclaredHere(名字))`——**那个原因就是跨文件层的入口**：它说的是"名字在别的文件里"，而不是"这个名字不存在"。

`index::project::definition_across_files` 把两层按 C++ 的解析顺序组合起来，**顺序就是正确性**：

```text
1. 本文件的作用域      —— 局部遮蔽头文件里的声明，永远
2. 本文件自己的顶层声明 —— 写在这里的声明不是头文件那条
3. 它 include 的头文件  —— 沿 include 图可达的那些
```

只有 `NotDeclaredHere` 会走到第 3 步；`Ambiguous` **不会**——那说的是"名字就在这里，而且不止一条"，去头文件里找是回答另一个问题。

跨文件查表要过三道判据：

1. **可见性**：声明所在文件必须从查询文件出发**沿 include 图可达**。项目里有 `Widget` 不等于这个文件能看见 `Widget`。
2. **限定名优先**：`a::Widget` 先按限定名匹配，再退到裸名——限定拼写是一个强得多的主张，不该被项目里任何一个 `Widget` 稀释。
3. **条件性**：路径上只要有一步 `#include` 落在 `#if` 里，答案就是 `Unknown(ConditionalCompilation)`，因为走没走那条分支取决于索引没有的宏。有条件路径与无条件路径同时存在时，无条件的那条获胜（它永远在）。

**反向边是派生的，不落盘**：摘要里存的是每个文件**自己写的** `#include`（直接边），"哪些文件包含这个头"是图的属性而不是任何文件的属性，所以它从摘要现算，内存里存。写进磁盘就等于存了一个结论：它没有哪个文件可以跟着一起失效，而它和摘要第一次不一致时是看不出来的。

**`MacroEnvironment` 被删掉了**（曾是 `cache.rs` 里的一个类型 + 键里的 `macro_env_hash`）。它算的是"沿 include 链累积的、定义过宏的文件的 content_hash 集合"，用来让"某个头文件改了宏"这件事传播到它下面每个文件的键上。删它的理由是**它算出来的东西对摘要的内容没有影响，却是唯一一个必须走一遍图才能算的键成分**——于是 `get` 不得不在查盘之前先解析，磁盘缓存因此只省了"写"，从来没省下"解析"。证据是三件关于生产者的事实：`build_scopes` 只吃语法树；`build_facts` 用预处理状态只为**找指令位置**（每条事实记下自己所在的 `#if`，让消费者去判断，这正是 guard 存而不用的原因）；`#include 宏名` 永远解析不出来。详见 `cache.rs` 的模块文档与下面"第三个被测试抓出来的键错误"。**如果哪天摘要开始依赖宏**（在声明里做展开、或者把 `#if` 的未取分支剪掉），环境必须回到键里，并且同一次改动里必须抬 `FORMAT_VERSION`——否则盘上已有的摘要不是"取不到"而是"悄悄错了"。

### 单文件那一半

`sema::resolve::definition_at(scopes, root, offset) -> Known<Binding>`。它问的是"游标下这个名字在本文件里指向哪条声明"，**只看作用域链**：

```text
做：   作用域链（含 `using namespace` 带来的命名空间）
不做： 基类、ADL、重载选择、`using Base::m`、限定名 `ns::count`、任何跨文件的东西
```

不做的那些**不是遗漏，是下一层**——但消费者必须能区分"没找到"和"没找过"，所以答案一律是 `Known`：`Yes(声明)` / `No`（本文件可达作用域里确定没有）/ `Unknown(原因)`。为跨文件这一条新增了 `UnknownReason::NotDeclaredHere(名字)`：名字在别的文件里，这是关于**本文件**的事实，而不是"这个名字不存在"。

**排序是答案的一部分**：栈的最后一个是最近的作用域，所以"哪个声明赢"完全由 `scopes_to_search` 的顺序决定。第一版把链先压栈、外围作用域压在上面，结果**最外层每次获胜**——局部遮蔽被跳过了。抓它的是遮蔽测试，别的测试都抓不到。

**一处已知的过度近似**：`using namespace` 的目标按"文件里所有指令命名的命名空间"取，而不是"游标可见的那些"。代价是文件里有两个指向不同命名空间的指令时可能跳错一次；反向收紧的代价是把一个明明可见的名字报成未声明。已写在函数文档里。

## 三条不变量（比功能清单重要）

1. **索引存事实，不存结论。**
   summary 里只有"这个文件写了什么声明/宏/包含"，**任何已解析、已推导、已实例化的结果都不落盘**。理由是可增量性：一个 `#define` 变化会改变依赖它的每个文件里每个名字的含义，一旦把结论写进缓存，一次改动就要全库重算；而事实的失效范围是**可计算的**（反向 include 边 + guard 剪枝）。
2. **`Unknown` 是一等公民，且在完整系统里也保留。**
   文件没索引、正在编辑、解析有错、名字依赖模板参数、展开超预算、`#if` 无法判定——这些都返回 `Known::Unknown(reason)`，而不是猜一个答案。语言服务器的价值在于"**知道自己在哪些地方不知道**"，`UnknownReason` 已经把这套词汇建好了（`DependentName` 等）。
3. **parser 宽容，语义层必须验证来源。**
   parser 是容错的（解析出错也留下无损的树）。语义层只能相信**干净解析**的文件里的声明；有错的文件其声明标记为"部分已知"，参与解析但可以被查询方降权。这是"全都要做"的代价：越往上做精确推断，越要清楚手上这份事实有多可信。

## 事实的形状：两个不得不再三确认的决定

**限定名要存限定路径，不能只存名字。** 一条 `DeclFact` 带 `name` 加 `scope`（声明所在作用域的**限定拼写**，如 `ns::C`）。

- 没有它，`ns::C::f` 查不到：名字本身不标识一条声明——两个文件可以各声明一个 `Widget`，一个文件可以在文件作用域和类里各有一个 `f`。
- 存**拼写**而不是 id，因为 id 是运行期 interner 的下标、重启即失效；拼写还能被 symbol 搜索直接显示。
- 派生它的前提是 `Scope` **记录自己引入的名字**（`Scope::name`），并且 `namespace a::b` 与 `namespace a { namespace b {` 必须产出同一条限定名——两处都有测试钉住。

**`include` 与 `path` 存路径，不存 `FileId`。** 同一个理由，而且更硬：`FileId` 写进磁盘之后，下一次运行读回来的含义是另一回事。反向 include 图因此是**从事实在内存里重建**的，不落盘——那正是"存事实不存结论"的直接推论。

**一处与不变量 1 有张力的地方，摆明在这里**：`IncludeFact.resolved`（`#include "widget.h"` → `/p/widget.h`）**确实是**项目层面的结论，不只是文字的事实——它取决于文件所在目录、include 路径，以及那个文件**到底在不在**。之所以还是存下来，是因为可见性走查（`index::project` 的 `visibility_of` / `includers_of`）只拿得到摘要，而它每问一次名字就要走一遍图；把解析推迟到查询时意味着把 resolver、provider、配置全都搬进 `ProjectIndex`，图的形状会在每次查询里重算。

存它的代价被两件事兜住了：（a）目录和配置进了键（见上），所以"键相同 ⇒ 解析结果相同"，复用不会串台；（b）**解析不到的 include 让摘要不落盘**（见下），所以磁盘上任何一份摘要里的 `resolved` 都是当时真实解析出来的。剩下的那个洞要说清楚：**"某个候选路径到底存不存在"不在键里，也不该在**（键必须能从文字算出来），所以"一个头文件被创建出来、并且排在某条搜索路径的更前面"这种事，键看不见——那是监听层的活。真正想做干净的那一天，走法是把 `resolved` 从摘要里拿掉、改成查询时解析，那是 schema 变更，值得单独一轮。

## 缓存与失效

- 目录：`<project>/.cppls/summaries/<hash 前两位>/<key>.bin`（一文件一摘要，**不要一个大 blob**）。`.cppls/` 已在 `.gitignore` 里——它随 checkout 走是刻意的（CI 拿到同样的热缓存），但派生数据永不入提交。
- 键：**`content_hash + context_hash + format_version`**。三个成分都是**能从文字和路径直接算出来的**——这不是巧合，是要求：只要键需要"先解析才知道"的东西，查盘就必须排在解析之后，缓存也就永远省不下解析。
- `context_hash` = 编译配置（include 路径按 `working_directory` 解析后、`-D`/`-U`、标准、目标）**加上文件自己所在的目录**。配置和目录是同一个问题而不是两个：`#include "widget.h"` 的意思是"**我旁边那个**"，所以同一段文字放在两个目录里是两份不同的编译、会解析到两个不同的文件。
- `format_version` 含 parser 版本号：parser 一升，整库作废。字节格式另有一个 `CODEC_VERSION`（写在文件头里），两者变化的原因不同：加字段两个都动，调整一条记录的字段顺序只动后者。**删掉键里的一个成分只需要动 `CODEC_VERSION`**：旧条目只是取不到（键的名字变了），永远不会被当成新键的答案，因为读回来的键要和刚算出来的键逐字段相等才算命中。
- 写盘是 `.tmp` + rename：崩溃留下的是旧摘要，而不是半份新的——**半份摘要是活的错答案，比没有更糟**。
- 读盘失败（缺失、损坏、版本不符）一律是"重建"的指令，绝不留一个字段取默认值的半份摘要。解码器对截断、超长计数、越界枚举值逐个报错，并且**拒绝尾随字节**。
- 启动：只 `stat`，命中即复用；mtime 变了算内容哈希，**哈希命中旧摘要直接复用**（分支切换因此从"全量重解析"变成"只读盘"）。内容真变了才重建，并沿**反向 include 边**做工作集失效。
- 批量变更（切分支/merge/格式化）：两段式——**打开的文件 → 它的 include 闭包 → 其余**，由 `index::worklist` 实现（一步一个文件，调用方决定节奏）；UI 不阻塞，未索引的文件查询返回 Unknown 而不是等。
- 监听（`notify`）：**过滤 `.git/` 与构建目录**；`compile_commands.json` 变更 = 配置维度全局失效（摘要本身仍可复用）。重命名按内容哈希复用。**文件的创建与删除必须让"它所在目录的包含者们"失效**，因为哪些候选路径存在是键看不见的那一半（见上）。

### 驱动层：`SummaryStore` 的三条规则

`index::store` 只做三件事：`get(path)`（现在是文件**当前**该有的摘要）、`invalidate(path)`（改了以后的工作集）、`stats()`（命中率）。它不监听文件系统、不排调度、不碰线程——和 `FileIndexer` 对解析的态度一样。

**规则一：先查盘，后建。** 顺序是：读文字 → 算键（哈希 + 语境，两者都不需要解析）→ 盘上有就直接用 → 没有才建、落盘。命中时**连 include 都不去找**（有测试用 provider 的探测量钉住这一点）。这条规则是宏环境离开键之后才成立的，见上；它也是"缓存到底省了什么"的答案：省的是解析，不只是写。

**规则二：记录了"没找到某个头文件"的摘要绝不落盘。** 那是一条关于**文件系统**的事实，而键必须能从文字算出来，于是键里没有"哪些候选路径存在"这一项——存下去就会在头文件出现之后继续说"找不到"，没有任何东西会发现。这种摘要照建照返回，只是不写，并计入 `StoreStats::unstored`：理由和不变量 2 是同一条，错的条目比没有的条目糟。注意规则只管**解析失败**，不管"包含的文件还没被索引"——后者是关于索引的事实，不是关于这份文字的事实，而且它自己会好。

**规则三：文件不能读不是错误。** 被删掉的文件、不是文件的路径，`get` 一律返回 `None`：调用方问的是一个不存在的文件，答案是"关于它没什么可说的"。**读得到但解析有错**是另一回事，照建摘要：parser 是容错的，一份带错文件的摘要正是半可用的编辑器要的东西。写盘失败同理（不报错）——只读 checkout 是完全正常的用法，它不该把编辑器变成坏的。

### 顺序层：`Worklist` 的两段与两个队列

`index::worklist` 只回答一个问题：**下一个索引哪个文件**。它是 `step()` 一步一个文件的驱动，不是返回 `Vec<PathBuf>` 的计划——因为**一个还没被索引的文件的 include 是不知道的**：每一步摘要到手，才多知道一层下一轮要做什么。这一步的形状同时决定了它的用法：编辑器每个空闲 tick 走一步，后台线程循环到 `None`，有预算的调用方随时停手（列表保持状态，没走到的文件查询返回 `Unknown` 而不是等）。

**两段，两个队列，不是因为两段代码不一样，而是因为一个队列会错。** 两半做的事完全相同（从种子出发的广度优先，跟着 include 走），只有一个队列看起来更简单，但那样一来"调用方列了一万个项目文件"就把"用户正开着的那个文件的闭包"挤到了最后——而那正是第一段存在的理由。有测试用一个比闭包更长的项目列表钉住这一点。

**第二段也跟 include，因为调用方的清单通常只有翻译单元。** `compile_commands.json` 里只有 `.cpp`，头文件一个都没有；不跟 include 的话，索引里除了"某个打开的文件恰好够得着的头"以外什么头文件都不会有。代价要说明白：**工作列表是它拿到的种子的传递闭包**——一个 include 了 `<vector>` 的根，在有系统 include 路径的机器上会把那些头也拉进来。要收窄就收窄种子（或者停手），这一层不对"哪些目录值得索引"发表意见。

**去重与终止**：按规范化路径建 `seen`，所以菱形包含只走一次、循环包含会终止、`open` 与 `project` 里同时出现的文件**只走一次且落在第一段**（它确实是"用户正看着的文件"，这就是第一段存在的理由）。

**一步的结果不问 store，而是看计数器的位移。** `StoreStats` 是累积的，所以 `StepOutcome` 是"这一步期间计数器往前挪了多少"——正因为如此它才是 `Copy` 且可比较的：store 自己的账就是唯一的一份账，另存一份在 `Worklist` 里就是第二个要同步的东西。`Unstored` 蕴含 `Built`（先建了才发现不该落盘），顺序按这个读。

### 三个被测试抓出来的键错误

三个都是**看起来在工作的错答案**，都靠"重启后重新打开应该命中"这一类端到端断言暴露：

1. **占位键被原样存了下来。** `SummaryStore` 当初必须先建摘要才能算环境，于是给 `FileIndexer` 传了一个占位键 `SummaryKey::new(0, 0, 0)`；而 `FileIndexer` 把调用方的键**原样**存进摘要。结果整个项目每份摘要的 `content_hash` 都是 `0`——全项目共用一个缓存条目。缓存**看起来是好的**：一个文件写进去，一个文件读出来，命中率 100%。它回答的是另一个文件。修法是让 `FileIndexer::index_tree` 用**它手里那段文字**覆盖 `content_hash`。**症状的形态值得记住**：`let _ = source;` 这种"参数收下了但没用"就是它的气味。今天这个 bug 已经不可能发生——键在解析之前就算好了，没有占位键可传——但覆盖那一条留着，它是"谁更清楚这段文字"的答案。
2. **目录不在键里。** 摘要里存的不只是"文字说了什么"，还有它的 include **解析到了哪里**；而 `#include "shared.h"` 的解析结果取决于**文件自己的目录**。于是 `a.h` 和 `sub/b.h` 内容相同时共用一个条目，第二个文件拿到第一个文件的解析结果——一个跳到它根本没包含的头文件上的定义跳转。修法是把目录并进 `context_hash`，并把 `config_hash` 改名为 `context_hash`。
3. **宏环境在键里，而它不该在。** 它不是错的答案，而是**不可能命中的缓存**：要在查盘之前算它，就得先解析，于是每一次"命中"都已经付过解析的代价。修法是删掉它（连同 `MacroEnvironment`），键变成两个成分，`get` 变成"先查盘"。这一条被记在这里而不是当作"优化"，因为它推翻的是本文档自己写下的键的定义。

顺带定下的一条：**相对 `-I` 按 `working_directory` 解析后参与哈希**。这样"换个目录跑编译器但 `-I` 一个没变"仍然命中（命中率），"相对 `-I` 在不同工作目录下指向不同目录"则不会共用条目（正确性）。两个方向都有测试。

### 被删掉的东西：`key_for`

`SummaryStore::key_for(path, source)` 曾经回答"这段文字在磁盘上有没有现成摘要"。它**要么不健全、要么没用**，所以删了：

- 它只用**已经持有的**摘要算宏环境，所以当 `source` 与持有的文字不同时，它给出的键**不是 `get` 会给出的那个**——它的文档承诺（"`path` 以 `source` 为内容时会有的键"）根本无法兑现；
- 而当 `source` 与持有的文字相同时，那份摘要**已经在内存里了**，这个键什么也没多说。

能兑现这个承诺的只有 `get`——而且现在它兑现得很便宜：键在解析之前就能算出来，所以"这个文件现在该是什么键、盘上有没有"不再是一个需要单独 API 的问题。

## "全都做"的顺序（以及为什么）

按依赖排，不能跳：

1. **事实层**（summary + include 图 + 反向边）——其他一切的地基；
2. **名字解析**：作用域链、`using`/限定名、跨文件（include 图上的可见性）；
3. **类型与重载**：需要准确的声明集，因此依赖 1、2 的完整性；
4. **模板实例化**：需要前两者 + 精确预处理；这一步开始"出错的文件"会明显影响结果；
5. **ADL**：需要完整可见性模型。

每一层加的是**查询**，不是索引字段——这条与不变量 1 是同一条。每层都必须能降级：下层缺失时上层返回 `Unknown(reason)`，而不是返回一个低置信度的猜测（猜测只在**读法**层允许，那是 parser 的形状偏好，且已经被测试钉住）。

## 索引与 parser 的关系：先不接

`cpp_parser::SymbolTable` 接口已经存在，而且 **`impl SymbolTable for ScopeTree` 已经能跑**——parser 今天就能吃真实语义信息。但跨文件的那一半**故意还没接**，理由是接口的形状：

`kind_of(&str)` 是**无位置**的，而 `#include` 的可见性是**有位置**的：

```text
第 3 行:  g(1, 2);        // 此刻 g 只是个没见过的名字
第 12 行: #include <x.h>  // x.h 里声明了 void g(int, int);
```

把"闭包内所有名字的并集"喂给一张无位置的表，第 3 行的 `g(1,2)` 会被读成**声明**（按 `g` 是类型），而它其实是调用。表仍然只影响读法、不影响结构（`tests/symbols.rs` 钉住了这一点），但**读法是错的**——正是 A0 类问题。

三条路：

- **(a) TU 级并集**：零成本，对绝大多数真实代码正确，在上面那个形状上误读；
- **(b) 位置感知表**（`kind_of_at(name, offset)`）：正确，代价是每次查询一次区间/链查询。`preprocess` 已有同形的 `PositionalMacros`，模式是现成的；
- **(c) 只服务导航，不给 parser 喂跨文件结果**（当前选择）。

**选 (c) 的理由**：本项目最贵的资产是 **parser 读法的稳定性**——`grammar-gaps.md` 1300+ 行、41 个已修条目、14 条维护约定都是围绕"读法可解释、可钉住"积累的。跨文件表一旦接入，同一份源码会因索引状态不同而解析成不同形状，所有形状断言的语境都变了。而导航（跳定义、找引用、符号列表、补全）**根本不需要 parser 知道任何事**——它要的是"名字 → 声明 + 可见性"，是另一种数据结构。

等 (c) 跑出真实的 `Unknown` 比例之后再决定 (a)/(b)：那个数字本来就是用来决定"回头改范围还是继续加功能"的。

## 先量四个数（再铺开）

1. 每文件摘要构建耗时；2. 1 万文件的常驻内存与缓存体积；3. 切分支后的缓存命中率（目标 >90%）；4. **`Unknown` 比例**（若大多数查询以 Unknown 结束，说明该回头改范围而不是加功能）。

第 3 个数现在才**真的**是"命中率"：宏环境在键里的时候，每次"命中"都已经付过解析的代价，`reused` 计的是写盘被省下的次数。今天 `reused` 数的就是被省下的解析次数，`hit_rate()` 的分母是"读过且需要回答的文件数"。

第 1 个数的第一次测量有工具了——`cargo run --release -p cpp_code_analysis --example measure -- [file.cpp] [轮数] [-I 目录]`，它用同一个文件量"建一次"和"命中一次"的比值（每次命中都新开一个 store，因为已经答过的 store 把摘要留在内存里，而重启要付的是查盘）：

| fixture | 构建 | 命中 | 倍数 |
|---|---|---|---|
| 合成单元，581 KB / 24000 条声明 / 2002 个宏 | 376 ms | 3.4 ms | **111x** |
| `cpp_parser/tests/real_world.cpp`，3 KB / 31 条声明（另给 `-I` 让它能落盘） | 2.4 ms | 0.28 ms | 8.5x |

小文件那个倍数低是应该的：命中的代价是"读 + 解码一份摘要"，跟摘要大小走；构建的代价跟解析工作量走。这两个数就是"缓存到底省了什么"的答案，也是第 3 条（`reused` 的定义）的证据。

顺带一个副产品：这个例子在 fixture 的 include 解析不出来时会**明说"这个文件不会被缓存"并列出没解析到的头文件**，而不是报一个 0% 的命中率——那条规则值得让用的人看见。

## 下一步（已定，未做）

已经是"能跑"的部分：`SummaryStore` 的建/复用/失效，以及"先查盘、后建"（18 个测试：一次"关掉重开、全部命中、一次解析都没有"的端到端，和一个用 provider 探测量证明"命中时连 include 都不找"的测试）；`Worklist` 的两段式顺序（10 个测试，其中一条**用 provider 的读取顺序**断言"打开的文件 → 闭包 → 其余"，另一条用比闭包更长的项目列表钉住"闭包不会被挤到最后")。还没做的，按顺序：

1. **`notify` 监听**：过滤 `.git/` 与构建目录；`compile_commands.json` 变更 = 配置维度全局失效；**文件的创建/删除要让它所在目录的包含者失效**——这是键看不见的那一半（候选路径是否存在）。监听层是第一个真正需要线程的地方，而 `SummaryStore`/`Worklist` 都刻意不含线程意见，所以它可以是薄薄一层。
2. **项目文件清单**：`Worklist` 要 `project` 列表，而"从一个目录里找出所有 `.cpp`/`.h`"这件事现在没人做——忽略规则、`.git/`、构建目录的过滤都还没有。它和监听层共享同一套过滤规则，所以两者应该一起设计。
3. **先 `stat` 后哈希**：mtime 没变就不算内容哈希。这条需要一个"路径 → (mtime, 上次的键)"的盘上旁表，它跟反向 include 边是同一类东西（可丢弃、可从摘要重建），不是"某个文件的属性"，所以要么内存重建，要么做成显式可丢的表。收益是省掉"为了算哈希而读一遍整个文件"——对一万个文件就是一万次全文件读。
4. **真跑一遍那四个数**：第 1 个有工具了（`examples/measure.rs`），命中率也有计数器，但**常驻内存与缓存体积**还没有测量代码。
